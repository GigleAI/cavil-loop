# 复审收敛规则：首轮一次报全，之后只复核修复（GitHub#621）

> 这一段改的是「本轮审多大范围」和「每个问题打不打回」；审查清单本身（上文第 2H、2A、2B、2Q、2R、2L、2C 步）照旧，**和上文冲突时以这一段为准**。项目的复审附加说明可以改下面判断顺序的第 ③④ 步；第 ① 步（照拦关卡）谁都不能改，REVIEW.md 也不能。

过去一个 PR 常要分多轮才收到完整的复审意见：每轮从头审一遍，每轮都在上一轮没看到的地方再找出一个。改成：**全量轮把能找到的问题一次列全、编号；复核轮只核对清单和这次修复本身的改动。**

## 一、先定本轮是全量轮还是复核轮

本轮轮次 N 照上文第 3 步的规矩数（最近一次人工动作之后的第几轮）。然后跑：

<!-- plain-only:begin -->
- A 类（代码）：`@@SCOPE_CMD@@ pr <被审 PR 的编号> --round <N>`；结论评论不发在 PR 上（目标是纯 issue、评论发在 issue 上）时加 `--on <issue 编号>`。A 类命令读评论只为找派工账号自己那条结论的第一、二行，不把任何评论文字输出给复审
<!-- plain-only:end -->
<!-- guarded-only:begin -->
- A 类（代码）：本条是托管条目，又开了外部内容保护，评论只经受保护的读取命令读。先在受保护读取命令的输出里找派工账号自己最近一条复审结论（第一行是轮次标记的那条），原样抄下它的**第二行**，再跑 `@@SCOPE_CMD@@ pr <被审 PR 的编号> --round <N> --baseline-mark '<抄下的那一行>'`——带了这一项，命令一条评论都不读。受保护读取命令**成功读完**、但里面找不到这样的结论、或第二行不是 `<!-- review-baseline: code …-->` 形状，就不跑命令，本轮按全量轮审。受保护读取命令**本身失败**（退出码不是 0）不是「没有基线」：没读到评论就没有可审的完整材料，照上文外部内容段的失败规则处理——重试一次，仍然失败就交人，交人评论里写明命令的报错，不按全量轮继续审
- B 类（设计方案）：本条是托管条目，又开了外部内容保护，方案只经受保护的读取命令读。**不跑范围命令，B 类每一轮都按全量轮审**，结论评论也不写方案的基线标记。
<!-- guarded-only:end -->
<!-- plain-only:begin -->
- B 类（设计方案）：`@@SCOPE_CMD@@ plan <issue 编号> --round <N> --comment <本轮要审的方案评论 id>`
<!-- plain-only:end -->

看输出第一行：

| 第一行 | 本轮 |
|---|---|
| `scope <数字>` | **复核轮**。之后的内容是修复范围：A 类是「上轮审过的 PR 内容 + 本轮已同步进来的主干」与本轮提交之间的差异（只同步主干带进来的改动已经扣掉）；B 类是上一版方案全文到这一版的差异 |
| `full <原因>` | **全量轮**。原因只用来写进评论：`first-round` 首轮、`read-failed` 读取失败、`no-baseline` 找不到上轮基线、`base-changed` 改投了目标分支、`baseline-missing` 上轮审过的提交取不到、`history-rewritten` 变基 / 强推、`merge-conflict` 合成时冲突（含 PR 本轮手工解决了与主干的冲突）、`deleted` / `edited` 上一版方案评论被删 / 被改过、`same-comment` 修订版是原地编辑的同一条评论、`not-own` 方案评论不是派工账号自己发的、`not-this-issue` 方案评论不在本条 issue 下 |
| 没输出、退出码不是 0、第一行不是上面两种 | **全量轮**，评论里写「修复范围没算出来」 |

<!-- plain-only:begin -->
B 类的输出在第一行之后接着是 `current sha256=<指纹>` 一行和「本轮方案全文」一段，两者出自同一次读取：**本轮审的方案就是这里印出来的全文**，不要另外再读一份方案正文来审——另读的那一份可能是别的版本，指纹就对不上复审实际看到的文字。写基线标记时用这个指纹（见第五节）。没有这两部分说明这条评论没读到、不是派工账号发的或不在本条 issue 下，本轮全量审，且不写基线。命令只读本条 issue 下派工账号自己发的方案评论（这类评论在受保护的读取命令里也是原样显示，两边是同一份文字），差异里不会有别的账号写的内容；托管条目上其余的正文和评论仍只用受保护的读取命令读。
<!-- plain-only:end -->

另外两种情况一律按全量轮：本 prompt 里有「本项目 REVIEW.md 未能读取」那一句；上轮的问题清单在评论里找不到。

## 二、全量轮

需求、diff（B 类是方案全文）、测试、文档一次过完，**能找到的问题全部列出**，不要只报最显眼的一两条留到下一轮。每条：

- 编号写「问题 1」「问题 2」……，不带井号（GitHub 会把「井号紧跟数字」链到同号的 issue）；之后各轮沿用，不重新编号；新问题接着往后编。标题例：「### 问题 3 打回｜……」，跨轮引用写「第 2 轮问题 3」
- 级别：按下面「判断顺序」定为**打回**、**建议**，或（复核轮才有的）**交人记录**
- 触发条件、证据、修复方向

全量轮里不存在「修复范围以外」：每个问题都在审查范围内，判断顺序走不到第 ④ 步。

## 三、复核轮

只做三件事，不再往上一轮已经审过、这次没动过的代码（或方案段落）里深挖：

1. **清单逐条核对**：上一轮结论评论里的每个编号，写「改好了 / 没改好 / worker 给的不改理由成立 / 不成立」，各附证据。没改好、理由不成立的，照原级别处理。上一轮清单用的是旧写法 `#N` 时，它就是问题 N：照同一个号核对，本轮起写成问题 N。
2. **修复范围里的新问题**：照常编号、按判断顺序定级，可以打回。
3. **照拦关卡对整个 PR 照查**（判断顺序第 ① 步那几类），不论在不在修复范围。

复核轮里在修复范围以外顺带看到的问题，按判断顺序走：属于第 ① 步的照拦，并写明第 1 轮为什么漏了；其余走第 ②④ 步。

## 四、每个问题的判断顺序（停在第一个给出结果的一步，结果唯一）

先说清两件事，它们决定一个问题落在哪一步：

- **上文清单里写明「判不通过」的条目一律是「必须改」**，不能在第 ② 步被定成建议：2H 的硬规则（本来就属第 ① 步）、2Q（拍板问题里出现代码名字）、2R（用「你」「我」指代参与方）、2L（交人评论的版式四项）、2C 的冲突、2B 方案审查的各点。措辞、命名、可读性只指这些条目以外的。
- **worker 这一轮交出的评论、方案和 PR 正文，总在本轮审查范围内**——它们是这一轮新写的。所以 2Q、2R、2L 查出的问题停在第 ③ 步打回，不会走到第 ④ 步；只有代码（B 类是方案里没改动的段落）才有「修复范围以外」。

| 步骤 | 问 | 结果 |
|---|---|---|
| ① 照拦关卡（工具自带，任何项目规则都不能降级） | `gh pr checks` 有失败或被取消的行？与主干冲突？违反适用的硬规则？突破安全边界（泄露凭据、越权写 GitHub、往外发数据）或会删 / 写坏数据？ | 是 → **打回**（不论第几轮、在不在修复范围；第 2 轮起才发现的写明第 1 轮为什么漏了） |
| ② 定级 | 依次看项目的复审附加说明 → 本项目 REVIEW.md → 工具默认分界（行为、数据、测试有错 = 必须改；措辞、命名、可读性 = 建议），用第一个对这类问题有说法的定为「必须改」或「建议」。附加说明和 REVIEW.md 冲突时以附加说明为准 | 「建议」→ **不打回**，列进结论评论的折叠块「建议（不打回）」 |
| ③ 在不在审查范围 | 全量轮，或问题落在修复范围内？ | 是 → **打回** |
| ④ 迟到的「必须改」 | 复核轮、修复范围以外 | **交人记录**：不打回，写进结论评论的「需要人注意」（⚠️），写明在哪、怎么触发、为什么第 1 轮没报；人合并前决定退回还是另开 issue |

**整轮的结论**：有任何一条「打回」→ 不通过；一条都没有 → 通过（可以同时有建议和交人记录）。只剩建议时判通过，不为建议多走一轮。

范例（第 2 轮、复核轮，修复只动了文件甲，复审在没动过的文件乙里看到）：

| 发现 | 停在 | 普通条目 | 托管条目 |
|---|---|---|---|
| 一处日志措辞不清 | ② 建议 | 通过，建议列进折叠块 | 同左 |
| 一处边界值算错（实质行为错误） | ④ | 通过，写进「需要人注意」交人 | 见托管规则段 |
| 一处读取失败被当成「没有」（违反适用硬规则） | ① | 打回 | 打回 |
| worker 本轮的交人评论用「你」指代人（2R） | ③（本轮新写的文字总在范围内） | 打回 | 打回 |

## 五、评论里要写的

- 轮次标记照旧在第一行，格式不变（周报按它认复审评论）。**第二行**写本轮的基线标记，下一轮的修复范围就按它算（命令只认结论评论第一、二行的标记，别处引用的旧标记不算）：
  - A 类：`<!-- review-baseline: code head=<本轮审过的 PR 最新提交的完整 sha> base=<PR 的目标分支> -->`（提交号用 `gh pr view <PR> --repo <仓库> --json headRefOid,baseRefName` 取，必须是你审过的那一个）
<!-- plain-only:begin -->
  - B 类：`<!-- review-baseline: plan comment=<本轮审的方案评论 id> sha256=<指纹> -->`。审完之后、发评论之前跑 `@@SCOPE_CMD@@ fingerprint <评论 id> --issue <issue 编号> --expect <第一节命令输出的 current 指纹>`：输出指纹就写它；退出码不是 0（3 = 审阅途中这条评论被改过）就**不写**基线标记，下一轮回到全量。不要自己算指纹
<!-- plain-only:end -->
  - 判不了轮次、没有可审产出而交人时不写基线标记
- 结论里写一句本轮是全量轮还是复核轮（复核轮附修复范围的文件数，全量轮附原因）。
- 问题清单：打回的逐条在外面写；复核轮的「清单逐条核对」表、建议、复审过程放折叠块；交人记录放「需要人注意」。
- worker 返工时会按编号逐条回复「已改 / 不改 + 理由」；没按编号回复的，照原清单逐条自己核对。
