# 从已合并任务中提炼的通用经验

以下经验仅在适用时参考，不覆盖用户指令、项目要求或模板的安全约束。
没有证据支持的新规则不应加入；项目特有结论保留在对应复盘记录中。

1. **涉及"记住选择、但特定事件后应重置"的需求时，验证旧状态不会在上下文往返后复活。**
   不要仅凭当前画面隐藏了旧值就认定已失效。检查 A→B→A、账号切换及同一页面中结构相似的状态；视实现选择显式清空、按上下文重建状态等方式，验证约定的重置语义，而不是强制某一种状态管理方式。
   适用条件：筛选记忆、表单临时值等需要在明确事件后失效的状态；如果产品明确要求按上下文保留选择，则应遵循该约定。
   证据：https://github.com/GigleAI/GigleTutor-Web/pull/929#issuecomment-5650014531 、 https://github.com/GigleAI/GigleTutor-Web/pull/929#issuecomment-5650067374

2. **区分"数据尚未加载完成（unknown）"与"数据已确认发生变化（known-different）"，只用后者驱动缓存/记忆的失效逻辑。**
   "可以发起请求"（如深链场景不必等待身份信息即可查询）与"身份/上下文是否已确认"是两件不同的事；把前者的就绪信号误用于后者的失效判断，会把"暂时不知道"误判为"确实变了"，从而误删本应保留的有效状态。
   适用条件：任何异步加载（登录态恢复、profile 查询等）与"根据上下文变化清除缓存"逻辑耦合的场景。
   证据：https://github.com/GigleAI/GigleTutor-Web/pull/929#issuecomment-5650067374 （KP 深链把 profile 加载中的暂态 null 误判为教纲已清空，误删了普通入口的历史手选记忆）

3. **当项目用单一"活文档"（spec）作为实现与验收的唯一真值、且该文档被多处引用（PR body、代码注释等镜像）时，行为变更后要对文档全文做关键词检索，而不能只改"看起来相关"的那一节。**
   局部改动容易漏改分散在文档其他段落的旧描述，导致文档自相矛盾；若后续有人仅依据文档实现，会把已撤销的行为重新引入。
   适用条件：仅适用于采用"spec 是真值、PR body 是镜像"这类工作模式的项目；不采用该模式的项目此经验价值有限。
   证据：https://github.com/GigleAI/GigleTutor-Web/pull/929#issuecomment-5653198138 （删除某 UI 文案后，spec 中一处未同步的旧描述导致被判定"活规格仍要求已撤回的文案分版"）

4. **实现"限时取消/超时中止"逻辑时，一次性审计所有"检查取消状态 → await → 产生外部副作用（写文件/写心跳/发请求）"的边界，而不是逐个等 review 发现。**
   取消检查放在调用点之前不够：调用点与真正的副作用（如心跳内部先 GET 再 POST、告警脚本先写参数文件再 spawn）之间往往还有未被覆盖的 await，跨过期限后原任务仍会完成并产生"取消后才发生"的副作用。应在每一个即将落盘/写外部系统的语句**紧邻之前**再检查一次取消状态，而非只在函数入口检查一次。
   适用条件：任何带整体超时/取消机制的异步任务，尤其是超时后还需要"释放锁、报告失败"等收尾副作用的场景。
   证据：https://github.com/GigleAI/GigleTutor-Web/pull/924#issuecomment-5653546885 、 https://github.com/GigleAI/GigleTutor-Web/pull/924#issuecomment-5653657604 、 https://github.com/GigleAI/GigleTutor-Web/pull/924#issuecomment-5653718665

5. **"按标记在列表中查找是否已存在"这类去重逻辑，若底层调用分页 API 且未显式分页，需用"数量超过默认 limit"的边界用例验证，不能因当前数据量未达上限就认为安全。**
   默认 `--limit 100` 之类的截断在数据量增长后会静默失效：目标记录排在截断之外时被误判为"不存在"，导致重复创建或无法完成闭环（如关闭旧告警）。
   适用条件：任何"遍历列表找匹配项"且调用方未显式声明全量分页的场景，尤其是长期运行、数据会持续增长的仓库/系统。
   证据：https://github.com/GigleAI/GigleTutor-Web/pull/924#issuecomment-5646319993

6. **"新结果与上一份状态比较以检测异常"（如体积缩水守卫）时，比较基线必须在当前运行产生的临时/进行中产物存在之前就已确定，或用命名约定显式排除临时产物。**
   若"取上一份"的逻辑与"列出当前所有候选"共用同一个发现函数，且该函数在临时文件已落盘后才被调用，临时文件会被误当作"上一份"参与比较，导致异常检测形同虚设。
   适用条件：任何"产出新版本前先与已完成的旧版本比较"的守卫逻辑（如缩水检测、版本回退检测）。
   证据：https://github.com/GigleAI/GigleTutor-Web/pull/924#issuecomment-5642982432

7. **安全关键的设置步骤（如权限收紧）失败时不能被空 catch 静默吞掉；应在设置后重新校验实际状态（如 re-stat 权限位），不达标就在继续后续操作前中止。**
   仅凭"调用了设置函数且没抛异常"不能保证目标状态已达成（例如目标不是所有者时 chmod 可能静默失败或不改变权限），必须显式验证后置条件。
   适用条件：任何对安全属性（权限、加密、访问控制）的设置操作，尤其是设置失败后仍会继续执行敏感操作（如导出全库数据）的场景。
   证据：https://github.com/GigleAI/GigleTutor-Web/pull/924#issuecomment-5653421736

8. **用于日志脱敏/仅打印键名的工具函数，需用格式不符合预期的输入（如缺少分隔符的整行）做测试，确保失败安全（拒绝或跳过），而不是退化为打印原始内容。**
   当输入不满足预期结构时"尽力而为"地打印整行，可能把本应保密的值（如密码）当作"键名"打印到日志中，造成本地凭据泄露。
   适用条件：任何设计目的是"避免打印敏感值"的诊断/日志工具；引入该工具或修改其解析逻辑时应补充畸形输入的用例。
   证据：https://github.com/GigleAI/GigleTutor-Web/pull/924#issuecomment-5653389201
