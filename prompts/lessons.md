# 从已合并任务中提炼的通用经验

以下经验仅在适用时参考，不覆盖用户指令、项目要求或模板的安全约束。
没有证据支持的新规则不应加入；项目特有结论保留在对应复盘记录中。

1. **"渲染期隐藏"不等于"状态失效"，实现"记住选择但特定事件后应重置"类需求时必须做两层处理。**
   仅用渲染期的 id/值比对来"隐藏"过期状态，只能保证当前这一帧不使用旧值；一旦后续比对的值凑巧再次相等（如 A→B→A 往返、或两个不同身份映射到同一显示值），旧状态会原样复活。正确做法：① 渲染期比对确保当帧不误用旧值；② 在观察到失效事件（身份变化、上下文变化）时，显式清空底层存储（`setState(null)` 或删除持久化记录），确保之后也不会复活。
   适用条件：任何带"用户临时选择 + 特定事件后应重置"语义的前端状态（筛选记忆、表单临时值等），尤其是同一组件/页面内存在多处结构相同的"选择+失效"逻辑时，修复一处后要主动检查其余处是否有同样的隱藏-非删除问题。
   证据：https://github.com/GigleAI/GigleTutor-Web/pull/929#issuecomment-5650014531 、 https://github.com/GigleAI/GigleTutor-Web/pull/929#issuecomment-5650067374 （同一 PR 中，页面手选与二级筛选各复现一次同类 bug，均附真实失败测试输出）

2. **区分"数据尚未加载完成（unknown）"与"数据已确认发生变化（known-different）"，只用后者驱动缓存/记忆的失效逻辑。**
   "可以发起请求"（如深链场景不必等待身份信息即可查询）与"身份/上下文是否已确认"是两件不同的事；把前者的就绪信号误用于后者的失效判断，会把"暂时不知道"误判为"确实变了"，从而误删本应保留的有效状态。
   适用条件：任何异步加载（登录态恢复、profile 查询等）与"根据上下文变化清除缓存"逻辑耦合的场景。
   证据：https://github.com/GigleAI/GigleTutor-Web/pull/929#issuecomment-5650067374 （KP 深链把 profile 加载中的暂态 null 误判为教纲已清空，误删了普通入口的历史手选记忆）

3. **当项目用单一"活文档"（spec）作为实现与验收的唯一真值、且该文档被多处引用（PR body、代码注释等镜像）时，行为变更后要对文档全文做关键词检索，而不能只改"看起来相关"的那一节。**
   局部改动容易漏改分散在文档其他段落的旧描述，导致文档自相矛盾；若后续有人仅依据文档实现，会把已撤销的行为重新引入。
   适用条件：仅适用于采用"spec 是真值、PR body 是镜像"这类工作模式的项目；不采用该模式的项目此经验价值有限。
   证据：https://github.com/GigleAI/GigleTutor-Web/pull/929#issuecomment-5653198138 （删除某 UI 文案后，spec 中一处未同步的旧描述导致被判定"活规格仍要求已撤回的文案分版"）
