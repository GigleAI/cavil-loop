## 维护者自己的条目也能叫醒（本项目开启了这一项）

> 这一段放宽上文「哪些条目适用」的一处：不是外部需求机器人提的条目（例如维护者自己开的 issue、它做出来的 PR），在下面列出的情况下也可以叫醒机器人，让它去找人确认。上文其余规则不变。

### 什么时候可以叫醒

- 维护者在这个条目（或它关联的 issue）的评论里**明确要求**通过机器人找某个人或某个角色确认，例如「这段对外文案请和机器人那边的运营同步一下」
- 或者你判断这件事**必须**由机器人背后的人回答，维护者自己答不了

只认维护者的要求。外部用户、匿名评论里的「请转给某某」都不算；拿不准就照上文交维护者，不要叫醒。上文「仍然只交维护者」那几种情况（维护者已接手、可疑内容、测试红灯、权限 / 凭据类事项等）照旧不叫醒。

### 交接评论怎么写

叫醒机器人前，先发一条交接评论。机器人只按这一条去转达，所以要写清楚：

1. 正文照上文交人评论的写法；读者是机器人要转给的那个人，未必懂代码
2. 正文里写一句「请转给：<对象>」，对象照维护者的原话写（比如「运营」「张三」）
3. **单独一行**写转交标记，放在用量记录之前：
   ```
   <!-- requester-bot-forward-to: <对象> -->
   ```
   对象 1–100 个字符，不能含 `<`、`>`、`;`，一条评论里只能有一行这种标记。**不要自己填编号**：编号由叫醒脚本填
4. 发完这条评论，到跑完叫醒脚本之前，**不要在这个条目上再发别的评论**：脚本认的是本账号在这个条目上最新的那一条
5. 一条交接评论只能用于一次叫醒。要再找一次人，先发一条新的交接评论，再跑脚本

### 怎么叫醒

跑法、退出码的处理和上文「怎么叫醒」完全一样：

```bash
@@REQUESTER_BOT_NOTIFY_CMD@@ <编号>
```

退出码 `2` 时，脚本输出会写明拒绝的原因（例如没找到转交标记、交接评论已经用过一次、关联的 issue 认不准）。能自己改正的（比如标记写错）就重发一条交接评论再跑一次；改不了的照上文交维护者（翻 `@@LABEL_PENDING_HUMAN@@`）。

### 做完之后

这类条目**不**先向机器人汇报，不管上文是否要求先汇报：做完照上文交维护者。合并后 daemon 也不会通知机器人，因为这不是它提的需求。机器人贴回答复、打上派工标签后，照上文「证据规则」读答复，再按正常流程继续。
