## 经验教训
1. **"某功能可选"的断言要对照默认路径的触发模板核实**（已确认）。方案阶段写下"⑤⑥ 可选"，实际模板无条件要求先发方案。复审靠读 `dispatch-new-issue.sh` 和模板才发现。
   - 这和已有规则 L2 相近，但复审没有按"前提未实测"定性，所以本次不计次。
2. **固定间隔采样的同步检查有盲区**（已确认）。这是本 PR 返工的第二个根因。维护者转来的参考评论其实已经提示过这一点，worker 在复审后才完整采纳。
3. **换外观的要求替代了此前"不照搬"的决定**。worker 明确声明旧结论被替代，没有悄悄改口。
4. **检查器扩展后抓到了真实缺陷**（"可选"标记越出红框）。这说明逐段判定的检查器有实际产出。

## 最佳实践（有适用条件）
- **适用**：用生成器产出多语言、动静多份落点的图或文档。
  - 做法：说明文字只放在一张内容表里，由生成器统一产出，再逐字节比对产物。
  - 验证：动静说明对拍，并对"静态版说法不同"做负对照。
- **适用**：检查"任意时刻最多一段可见"这类时序属性。
  - 做法：把所有动画的关键帧时间合并，按小段逐段判定。
  - 验证：构造短于旧采样间隔的负对照，确认旧检查放过、新检查拦下，并用旧检查跑同一套测试。
  - 边界：此法只适用于本 PR 支持的离散或受限缓动动画，不是任意脚本或样式行为的通用证明。
- **适用**：参考图与代码行为不一致时。
  - 做法：逐条列出与参考图的差异、改动原因和依据，并写明"不同意回一句改回"。
  - 实践：本 PR 做到了这一点（见上方 5 处文字改动表）。
- **适用**：声明验证状态。
  - 做法：把"实测过的 / 没跑过的"分栏。
  - 实践：PR 正文和各轮评论都明确写了 Safari 和手机 App 未验证。复审也没有把 worker 的网页播放自述当作独立实测。
  - 这与 L11 同向，已记入 L11 的"这样做是对的"，不计次。

## 流程改进
- 方案阶段对"可选 / 默认关闭 / 跳过"之类的流程断言，在方案中注明核对过的模板或代码位置。
- 同步类检查器出厂时就应以"切段判定"为默认，不再先做采样再返工。
- 人工中途指定参考物时，先对参考物做事实核对，再决定整体采用或局部采用。
