## 结果与证据（已确认事实）

- **需求**：长期无活动项目应渐进退避轮询频率，同时「读不到 GitHub」需单独一套节奏、不能被当成「空闲」。动机数据来自实测 poll.log（7 天窗口，两个项目 9581 轮零派工；封号 88 小时内 5 个项目共 30,040 轮全 403）。
- **设计阶段人工深度参与**：`luosky` 在 issue #35 中给出 3 条真实文字回复，分别是「先讲现状」「退避方案是怎样的？本地状态坏了会不会一直卡着？」「阶梯改成按 1/3/7 天分档，心跳用最长间隔」，直接决定了最终阶梯参数和心跳时长（[评论1](https://github.com/GigleAI/cavil-loop/issues/35#issuecomment-5771632493)、[评论2](https://github.com/GigleAI/cavil-loop/issues/35#issuecomment-5771679372)、[评论3](https://github.com/GigleAI/cavil-loop/issues/35#issuecomment-5771773661)）。人工提出的「本地状态坏了会不会卡死」直接催生了心跳/数值夹紧/双时间戳三道防线的设计（[方案答复](https://github.com/GigleAI/cavil-loop/issues/35#issuecomment-5771716271)）。
- **验收口径冲突并被人工重新拍板**：issue 原文「空闲 1 小时降到 1/4」与最终 1/3/7 天阶梯不相容，agent 在 [v2 方案](https://github.com/GigleAI/cavil-loop/issues/35#issuecomment-5771872917) 中提出修订版验收表，issue 正文随后追加说明（未见到 `luosky` 对这次口径变更的单独文字确认，只能视为随方案整体推进）。
- **PR 内独立复审共发现至少 5 类真实缺陷**，均被开发 agent 承认并修复：
  1. 7 天档未生效（期望 2 轮实得 60 轮）——根因不在被测代码，而是测试自身遗留 tmux 会话未清理（[复审](https://github.com/GigleAI/cavil-loop/pull/39#issuecomment-5772373456)，[定位与修复](https://github.com/GigleAI/cavil-loop/pull/39#issuecomment-5772777041)）
  2. 超大数值 `next_due` 在 bash 算术中**静默回绕**成合法未来时间，绕过 fail-open（[复审](https://github.com/GigleAI/cavil-loop/pull/39#issuecomment-5772835326)，[修复](https://github.com/GigleAI/cavil-loop/pull/39#issuecomment-5772997551)）
  3. `last_active`/`fail_streak` 校验时机太晚（在「是否跳过」判定之后才兜底），损坏状态仍会被跳过一轮（[复审](https://github.com/GigleAI/cavil-loop/pull/39#issuecomment-5773080176)，复审轮次用尽转人工；人工仅移除 `pending/human` 标签无文字回复；后续独立复审重开第 1 轮再次确认同一问题——[复现](https://github.com/GigleAI/cavil-loop/pull/39#issuecomment-5774135512)，[修复](https://github.com/GigleAI/cavil-loop/pull/39#issuecomment-5774321544)）
  4. `last_active > last_poll`（写入路径产生不出来的状态组合）仍被判定为「跳过」（[复审](https://github.com/GigleAI/cavil-loop/pull/39#issuecomment-5774424973)，[修复：改用闭包不变式取代逐字段清单](https://github.com/GigleAI/cavil-loop/pull/39#issuecomment-5774726460)）
  5. 前导零数值在 bash 算术中被按八进制解析导致报错（[复审首次上报](https://github.com/GigleAI/cavil-loop/pull/39#issuecomment-5774817905)，[复审再次上报](https://github.com/GigleAI/cavil-loop/pull/39#issuecomment-5776007654)，人工再次仅移除标签无文字回复；[修复](https://github.com/GigleAI/cavil-loop/pull/39#issuecomment-5776234982)）
- **一次关键的「复核而非照单全收」**：针对上述第 5 条，开发 agent 承认缺陷本身属实，但独立实测发现复审报告的具体后果描述（「shell 返回 2，未进入轮询，需人工介入」）与实测（「退出码 0，完整跑完一轮，状态被自动重写」）不符，据此在评论中给出了更正而非全盘照搬（[更正记录](https://github.com/GigleAI/cavil-loop/pull/39#issuecomment-5776234982)）。
- **最终通过**：第 2 轮独立复审确认「未发现可定位、可复现的阻塞问题」（[通过评论](https://github.com/GigleAI/cavil-loop/pull/39#issuecomment-5776318505)），随后由 `luosky` 合并。
- **人工在密集 review-fix 循环期间的参与方式**：两次仅通过移除 `pending/human` 标签让流程继续，**始终未见任何文字回复或 checkbox 勾选**；开发 agent 在两轮回复中都如实标注这是「推断，非确证」，并请求人工纠正（未见后续文字回应）。
- **生产验证缺失（已在 PR 中明确声明，未见后续补充证据）**：PR 正文写明「沙盘全绿 ≠ 生产 daemon 跑通」「本 PR 不拿沙盘结果冒充生产结果」，功能默认开启但第一档需满 1 天才生效，因此合并当天不会看到任何效果变化。本次复盘未见任何后续验证「生产环境调用量是否真的下降」的记录。
- **自指边界**：PR 正文明确声明本项目技能目录软链接指向 main checkout，而本 PR 改的正是复审/派工脚本自身，PR 期间生产 daemon 与复审跑的都是 main 的旧版本，属于本项目第 4 次出现该固定风险点（另见 #27 #31 #37）。

## 经验教训

1. **有效做法**：设计阶段用真实历史日志回放（而非纯理论推导）支撑退避参数选择，并如实披露「这是上界不是预测」，帮助人工快速理解权衡并给出针对性反馈。
2. **返工原因**：初版「状态坏了就该跑」的防护，是按发现顺序逐点打补丁（先补格式校验，被抓到没补位数；补了位数，被抓到校验时机太晚；补了时机，被抓到没验字段间关系；补了关系，还被抓到进制解析问题）。5 轮修复都属于同一类问题（数值/状态合法性判定）的不同变体，说明第一版实现没有先做「输入维度全集枚举」就动手实现，导致同一根因反复复发。
3. **失败教训（可复用）**：review 认定「缺陷属实」不等于其描述的「后果严重性」也准确——本次一次独立实测证明复审报告的具体后果被高估（报告写「需人工介入」，实测是「自动恢复」）。开发方在承认缺陷的同时仍对报告的具体断言做了独立核实，避免了过度修复或错误沟通。
4. **观察（非失败）**：人工在设计阶段深度参与（3 条实质性文字回复直接决定参数），但进入 PR 密集 review-fix 循环后转为纯 relabel、不留文字，依赖自动化独立复审兜底。本次独立复审确实拦住了多个真实缺陷，流程整体有效，但缺乏人工书面确认意味着「复审轮次用尽后是否该继续修」这类关键决策点，事后无法用书面证据还原人工真实意图，只能靠 agent 自行合理推断。

## 最佳实践（含适用条件与验证方法）

- **负对照（negative control）**：每条新增断言都需验证「退回旧实现会让它变红」，本 PR 在 9 组主负对照之外，针对每一轮 review 新发现的缺陷追加了专门的负对照（如「摘掉位数上限」「摘掉字段间关系校验」），是判断「测试是否真的测到点子上」的可操作方法。适用边界：仅能验证「新断言能分辨已知的两种实现」，不能证明「没有第三种同样能通过测试的错误实现」。
- **状态损坏时的 fail-open 设计**：本 PR 最终收敛为「用写入方恒满足的数学不变式判定状态合法性，不合法一律当作跑」，比逐字段列清单更不容易遗漏变体。适用条件：仅在能明确刻画「合法写入的状态空间」时适用；若写入逻辑本身发生变化，不变式需要同步更新，否则可能误判合法状态为损坏（会导致多跑而非少跑，本 PR 中被认为是安全方向）。**关键边界**：此类本地状态只应决定「这一轮是否执行」，不应参与「执行时的具体行为」判定——真值应始终来自实时 API 快照。
- **数值 fail-open 校验需在所有可能返回「跳过」的判断之前统一执行**，覆盖字符类、位数上限（防 bash 算术静默回绕）、进制（防前导零被当八进制解析）三个维度；闸门调用方式本身也应做成「内部异常也等于放行」的结构性 fail-open，而不依赖调用方特定的错误处理路径是否正确（本 PR 中曾出现「调用方式偶然安全，但换一种写法就会变成硬停摆」的情况）。

## 流程改进

- PR 正文用「实测过的」与「负对照」两栏分别列出验证结果，且明确写出未验证事项（生产未跑、验收口径变更等），这种披露格式值得在本项目其他 PR 中延续。
- 复审轮次上限用尽转人工后，若人工只做 relabel 不留文字，建议评论模板显式要求人工在轮次上限时至少勾选一个「继续修 / 就此合并 / 降低验收标准」选项，减少纯靠 label 推断意图的情况（本次已发生两次）。

## 待泛化的流程改进

以下发现具有跨项目参考价值，需经过独立的去项目化审查后才可能进入公开模板：

- 「负对照」作为测试有效性验证手段（退回旧实现、确认对应断言变红）具有通用性，不依赖具体技术栈。
- 「review 报告的缺陷属实 ≠ 报告描述的具体后果准确」——收到问题报告后，除了修复根因，还应对报告中的关键事实性断言（如错误码、是否阻塞、影响范围）做独立复核，必要时予以更正，是通用的问题处理原则。
- 「同一类问题被同一 review 流程连续发现 3 次以上变体时，应转为枚举该逻辑涉及的全部输入维度做系统性收口，而非继续逐点响应式打补丁」是通用的调试/设计策略，不限于本项目的 bash 脚本场景。

## 适用边界

- 本报告结论完全基于 PR/issue 的评论文本、时间戳与 agent 自述的本地测试输出，**未接入任何生产系统日志或部署记录**，因此无法判断合并后生产环境的实际调用量是否如设计所预期下降，也无法确认此后是否有人工做过验证。
- 各条评论 footer 中标注的 `cost_usd`/token 数字仅为该条评论自身的用量估算，本报告不据此推算 PR 整体成本或耗时主因，也不从评论轮数反推调用次数。
- 「人工仅凭 relabel 推进流程、未留文字」的判断依据是证据中 agent 自述及其对 label 时间线的引用，未能独立核实 GitHub timeline 原始数据，视为高置信度的间接证据而非一手核实。
