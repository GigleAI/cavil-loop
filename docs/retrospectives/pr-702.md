## 经验教训
1. **设计方案阶段的实测证据同样要给可复跑的完整命令，不能只给结论性数字**：首轮方案复审被打回的唯一理由就是复跑命令里省略了筛选条件，导致关键数字（"卡片距浮层仅剩约 13px"）无法被独立复现。这与既有硬规则 L34（"PR 正文或交人评论引用对拍或测试计数时，写明命令与口径"）是同一类问题，只是发生在方案评论而非 PR 正文——本次复盘按该规则的精神计入了一次 Seen（详见下节），但这属于对规则适用范围的推断，而非规则原文已经明确覆盖，已列入"建议修改"供人工定夺。
2. **验收运行本身是发现"隐藏"过期检查的有效手段**：方案阶段只定位了两处已知红灯，worker 没有止步于方案范围，而是真正跑了手动 Client 工作流做验收，因而额外发现两处因其他并行 PR（#697）和浏览器时序差异导致的新过期点，避免了"修好方案里的两处、合并后立刻又因另外两处再次发版失败"的情况。
3. **浏览器间时序差异要用"等待异步状态达成"而非盲目加延时/降阈值来修**：设置页目录跳转在 WebKit 上两次失败、本机 Chromium 一直通过，worker 对根因的解释（页面因异步读取变长、平滑滚动途中被打断）明确标注为"推理，未实测"，但修复方式（先等待卡片读完再触发滚动）是在真实 CI 的 WebKit 环境里验证过"失败→通过"的，这是一个"根因推测、结果已验证"区分清楚的好示范。
4. **冲突处理核对权威来源而非简单二选一**：设置总数在合主干时与并行 PR 冲突，worker 核对了登记表当前真实项数（86）后采用主干的值，这是既有经验 L5（合主干后核对新约定）精神的正确应用，未发现返工。

## 最佳实践（附适用边界）
- **实测数字配可直接复跑的命令**：凡在方案或 PR 正文里引用"跑了测试、得到某个数字/结论"，都应附带环境变量、完整过滤条件、受测提交号与运行环境（浏览器/操作系统），使读者无需猜测即可复现。适用于任何会被复审或维护者复核的实测断言；对纯代码走查、无需复现的结论不适用。
- **交付前做一次更大范围的验收，发现范围外的同类问题一并修复，但须标注哪些是原方案范围、哪些是验收新发现**：仅在改动代价低（本 PR 只改测试文件）、且有可低风险运行的验收环境（不勾 publish 的手动工作流）时适用；涉及生产数据或高代价操作时不应擅自在验收阶段扩大范围，应回到方案阶段与人确认。
- **浏览器行为差异以"修复后在失败环境里验证通过"为准，而非仅凭本机能复现的环境跑绿**：本例本机缺 WebKit 系统库、无法本地复现失败，如实说明"未在本机验证、以 CI 结果为准"，而不是用本机 Chromium 的通过结果替代对 WebKit 的验证。
