## 经验教训
1. 同一条规则写进多处指令(已确认有效):规则写进 5 个位置,测试拼出成品对拍,再对每个写入点单独做反例。「别的项目没有附加指令」的场景也实际拼了一遍。这样才没有只改一处就漏掉别的。
2. 设计阶段就识别出关键落点:开了复审关卡后,翻到 `pending/human` 的多是复审那条评论,所以通用复审指令也要改。这是方案里的判断,推断它有效,但缺少部署后证据。
3. PR 正文的反例数字有误(见上)。独立复审复跑发现并更正,说明独立复跑有价值。

## 最佳实践(有适用条件)
- 适用:规则要同时出现在多份 prompt 或模板时。做法:读仓库真实模板,用生产使用的拼装函数生成成品,逐字对拍,并对每个写入点做删除或改一个字的反例。验证:反例全部变红,对旧 main 跑新测试能看到现状缺口。
- 适用:人只看一条交接评论时。做法:步骤、结论、限制写进评论正文,链接只当出处,发出前问「不点链接能否知道发生了什么、要做哪几步」。这是本次采用的一种做法,效果尚待部署后观察。
- 适用:只有 relabel、没有书面确认时。做法:明写「未见书面确认,按方案原样执行」。
- 适用:交付含「改到自己运行时依赖的模板」时。做法:单列「还没验证的」,说明部署前仍是旧版。

## 流程改进
