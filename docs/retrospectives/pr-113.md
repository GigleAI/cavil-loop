## 结果与证据
已确认事实：
- 设计阶段返工 1 轮。首版方案承认没核实入口是否属于 `grokbot` 账号，却仍把入口挂到该账号的准备清单和首页链接上。复审指出，账号对不上会导致邀请、配置错误，作者识别检查也会拒绝需求（issue 评论 6574579672）。
- 修订版改为：入口单独介绍，`grokbot` 只是示例账号名，对接时用实际账号，不承诺开通即可接入。该版本通过复审，并在 PR 中照此落地。
- PR 零返工、无行内评论、无 review。独立复审确认四份文档的入口地址各一处且与 issue 一致，`git diff --check` 通过，与 main 无冲突。
- 独立复审跑 `MUTATION=1 bash tests/requester-bot.test.sh`，退出码 1：1787 通过，6 失败。失败原因是旧版基准提交已含新规则，6 项负对照没有变红。复审核对后认定这是既有基准失效，不是本次文档缺陷，也没有因此打回。
- worker 自报默认模式 416 通过、0 失败。复审说明这与负对照模式的计数不是同一口径。
- 人工动作只见重新打 `pending/agent`，没有书面确认；PR 正文如实写成"按方案原样执行"。

未验证：入口页面内容和长期有效性、入口背后实际的 GitHub 账号、真实接入是否通。合并不代表这些已验证。用量和耗时无法据评论轮数推算，这里不做量化。

## 经验教训
1. 外部入口与现有示例的对应关系没有证据时，不要在文档里默认绑定（推断依据：复审提出的条件性风险，没有实测接入失败）。
2. 现有回归只管文件范围、行数和锚点，证明不了新写说法的正确性。本 PR 补了人工逐句核对和 grep 地址计数，并如实说明回归的局限。
3. 负对照的旧版基准会随主干演进失效（见上面的 6 项）。这是既有问题，需要另行处理，不属于本 PR。

## 最佳实践（适用条件与验证方法）
- 适用条件：文档中引入外部产品入口，而身份对应关系未经核实。做法：只用需求方原话，把入口与示例分开写，并明说"不讲开通配置"。验证：grep 地址次数、grep 禁用说法、中英逐句对照。
- 交付时单列"还没验证的"，把自动回归与人工核对分开披露（与现有 L11 的做法一致）。
- 只见改标签时写"未见书面确认，按方案原样执行"（与现有 L9 的做法一致）。
