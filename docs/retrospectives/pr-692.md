## 经验教训

1. **删除清单要按「谁在执行它」来列，不能只按「它在哪」来列。** 首版方案删掉了工具目录，却只清理了提到它的注释，漏了真正执行脚本的检查步骤。之后的版本靠全仓扫描才逐步补全（https://github.com/GigleAI/cavil-loop/issues/684#issuecomment-7091985949 、https://github.com/GigleAI/cavil-loop/issues/684#issuecomment-7102870373 ）。
2. **验收数字必须和所审提交是同一次运行。** 表里混进了改动中途跑出的数字。条件运行的检查（同版本跳过的新旧对比）让同一个文件在不同时点的通过数不同，复审一复跑就对不上（https://github.com/GigleAI/cavil-loop/pull/692#issuecomment-7150442236 ）。
3. **「总条数不变」不能当删除类改动的验收口径。** 改成「保留 / 删除 / 改写」三类、差额逐条归属之后，方案才可判定（https://github.com/GigleAI/cavil-loop/issues/684#issuecomment-7091985949 ）。
4. **按路径触发的检查会漏掉跨目录的耦合。** 新增驱动的提交没动 `client/`，客户端检查没有运行，写死的列表过期到本 PR 才暴露（https://github.com/GigleAI/cavil-loop/pull/692 ）。
5. **做对的地方：**
   - 人只是提问时，agent 只回答、不开工，并把可选方向列出来由人决定。维护者据此做出了删除的决定（https://github.com/GigleAI/cavil-loop/issues/684#issuecomment-7091633815 ）。
   - 返工时把问题从复审点名的 2 个文件扩查到 12 个，整表在一次运行里重写（https://github.com/GigleAI/cavil-loop/pull/692#issuecomment-7150855600 ）。
   - 删除后失去的保障（不再自动检验测试能否抓住改坏的实现）在正文可见区明示（https://github.com/GigleAI/cavil-loop/pull/692 ）。

## 最佳实践（附适用条件与验证方法）

- **退役一套工具时**：先全仓搜索它的路径和命令名，按调用入口列删除表。验证方法是带排除项的残留扫描，贴出命令输出，剩余命中逐条说明。本次用的是 `git grep`；别的项目可以用等价的搜索手段，关键是由执行入口驱动清单。
- **删除或改写测试时**：按保留、删除、改写分类，改前改后的通过数差额逐条归属。验证方法是整表数字出自同一提交的同一次运行，写明命令、提交和比较基线，与 CI 逐项比对，环境差异单列。
- **有条件跳过的检查时**：表里同时列出「跑了几组 / 跳过几组」，这样读的人能看出数字为什么变。
- **人提出疑问时**：先回答，再列选项，不替人决定范围。验证方法是答复里没有代码或方案改动，并明确写出需不需要人动手。

## 待泛化的流程改进

以下是候选，需要另做去项目化审查后才可进入通用模板，本次不发布：

- 退役工具时，由执行入口驱动删除清单，并做残留扫描验收。

- 按路径触发的检查要留意跨目录的写死清单。
