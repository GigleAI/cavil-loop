## 需求与结果
需求（issue #722）：点「交给 agent」「托管」时若回复框为空，GitHub 上以前只留标签变化，agent 接手后常因看不到人的话而空绕一圈。PR #724 的方案是：回复框为空（含只有空格）时，客户端先发一条「继续」（英文界面「Continue」）评论，发成功再改标签；从旧操作重试（通知里的「重试」、重新托管）一律不再补发，只带旧操作里确定未发出的那段评论。该 PR 已合并（`merged_at` 2026-11-26T04:35:24Z），issue 随 `Closes #722` 自动关闭。

**结果判定边界**：本次复盘只能确认「代码已合并、单元/端到端测试在提交 d5f525b 上实测通过、独立复审复跑部分测试一致」，**不能**证明该版本已在真实生产环境被用户实际使用过（无部署或线上行为数据作为证据）；也不代表 GitHub 完整 CI 已跑完（复审评论自述末次检查时仍有分片在跑，复审本身对此作了披露，见下）。

## 过程与关键证据

### 设计阶段：1 轮打回、1 轮通过
- 首版方案把「补不补默认评论」仅系于「旧操作的评论步骤是否已成功」，漏了评论被人从回复框补发（成功 / 在路上 / 结果未知）等情形，复审第 1 轮判定打回："问题 1 打回｜补发过或结果未知的评论，不能因重试再自动补一条"（见 https://github.com/GigleAI/cavil-loop/issues/722#issuecomment-7181751756 ，`codex-review-round:1` 节）。
- 修订版把六种评论归属情形列成表格一次收口（已发出 / 补发成功 / 补发在路上或结果未知 / 确定未发出 / 原本无评论 / 记录找不到），复审第 2 轮通过（同一条评论 `codex-review-round:2` 节）。
- 本 PR 自身在正文里对 L1（连续三次同根因变体才需整体重写）做出判断「否：复审只打回过 1 轮，没有同源第 3 个变体」——按现有规则定义的计次口径（3 轮以上才算），本 PR 的 1 轮打回不构成 L1 规则所述场景，这一判断与证据相符。

## 有效做法（值得参考，不作为新规则）
1. **方案阶段把"重试是否补默认内容"的全部状态一次性列成表**，比逐条打补丁更快收敛（1 轮打回即收口），避免了本项目历史上多次出现的"同根因连续返工"（对应现有规则 L1）。
2. **用同一个函数承载"补不补、补什么"的判断**，主程序入口与界面提示共用，减少后续维护时两处判断漂移的风险（对应现有规则 L3）。
3. **测试断言的是实际收到的 GitHub 请求（条数、正文），而非源码文本**，覆盖重试在各种评论归属状态下的分支，并保留"全新空回复确实发出一条评论"的正对照（对应现有规则 L4）。
4. **独立复审复跑测试并给出与 worker 一致的数字**，而不是单纯采信 worker 的"已测试"自述（对应现有规则 L34）。

以上均是本 PR 对现有硬规则的良好落实，证据充分，但未发现超出现有规则表述的新技巧，故未在经验文件中新增条目或扩写「这样做是对的」字段，以免与既有同类记录重复、增加文件体量。

## 待泛化的流程改进（供后续去项目化审查，非本次直接落地）
观察：本 PR 的设计复审在代码产出之前（即还没有任何实现成本投入时）发现并纠正了一个状态枚举不全的设计缺陷（原方案只判断"旧评论步骤是否成功"一种情形，漏判补发中/补发结果未知等情形），仅用 1 轮方案迭代即收口，随后代码一次性通过复审。这提示"先完整评审设计方案、再开始写代码"的两阶段流程，对于涉及多种状态组合的功能，可能比"直接写代码再在代码审查阶段发现状态遗漏"更低成本——因为状态枚举类问题在纯文字方案阶段修改的代价远低于已经写出代码和测试之后再返工。

这一观察目前只基于**单个 PR 的个案**，样本量不足以得出因果结论，也未与「跳过设计阶段直接写代码」的对照组比较过返工率，仅供后续独立、去项目化地评估是否有共性价值，不代表应将"两阶段流程"当作唯一正确做法——对于状态组合简单、风险低的小改动，省略独立设计评审轮次也可能是合理选择。
