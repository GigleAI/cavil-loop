## 经验教训
- 方案阶段（已确认）：新增对外写入的默认项不应包含「顺带扩大写入范围」，这类事应收窄或单独交人。
- 方案阶段（已确认）：新方案要先对照已有的人工选择（#270），再写显示规则。
- 实现阶段（已确认）：没有出现代码层面的返工，也没有复审指出的问题。
- 推断：方案阶段多花的几轮，可能减少了代码阶段的返工。耗时和用量数据只覆盖部分评论，不能量化主要耗时来源。

## 最佳实践（有适用条件）
1. **多个入口共享同一份规则时**：入口都走同一个计划生成函数，判定逻辑（如「当前迭代」）复用已有函数。
   - 验证：单元和界面测试各覆盖每个入口。本 PR 的做法是两个新建入口共用 `previewCreate`，判定复用 `isCurrentIteration`。
2. **自动补写字段的功能**：分别测「设了」「没设」「不该写」三类，且「不该写」旁配「该写的确实写了」的正向断言。本 PR 对没勾看板、无迭代组、重叠场景都这样做。
3. **PR 正文报测试数**：写明命令和口径，并说明默认跳过项不计入通过数。本 PR 的数字与复审复跑一致。
4. **同一处代码被另一个未合并 PR 修改时**：先登记等待，在合并后的主干上实现。
   - 适用边界：只适用于改动面确实重叠、且前置合并时间可预期的情况。
