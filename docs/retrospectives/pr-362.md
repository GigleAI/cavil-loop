## 经验教训
1. **人工在方案通过后推翻前提**：已通过复审的兼容方案被「旧名字不要了」取代。这是需求变更，不是实现错误。处理得当：方案修订版开头引用了人的原话，并在折叠块里写明与上一版的差异和被排除的方案。
2. **删除兼容的代价要提前披露**：修订版和 PR 正文用表格列出每种旧配置升级后的行为，并说明本仓库配置先追加新名，实现无空档过渡。这让维护者和复审都能按最新要求验收。
3. **前两轮方案复审只涉及版式**（命名理由、情形表折叠，版本说明移位），技术方向未变，不属于同根因技术返工。

## 最佳实践（有适用条件）
- 适用：配置项改名且人决定不保留旧名时。先列出「旧配置升级后的每种结果」，并安排仓库自身配置的过渡。验证方法：用真实派工和轮询入口断言旧名无效、提示内容正确，且有一个正向对照。本 PR 用此法，复审复跑一致。
- 命名问题要先区分「名字被读错」和「风格统一」，不把全库重命名扩进本次范围。本 PR 明确不改其他开关。
