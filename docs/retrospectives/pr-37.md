## 需求背景（已确认事实）

issue #34 记录的是一次真实生产事故：2026-09-18，一条 PR 的目标分支被手工建的 worktree 占用，daemon 在 2 小时 24 分内重复派工 270 次，直至 GitHub 封停 bot 账号才停止（证据：issue 正文列出的 `poll.log` 计数、journal `fatal: refusing to fetch` 报错、`git reflog` 记录）。根因被拆成两个独立缺陷：A）派工失败没有任何退避机制；B）新建 worktree 前不检查目标分支是否已被别处占用。

## 结果与证据

- PR 声明改动：`_lib.sh` 新增 3 个 helper（`dispatch_fail_bump/reset`、`run_git`、`branch_checked_out_elsewhere`）、`agent-poll.sh` 三个派工点接入计数与升级逻辑、`dispatch-pr-comment.sh` Case C 与 `create-worktree.sh` 加前置检查、新增 `DISPATCH_MAX_RETRIES` 配置及相关文档。
- 测试结果：PR 正文与两轮复审都称 `tests/dispatch-backoff.test.sh` 42 条断言全过、仓库全部 28 个测试套件全绿，并描述了三组负对照（退回旧实现／去掉前置检查／改用前缀匹配）分别导致失败数减少。**这些数字均来自 PR 作者与复审 agent 的自陈文本，本次证据包里没有独立的 CI 运行日志或 check-run 链接可交叉核实，只能作为「自陈+复审重跑」两层证据，不构成第三方独立验证。**
- 作者在 PR 正文第 4 节明确声明：**未在真实 daemon 上跑过生产派工**，本次验证限于沙盘端到端回归（真 `agent-poll.sh`/`_lib.sh`/`flock`/`jq`，假 `gh`/`tmux`/被派工脚本）。PR 合并（`merged_at`）本身不等于该修复已在生产 daemon 上真实跑过一轮 poll；截至本次证据采集，未见后续 poll.log 或生产回归证据。

## 有效做法（有证据支持）

1. **设计阶段先实测再定方案，推翻了两个"想当然"的假设**：
   - 假设 1（issue 原文认为）"dispatch 子进程 stderr 只进 journal、没进 poll.log" —— 方案评论实测证明是被 `_lib.sh` 顶部 `exec 2>/dev/null` **永久**重定向丢弃，此前能在 journal 看到报错纯属巧合（原代码写了 `2>&1`）。这推翻了"在 `agent-poll.sh` 里捕子进程 stderr"这条最初直觉路线，改为必须在 dispatch 脚本内部收集。
   - 假设 2（issue 未提及）"只要修好 fetch 失败就够了" —— 实测发现 `git worktree add --force` 在分支被占用时反而会**成功**，制造两个 worker 共用一个分支互相覆盖的新隐患。这把"分支占用前置检查"从"顺手加一下"提升为"必须做"。
   - 两条实测都作为证据出现在 [方案评论](https://github.com/GigleAI/cavil-loop/issues/34#issuecomment-5769590395) 第 1 节，且都各自钉了对应测试。
2. **端到端回归覆盖真实标签状态转移**：跑真实四轮 `agent-poll.sh`，验证「派工失败计数 1→2→3→达到上限翻 `pending/human`→第 4 轮不再派工」的完整链路，而不仅是单元级断言。
3. **负对照证明测试有效性**：分别退回旧实现、去掉前置检查、改用前缀匹配三种方式，验证测试套件确实能从全绿掉到有失败，避免"正确输入→正确输出"式的自证测试。
4. **失败计数命名空间隔离**：`dispatch-fail/<kind>-<num>` 与既有 `selfheal/<issue_n>` 分开存放，避免 issue 和 PR 共用编号导致两套计数互相清零。
5. **全等匹配防止子串误判**：`branch_checked_out_elsewhere` 用全等而非子串匹配分支名，明确对标此前 `tests/greedy-dispatch.test.sh` 里 `pending/human` vs `pending/humanoid` 的同类陷阱，并专门写了 `issue-3` vs `issue-34` 的负例测试。
6. **默认项+显式征询相结合**：Q1–Q3 给出明确默认答案并说明理由，人类只需一句"可以按默认方案实现"即可完成拍板，未产生额外来回。
7. **主动披露已知边界**：PR 正文第 4 节列出未做事项与残留风险（如 `--force` 造成双 worktree 的隐患只有单测覆盖、没有端到端覆盖；本项目技能目录软链指向 main、本 PR 自身被派工时跑的是旧版脚本），没有等被追问才承认。

## 流程中的观察点（非典型返工，但值得记录）

- **复审第 1 轮的判定标准与项目自身 review 模板存在冲突**：[review.template.md](https://github.com/GigleAI/cavil-loop) 明确规定"B 类（纯设计）此时没有代码是正常的，不得以'没有实现/没有测试/工作树与 origin/main 无差异'判不通过"。但复审第 1 轮的结论恰恰是"当前工作树没有任何交付改动……请先实现"（[评论](https://github.com/GigleAI/cavil-loop/issues/34#issuecomment-5769671286)），套用的是代码验收标准（2A），而当时 issue 上只有一份等待人工确认的设计方案、尚无 PR。PR 正文第 5 节也提到"issue 是从 `pending/human` 被直接翻到 `pending/review`、由复审 agent 打回 `pending/agent`"——**这句话本身是 PR 作者的自述，本次证据中没有独立的 label 变更历史 API 记录佐证，谁/为何做了这次标签跳转不明确，属推断**。可以确认的事实是：设计方案在获得人工文字确认之前，就已经进入了要求交付实现的复审循环，只是最终结果因为默认项恰好合理、且人类事后确认（"可以按默认方案实现"）而没有造成返工。这是一次流程执行偏差被结果掩盖的案例，不代表流程整体失效，但值得在项目内部核对复审触发逻辑是否会跳过设计确认关卡。
- 第二轮复审虽然技术验收通过，但仍要求人类对 Q1–Q3 给出**显式**文字确认才允许合并，理由是这些默认项涉及"改变对外可见的失败升级行为"（如立即转人工、不发 GitHub 评论）——这类改变对外行为边界的决策，仍应等到人类明确表态后才落地合并，这一点在本次执行中做到了，没有跳过。

## 失败教训 / 未验证事项

- **本次全部测试证据均为自陈**，缺少独立 CI 运行记录或第三方 check-run 链接；不应把"PR 描述称测试全绿"等同于"已被独立验证"。
- **未在真实 daemon 上跑过生产派工**，这是作者自己承认的边界，合并动作不代表该修复已在生产环境实际执行过一次 poll 循环；本次证据包里也没有合并后的 poll.log 或后续生产观察记录。
- **双 worktree 隐患（`git worktree add --force` 成功）只有单元测试覆盖**，没有端到端覆盖——作者解释是因为加了前置检查后 fetch 会先失败退出，`worktree add` 那行根本执行不到，因此这个隐患的"真实链路"验证依赖于对 git 行为的单点断言，一旦未来 git 版本改变该行为，此隐患可能重新出现且不会被现有端到端测试发现。
- **无法量化本次任务实际调用次数、token 用量或主要耗时来源**。评论中虽然嵌有部分自动化 footer（如 `agent-metrics` 标签内的 token/成本估算），但这些是该项目自身流水线针对具体 agent 任务的记录，不能用于推算本次复盘过程的资源消耗，也不构成对"本次 PR 从设计到合并总耗时/成本"的完整核算依据（仅覆盖了披露 footer 的那几条评论对应的单次 agent 运行）。

## 可复用的最佳实践（附适用条件）

1. **改动前先在沙盘里实测机制性假设，而非只读代码推理**——适用于：涉及 shell 重定向、进程间 IO、并发资源占用（如 git worktree）等"表面行为符合直觉但实际机制不透明"的场景。验证方法：构造最小可复现环境，逐条断言观察到的实际输出/退出码，而不是仅凭源码逻辑推断。
2. **修复某个失败点后，检查其"下一步操作"是否会在失败原因消除后暴露新的次生风险**——适用于：任何"failure A 掩盖了 operation B 的不安全行为"的场景（本例中 fetch 失败掩盖了 `worktree add --force` 的双写风险）。验证方法：即使当前测试因 A 未修而无法触达 B，也应针对 B 单独写一条直接断言其真实行为的测试。
3. **用负对照而非仅正向断言证明测试有效性**——适用于：任何声称"新增测试覆盖了某个 bug"的场景。验证方法：临时还原到旧实现或去掉修复的关键部分，确认测试套件确实从全绿转为有失败；只验证"正确输入→正确输出"不能算作已证明测试有效。
4. **计数器/状态类持久化数据要按资源类型分命名空间**——适用于：同一份状态目录可能被多个逻辑上独立的编号体系（如 issue 号与 PR 号共用同一数字空间）共同写入的场景。验证方法：构造 issue 和 PR 共用同一数字编号的用例，确认互不清零。
5. **人工拍板确认可以是勾选也可以是文字回复，但复盘/审计时都要落到具体评论 URL 和正文内容**——适用于：任何依赖"人是否已确认某默认方案"作为下一步执行依据的流程。验证方法：核对该评论的 `created_at`/`updated_at`（判断是否编辑过 checkbox）以及正文原文，而非仅凭"issue 已关闭"或"标签已翻转"推断已确认。

## 待泛化的流程改进

- **复审环节应能识别自己正在审查的是"设计阶段产物"还是"实现阶段产物"，并套用对应标准，而不是被表面的标签状态（如任务队列位置）误导去要求跨阶段的交付物。** 本项目在这次执行中出现过一次复审用代码验收标准去评判尚处于等待人工确认的设计方案的情况，最终因默认方案本身合理、人类事后补上确认而未造成实质返工，但这类"标准错位"若发生在默认方案不合理的场景，可能导致跳过必要的人工确认关卡就已产生代码改动。这类"生成式自动化流水线中，阶段判定应基于产物特征（是否已存在满足验收的代码/测试 diff），而非仅凭队列位置或标签状态"的原则，具备跨项目参考价值，但本次证据样本仅一例，且成因（谁/为何触发了标签跳转）未能独立核实，需要在更多案例中重复观察后再考虑固化为通用流程建议。
