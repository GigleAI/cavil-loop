## 经验教训
1. 本机全绿不等于 CI 全绿。首次 GitHub 运行暴露四类依赖开发机的问题：
   - 默认分支名（假仓库没写 `-b main`）。
   - 时区（夹具按北京时间写，生成新记账行时跟本机时区）。
   - 外层 CI 变量泄漏进被测运行。
   - 缺 git 全局身份。
   证据：PR 正文 https://github.com/GigleAI/cavil-loop/pull/121 。
2. 补跑「模拟 GitHub 机器」的命令（`TZ=UTC` 加最小 git 配置），确认同类问题一次收干净，而不是只修出错的那几处。这是确认的事实（PR 正文）。
3. 方案阶段的版式与交接口径问题，在 PR 阶段没有重现。方案复审的意见被完整吸收。

## 最佳实践（有适用条件）
- 引入 CI 总入口时，让本机、各分路、汇总共用同一入口脚本，并按「每个该跑的文件恰好通过一次」汇总。验证方法：用同一假目录对拍列表、分路、汇总三处，并分别做负对照。
- 「整个文件自行跳过」不等于通过：除非在排除清单里并写明原因，否则判红。适用于测试缺依赖时会静默以 0 退出的场景。
- 声称 CI 能拦截失败时，在真实 CI 上做「绿 → 故意改坏变红 → 撤销变绿」演示，并保留演示提交和运行链接。
- 发现与本 PR 无关的既有问题（6 项失效的负对照）时，如实披露、不顺手改、建议另开 issue，并预告手动入口目前会红。
- 单列「还没验证的」：手动运行、fork PR、系统镜像升级。
