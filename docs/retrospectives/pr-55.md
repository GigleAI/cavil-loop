## 3. 经验教训
1. **"有价"的判定在多个组件间不一致，是本 PR 的核心缺陷来源。** 真假判断吞掉 $0；抓价器按基名候选判断而消费者按完整名取价。两者都是"生产者与消费者各自实现同一判定"。
2. **状态/来源标注与数值需分开保留。** 冲突与"来自自动抓取"是两个独立维度，合并成一个桶会丢信息（新增 `disputed_fetched` 解决）。
3. **自己的测试只覆盖了非零价、先出现日期名的顺序**，独立复审通过构造边界 fixture（零价、缓存顺序、冲突+抓取）发现问题，测试全绿不能推出这些分支正确。
4. **方向被人推翻并非返工**：人要求"运行时抓价"，agent 重新出方案并明确列出对安全约束（AGENTS.md "运行时不联网"、worker 只访问 github.com）的修改，把联网限定在 daemon，这是有效做法。
5. **在文件末尾追加函数的改动与 main 反复冲突**（两次），且文本合并可能静默丢失共用的结尾行。

## 4. 最佳实践（含适用条件与验证方法）
- 当"某值是否可用/已有"被多个模块判断时，应抽成共享判定或对拍：适用于生产者-消费者共享缓存的场景。验证：对同一输入分别跑生产者与消费者，并覆盖零值、别名/后缀名、不同写入顺序。
- 对"缺失"使用显式空值判断而非真假判断：适用于合法值可能为 0 的字段。验证：加零值用例并对旧实现做负对照。
- 外部抓取的数据当不可信：多源一致、范围/结构校验、精确名匹配、失败冷却、不覆盖已有值。适用于自动写入影响金额等看似正常却可能错的输出；是否需要双源取决于出错代价，不是唯一架构。
- 来源与可信状态分开传递到最终展示：验证方式为每个组合各有端到端（驱动→周报）对拍用例。
- 合并 main 后：不仅看无冲突标记，还应检查两侧同时追加的函数结尾是否完整，并把新测试跑在最新 base 上（`bash -n` + 相关测试）。
- 在 PR 里分栏披露"实测过的 / 没跑过的"，并写明自指滞后，本 PR 做得较好。
