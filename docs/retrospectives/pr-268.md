## 经验教训
1. **重构或改动生产代码时，要同步负对照的替换原文（确认事实）。** 本 PR 改了 `engine.rs` 和 `api.rs` 的结构，两条旧负对照随之失效。默认 `npm test` 跳过负对照，这个错误只有靠静态 `--check` 才能发现，是复审 agent 实跑后查出的。worker 在自审表里宣称 L3 做到，但没有在交付前跑 `--check`。
2. **方案阶段把验证安排和项目约定对齐。** 方案里写了本地跑负对照，被复审打回。不过这只是方案文字，没有造成实际返工。

## 最佳实践
- 竞态修复：把写入落点移到持有「会话有效性」检查的同一临界区，而不是靠给队列加延迟或等待。适用于异步写入与会话变更并行的场景。验证方法：测试扣住旧写入，直到退出或新登录之后再放行，并断言「本轮确实发生过认定」以防空过。本 PR 用真实 Rust 子进程和 SQLite 文件做了这一点。
- 排除方案时写明理由，包括「只改测试时序会掩盖真 bug」。适用于测试偶发失败但不能确定是测试问题还是产品问题的场景。
- 禁止写入的键做成「窗口可读、不可写」的独立键表，而不是并入凭据键表，以免窗口启动时读不到。适用条件：该值既需要启动展示，又只能由后端写。
- 交付时单列「尚未执行」的验证项（负对照）。

## 流程改进
- 改动被负对照引用的源码时，交付前跑一次只读的 `node client/test/mutation/run.mjs --check`。它不执行负对照，与「本机不跑负对照」不冲突。这条已记入 lessons（L67 的第二次出现）。
- 方案阶段的验收标准先对照项目关于负对照运行时机的约定。该问题只出现一次，证据不足，不单独成规则。

## 适用边界
- 后端锁内写入适合「令牌或会话有效性由后端持锁判断」的架构，不是唯一方案。若会话归属能由命令携带，加会话号也可行，但本 PR 评估后认为对偏好设置代价更大。
- 启动时凭据被外部替换、账号未知的路径明确不在范围内，行为不变。
