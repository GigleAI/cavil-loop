## 3. 经验教训
1. **对「已完成」的记录必须以「所有写入被确认成功」为条件。**
   - 本 PR 的五个问题有一个共同根因：先把 PR 或任务标为已处理，再做可能失败的读写。
   - 一旦记录为已处理，失败就没有第二次机会。
2. **读失败不能映射成一个具体状态。**
   - `|| echo "OPEN"` 这类兜底会把「未知」变成「确定」，在本 PR 前就存在。
   - 拆 sub-issue 后，每个子项合并都会经过它，问题才被放大。
3. **逐点修补会多轮返工。**
   - 第一轮复审后，开发方在第 2 轮修复时把汇总里每个写步骤都列出并逐个测试，这一步有效。
   - 但合并收尾（入队、子项标签）仍被后续几轮复审发现，说明该次枚举没有覆盖上游的读取和入队环节。
   - 这是推断，证据是后续 review 找到的问题类别。
4. **三项核对和安全边界的设计在复审中没有被指出问题。**
   - 这些边界包括：父子关系核对、bot 创建、标记指向父 issue，以及 daemon 从不关闭父 issue。
   - 这是复审评论的自述，不是代码级证明。

## 4. 最佳实践（有适用条件）
- **适用条件**：有重试语义、状态存于本地文件、并依赖 GitHub API 读写的轮询程序。
  - 原则：先枚举处理流程中所有读和写，再逐个回答「失败后下一轮能否重试」。
  - 验证方法：给每个读写步骤配一个失败注入测试，覆盖「首轮失败、下轮恢复」的跨轮场景。
  - 用旧实现做负对照：旧代码应使新增测试变红。
- **适用条件**：做完成度聚合，比如判断所有子项是否关闭。
  - 原则：下「全部完成」的结论前，要确认列表完整。至少确认当前项在列表内、条数与来源总数一致。
  - 验证方法：覆盖空列表、缺当前项、缺其他项三种输入。
- **适用条件**：需要在合并后以自动化方式改变他人可见状态。
  - 原则：披露「未验证的写接口」，并在首次真实执行时安排人工核对。
  - 本 PR 已这样做，值得延续。
