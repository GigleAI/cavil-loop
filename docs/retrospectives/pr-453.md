## 经验教训
1. 设计阶段的「改前图」必须来自真实客户端，不能用重画原型（已确认，第 1 轮打回）。这是项目对方案复审的现有要求，本次是 worker 初版未做到，属于设计评论版式问题，未命中现有 L 规则，也仅此一次，故不新开条目（证据不足以判断是否反复出现）。
2. 方案评论里引用测试计数必须带命令、目录、通过/失败数（第 2 轮打回）。这与 L34 同类，但发生在 issue 方案评论而非 PR 正文；归属拿不准，本次不计次，仅在此记录（推断）。
3. 版本修改过程应放折叠区，不放可见开头（第 2 轮）。

## 最佳实践（有适用条件）
- 界面外观类改动：先截真实改前界面并标出修改处，再给候选；验证方法：复审可下载并目视核对。
- 动画类改动：断言「动画在跑」与「停止」成对出现，并读计算样式/实际偏移，不读源码文本；适用于有真实窗口测试的客户端。验证方法：把动画去掉后断言应变红（本 PR 未跑负对照，仅为建议）。
- 状态判断保持单点：issue 与 PR 共用同一图标分支，不新增第二套判断（对应 L3，本 PR 做对，复审确认）。
- PR 正文测试表写明命令、目录与浏览器引擎切换方式（`CAVIL_E2E_ENGINE=chromium`），独立复跑数字一致（对应 L34，做对）。
