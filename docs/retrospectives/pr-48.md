## 3. 经验教训
1. **并行重叠的工作没有被及时发现（事实）。** #47 合并后，#48 才被人发现重复。返工是整体重做并缩成补丁，而不是继续在旧提交上修。推断：开工前或开 PR 前对照 base 的最新合并 PR，可以更早发现。证据不足以说明谁先开始，#47 的 PR 时间线不在输入内。
2. **「测试里禁止 `def is_bot`」这类过死的结构性断言会误报。** 应断言行为或对象同一性，不要断言源码写法。
3. **端到端测试有多个计数位置时，只断言一处会留下盲区（事实）。** 复审靠独立负对照发现了这个缺口。「判定函数有单测」不等于「所有调用点都用了它」。
4. **「不放宽匹配」与「大小写不敏感」不冲突，但会改变行为。** 行为变化需要写进文档，并让人确认。本次靠 A/B/C 选择题完成确认，但勾选在第一版交付之后才出现。
5. **人用一句「解一下冲突」来推进时，真实问题是 PR 是否还有存在价值。** worker 用实测对照回答了这一点，值得保留。

## 4. 最佳实践（含适用条件与验证方法）
- 当 PR 与近期合并的 PR 同一区域时：先把新测试跑在最新 base 上，列出「已有 / 缺失」，再决定重做、缩小还是关闭。验证方法：对照表里每一行都标注实测结果。
- 当同一规则被多处调用（如汇总表与明细）时：对每个调用点分别做「仅此处退回旧实现」的负对照，并要求测试因此失败。验证方法：每个负对照都有对应失败用例的记录。
- 只改文档口径或测试的补丁：在 PR 正文中写明「不改的文件」和「没跑过的验证」，避免读者把测试通过理解为已在线上生效。

适用边界：以上是针对「小规则被多处引用」的脚本类改动的经验，不是说所有 PR 都必须逐点做负对照。
