# PR #440 复盘：经 GitHub 图片代理显示的图片不再误报「不在 GitHub 的地址上」

## 来源
- 需求 issue：https://github.com/GigleAI/cavil-loop/issues/439（客户端带图评论下总出现「有 1 张图片不在 GitHub 的地址上」，图片实际能显示）。
- PR：https://github.com/GigleAI/cavil-loop/pull/440（托管 autopilot，单提交，3 个文件，+49/-3）。

## 结果与证据
**已确认事实**
- 根因：计数用的一条规则在整段 HTML 上匹配 `<img … src="…">`。`src` 前只要求单词边界，`data-canonical-src` 也满足；中间又是贪婪匹配，于是取到的是外站原始地址而不是 camo 代理地址。依据：方案评论 https://github.com/GigleAI/cavil-loop/issues/439#issuecomment-6820506634；方案复审用真实夹具复现了旧规则取到外站地址（3 张图 3 通过 / 0 失败）：https://github.com/GigleAI/cavil-loop/issues/439#issuecomment-6820572339。
- 修复：先逐个取出图片标签，再只认标签内前面是空白的 `src=`，转义值还原后再比对；复用同文件里 `markReleaseImages` 已有的 `IMG_TAG` / `IMG_SRC` / `unescapeAttr`，没有放宽允许加载的图片来源。依据：PR 正文。
- 测试：PR 正文与复审复跑的口径一致，针对性测试 19 项、完整默认回归 1757 项通过，类型检查通过（命令与口径见 https://github.com/GigleAI/cavil-loop/pull/440#issuecomment-6820780282）。负对照、Playwright 界面测试、真实桌面目测均未跑，复审也明确写了这一点。
- 合并：daemon 自动 squash 合并（https://github.com/GigleAI/cavil-loop/issues/439#issuecomment-6820833501）。合并时 GitHub 客户端快速检查在复审评论里仍是「运行中」，合并评论称自动检查全部通过。

**返工**
- 方案阶段被打回 1 轮，原因是交付指引自相矛盾：开头写「直接执行」，结尾却要求维护者确认并重新打标签（https://github.com/GigleAI/cavil-loop/issues/439#issuecomment-6820433056）。修订版删掉了确认要求，第 2 轮通过。代码阶段首轮复审通过，没有行内评论或 review 提交。

**未验证 / 无法量化**

## 经验教训
1. 同一类判断（「图片加载地址」）出现在计数和附件改写两处时，旧计数规则与改写规则不一致，是这次误报的结构性原因（推断，依据是方案对根因的描述）。
2. 托管方案评论里「无需人动手」与「请确认并重新打标签」并存，会被独立复审打回；这是一次文字层面的返工。

## 最佳实践（有适用条件）
- 适用：从 GitHub 渲染 HTML 取属性值。做法：先切出标签，再按空白前置的属性名取值，不在整段 HTML 上用单词边界加贪婪匹配；验证方法：用录制的真实 GitHub 输出，同时断言「应不计」和「应计」的路径（本 PR 均做到）。
- 适用：同一规则有多个调用点。做法：复用已有规则和还原函数，并让每个调用点（正文、逐行评论）在测试里被覆盖。这是本次采用的一种做法，不是唯一架构。
- PR 正文写明测试命令与口径，并在正文列出未跑项，复审复跑数字一致。
- 托管方案评论写交付指引时，全文只给一种走向。
