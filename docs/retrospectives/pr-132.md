# PR #132 复盘:维护者在 PR 上打托管标签也算授权

## 1. 来源
- 需求:[issue #128](https://github.com/GigleAI/cavil-loop/issues/128)。已确认事实:要求维护者在 PR 上打 `autopilot` 也算授权,同时守住防 agent 自授权、两处标签合并判断、不减合并前检查。
- 方案:经 3 轮设计复审后通过([第 3 轮](https://github.com/GigleAI/cavil-loop/issues/128#issuecomment-6618610048))。`luosky` 只做了翻标签,没有书面确认,按默认 A 执行。issue 评论里两个 A 显示已勾,勾选人未验证。
- 实现:[PR #132](https://github.com/GigleAI/cavil-loop/pull/132),10 个提交,约 +1235/-85,2026-11-04 合并。

## 2. 结果与证据
- 已确认:PR 已合并。末轮复审([评论](https://github.com/GigleAI/cavil-loop/pull/132#issuecomment-6628757002))独立复跑了默认回归 412/0、2 份负对照和原始反例,CI 四个分片和汇总为 SUCCESS,与 `main` 无冲突。
- 未验证:真实 GitHub 上的接手/交人、双机竞态均未演练。合并不代表线上已执行,部署前线上仍是旧版。
- 全仓 `tests/run.sh --ci` 和 80 份负对照的全量结果是 worker 自报。复审只独立抽跑了其中几份,而且 80 份是在不同版本的测试上分批跑的。
- 耗时和成本:评论里有零散的单轮耗时和 token,但没有完整汇总,总耗时和主要耗时来源无法量化。不能从评论轮数推算。

## 3. 返工原因(事实)
返工几乎都集中在同一块:接手时"判不了"的异常处理,外加授权候选的选择。这里按复审轮次叙述。
1. 第 1 轮([评论](https://github.com/GigleAI/cavil-loop/pull/132#issuecomment-6619558657)):
   - 候选筛选要求"PR 自己挂着标签",所以只在 issue 上重新授权不会接手。
   - 接手阶段读不到信息时永远不交人。
   - 等人标签和复审标签共存时仍然接手。
   - 组合表里有一行预期被改成"PR 没标签就不接手",等于把错误行为写成了预期。
   - PR 正文写的负对照数量(58)与实际(55)不符。
2. 第 2 轮([评论](https://github.com/GigleAI/cavil-loop/pull/132#issuecomment-6621606711)):
   - 留言失败后接口同时恢复,交人说明永久漏发。
   - 写前第二次许可判不了时不计数。
   - 阈值交人前已读到 PR 关闭,仍然写入。
3. 第 3 轮([评论](https://github.com/GigleAI/cavil-loop/pull/132#issuecomment-6622602816)):
   - 旧交人待办压掉维护者的新授权。
   - 正文改绑到另一个 issue 后仍执行旧交人。
   - 此时已到轮次上限,交人选择。
4. 重置后的轮次:
   - 先后发现"只差说明"分支绕过身份和标签核对([评论](https://github.com/GigleAI/cavil-loop/pull/132#issuecomment-6625459668))。
   - 接着发现两处同秒授权时,PR 内明确在后的授权被 issue 那条遮住([评论](https://github.com/GigleAI/cavil-loop/pull/132#issuecomment-6626707181))。
5. 人工追问"为什么来回这么久"和"为什么要测 80 份":
   - worker 的回答是前期没有一次列全异常组合([评论](https://github.com/GigleAI/cavil-loop/pull/132#issuecomment-6628584220))。
   - 末轮复审改为只抽跑相关负对照([评论](https://github.com/GigleAI/cavil-loop/pull/132#issuecomment-6628757002))。

推断(未证实):前期若按第 4 轮才采用的"完整状态表加统一规则"一次盘点,可能少几轮。轮数不能换算成成本。

## 4. 有效做法
- 方案阶段把授权判据收成一条不变式,三个调用点共用一个函数,各调用点单独做负对照。
- 测试用真实轮询子进程加有状态假 GitHub,"零写入"断言配"确实读过"的到达性检查。
- 复审用独立故障注入脚本复现缺陷,没有信默认回归全绿。
- 第 4 轮把交人待办的失效规则统一为"动手前用同一个接手判断重判",之后只剩边角问题。
- 如实披露限制:未做真实 GitHub 演练、部署前线上仍是旧版、权限变化不刷新更新时间。
- 修测试隔离问题、报告"准备失败"的负对照并更新原文,没有跳过。

## 5. 经验教训
- 只在被点名的分支补丁,会让同源变体连续出现(命中 L1)。
- 持久化的"待办/决定"重试时,必须复用与正常路径同一套判断(命中 L3、L41)。
- 对拍表的预期值应由规则推出,不能照现行输出改写(新观察 L57)。
- 多个候选证据先压成一条再比较,会遮住明确有效的那一条(新观察 L56)。
- 正文里的测试数字要复核(命中 L34)。

## 6. 最佳实践(有适用条件)
- 适用:带"判不了 → 计数 → 交人 → 补发"的多轮自动化。做法是先列状态表(待办是否已写标签、说明是否已发、当前标签与操作者、读取成功或失败、绑定是否变化、是否有新授权),为每格定义继续、作废或保留。验证:跨轮故障注入,加旧版本整份回退的负对照。
- 适用:负对照很多、单轮耗时长时。日常改动抽跑相关负对照,广泛共享逻辑改动或阶段收口时再全跑。这是末轮复审的实际做法,不是唯一正确的架构。

## 7. 流程改进
- 复审第 1 轮就应要求一次性提交"状态表加输入组合表",再进入代码返工。这是建议,尚未落地。
- PR 正文的测试计数要在提交前用当前提交复跑。
- 适用边界:只对状态机较复杂的异常处理有意义,小改动不必。

### 待泛化的流程改进
- 候选:"持久化的待办在执行前必须用与正常路径相同的判断函数重判"。需经去项目化审查后才可用于通用模板,本报告不发布到公开仓库。
