### 已确认的事实

- **问题**：本该在北京时间 11-23 出的每周正式版（后台工具和客户端）都没出。PR 正文和 worker 评论写明，11-21、11-22 两次定时 Release 运行都是启动失败、零任务，所以也没有自动开出发版失败的 issue（https://github.com/GigleAI/cavil-loop/pull/686 ，https://github.com/GigleAI/cavil-loop/issues/578#issuecomment-7102319117）。复审独立实查了其中 11-22 那次运行（https://github.com/GigleAI/cavil-loop/pull/686#issuecomment-7102410884）。
- **根因（worker 判断，复审对照 GitHub 官方说明认可）**：客户端流程新增的「每晚失败自动开 issue」任务要写 issue、读运行记录的权限。发版流程调用客户端流程时只给了写代码库内容的权限。被调流程要的权限超过调用方给的，GitHub 就整个拒绝启动。
- **修复**：发版流程的调用任务补上两项权限；新增一个文本守卫，扫全部流程文件里的本仓库流程调用，核对调用方权限盖住被调流程每个任务的权限；改了一条既有断言；在 `AGENTS.md` 登记新测试（https://github.com/GigleAI/cavil-loop/pull/686）。
- **发现途径**：维护者在 11-23 留言「看下有没有」（https://github.com/GigleAI/cavil-loop/issues/578#issuecomment-7099040124），worker 才查出发版流程没启动。此前 agent 已写明 daemon 不能按日期叫醒，要人来点（https://github.com/GigleAI/cavil-loop/issues/578#issuecomment-6961975008）。
- **流程**：复审第 1 轮通过，没有返工。改动碰了 `.github/`，托管不自动合并（https://github.com/GigleAI/cavil-loop/pull/686#issuecomment-7102431075）。维护者于 2026-11-25T01:32:35Z 手动合并。

## 经验教训

1. **被调流程多要一项权限，调用方没跟上，整个调用方流程就起不来。** 失败发生在任何任务运行之前，原有的「失败自动开 issue」机制也不会触发。被调任务在这次调用下会被跳过也一样（https://github.com/GigleAI/cavil-loop/issues/578#issuecomment-7102319117）。已记为目录经验 L78。
2. **「零任务的启动失败」没有告警。** 这次靠维护者追问才发现。现有流程没有覆盖「定时流程根本没启动」这种情况（https://github.com/GigleAI/cavil-loop/issues/578#issuecomment-7099040124）。
3. **按日期等待的收尾项靠人记得来点。** agent 提前写明了这个限制和预期日期，维护者当天就追问了，所以没有漏掉。
4. **做对的地方**：
   - 修一处的同时加了扫全部调用点的守卫，守卫读真实流程文件。
   - 正文每个数字都写了命令和提交，复审复跑一致。
   - worker 和复审都把「未验证」单列，没有把复审通过或合并说成已发版。
   - 排除方案（拆流程、只手动重跑）写了理由。

## 最佳实践

- **改可复用流程的权限时，把全部调用方当作同一次改动的一部分。**
  - 适用条件：流程之间存在调用关系。
  - 验证方法：跑权限覆盖守卫，并在修改前的版本上确认它会变红。真实启动行为只能在合并后的首次运行确认，交付里要写明这一点。
  - 文本守卫只是本次采用的一种手段，不是唯一做法。
- **本地无法验证的平台行为，登记成合并后待办。**
  - 写全谁做、做什么、怎么触发。
  - 对外不说「已恢复」，等真实运行结果。
- **依赖定时触发的验收，交付时写明最早可验收的日期和推算依据。**
  - 例子见 https://github.com/GigleAI/cavil-loop/issues/578#issuecomment-6961975008 。
  - 到期后先确认流程是否启动，再看产物。

## 流程改进

以下都是建议，尚未实施。

- 给定时流程加「没启动 / 零任务」的监测或提醒，比如由另一个独立流程检查最近一次 Release 运行的结论。
- 收尾核对类 issue 用修复 PR 关闭时，考虑让修复 PR 不直接关闭核对项，或由 daemon 在待办完成前保持打开。现状是关闭后挂 `pending/human` 提醒，要人重开。是否调整由维护者决定。
- 碰 `.github/` 的修复 PR 要人工合并。当修复对象正是每天定时失败的流程时，可在交人评论里更醒目地标出「每晚一天就多失败一次」。这一条基于上面的推断，未证实。

## 待泛化的流程改进

以下是候选，需要另行做去项目化审查后才能进通用模板。

- 调用方授予、被调方声明的权限或能力，如果不一致会导致「整体不启动且无告警」，就应当有覆盖全部调用点的静态一致性检查。
- 依赖定时触发的自动化，要单独监测「未启动」，不能只监测「运行失败」。
- 修复类 PR 关闭验收类条目时，验收未完成的部分要有不依赖人记忆的续接机制。
