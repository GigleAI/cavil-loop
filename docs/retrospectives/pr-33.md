## 4. 经验教训（推断部分已标明）
1. **归属要靠正向证据。**“没登记给别人”和“启动后才出现”都不能证明“这条是我的”。
   - 凡是向注册表写入、认领或收养资源的入口，都应逐个列出，并写清各自的证据。
   - 本次三个写入口依次出问题，证据表最终放进了 AGENTS.md。
2. **测试夹具必须取自真实形状。** 短单行 prompt、把任务放在第一条 user 消息，都绕过了缺陷。
   - 夹具应使用仓库自带的多行模板和真实日志结构，包括前置上下文消息。
   - 推断：先读一份真实产物，可能在更早的轮次就暴露第一条 user 消息不是派工 prompt 这个问题。
3. **跨边界要测真实调用形状。** `$( )` 吞变量就是这一类问题。
4. **负对照必须确认红的原因是语义退回，而不是语法错误。**
5. **近似比较会同时造成两种错误。** 前缀和首行比较既漏判（认错别人的会话），也误拒（拒绝自己的会话）。
   - 误拒不报错，只让功能静默失效。
6. **同一根因被连续发现多次后，应重新评估设计。** 本次作者提出了“不复用”的替代方案，但没有得到决策，所以每轮仍在边界上继续打补丁。
7. **合并 main 后要检查新增的横切参数是否落到新代码路径上。** git 自动合并不会提示这类遗漏。

## 5. 最佳实践（附适用条件和验证方法）
- **条件**：多角色共享同一个工作目录或历史库，并且要复用、续接或收养某个会话。
  - **做法**：把“被认领”定义为可举证的事实，例如自己发放的 id、接管前的快照，或与本次启动绑定的唯一标记。无法举证就拒绝认领并留诊断。
  - **验证**：对每个写入口各做一次“只退回这一处”的负对照；再用真实结构、多行、带前置消息的夹具，覆盖两个角色方向。
- **条件**：外部 CLI 的落盘格式不受自己控制。
  - **做法**：先读一份真实产物，再写解析。
  - **验证**：夹具与真实事件顺序一致。
- 取舍：宁可丢上下文，也不串角色。但这要明示，并且保证跨轮复用仍能工作。
  - 这不是唯一架构。“每次新开”的方案更简单，代价是上下文和缓存。
