## 经验教训
1. **多入口同一规则，要查完整链路。**
   - 事实：方案首版只改了判断函数，但讨论区转发在判断之前就丢了修饰键信息。
   - 推断：只盯「判断规则在哪」，容易漏掉判断之前的输入采集与转发环节。
   - 这与已有规则 L3（多入口共用同一实现、同输入对拍）同类。问题在方案阶段被复审拦下，交付前已改掉，所以不计次。
2. **偶发失败如实披露。** worker 明确写出「与本改动看起来无关、但没能确认」的偶发失败和本机负载条件，并说「以 PR 的 CI 为准」。复审也没有把偶发问题改称已修复。这是 L11、L34 提倡的做法。
3. **测试计数写明命令与口径。** 正文每个数字都附命令，复审复跑与正文一致（59 与 16）。同一命令两次结果不同（28/1 与 29/0），两边都明写了。
4. **用量无法量化。** 输入里 worker 的方案轮、实现轮缺少 token 和耗时数据，不能判断返工对总耗时的影响。

## 最佳实践（有适用条件）
- 适用：Mac 与其他平台的快捷键分组、同一动作有多个触发键。
  - 做法：旧键保留生效、只改提示和显示，降低用户迁移成本，并在方案里说明取舍理由。
  - 验证：单元测试覆盖新旧键、平台、输入框与设置页等上下文。
- 适用：带隔离 iframe 的界面。
  - 做法：隔离框把修饰键分别传出，主窗口还原后交给同一判断函数；旧格式消息仍按原方式处理。
  - 验证：e2e 经真实讨论区脚本和窗口消息链路，并配「普通 ⌘ 数字确实切换、⌘R 确实重读」的正向对照，防止「不切换」类断言空转。
- 脚本指纹变化时，同步更新两处登记，并用现有一致性测试核对。
- 这些做法依赖本项目的快捷键表与隔离讨论区结构，不是唯一正确架构。
