## 3. 经验教训
- 事实：第 2 轮暴露出，程序测试只能验证“Seen 的 PR 号和链接出现在迁移表里、且该 PR 有报告”，判断不了引用内容是失败证据还是正面案例。这个缺口靠人工阅读才发现（第2轮评论明确这么说）。
- 事实：作者在第 1 轮修复里已经口头定了“被引用、做对都不计”的口径，仍在第 2 轮被指出误计。第 2 轮复审提醒其他迁移项也按此核对后，作者一次扫出 6 处同类问题。
- 推断：口径写出后，缺少一次“对全部计数项用同一判据重扫”的步骤，是同类误计反复出现的可能原因。
- 事实：自审表第一次只接到返工入口。这是 L3 同类问题：同一要求有多个代码交付入口。
- 事实：复审第3轮通过后，L2、L5 降为观察中，这是计次口径修正的直接结果。

## 4. 最佳实践（有适用条件）
- 适用条件：把历史引用迁移成计数，且计数会触发自动升级或打回时。做法：先定“什么算一次发生”的判据，包括做对、只被提及、同一原文重复计入是否算；再用同一判据对每一项重扫。验证：迁移表逐行列出报告行号、原文摘句，抽样回读原文，并列出没计入的引用及原因。
- 适用条件：要求写入多个相似入口（首次交付、返工、子 issue、review）时。做法：找出全部相关入口，用同一段文字，并用测试枚举所有含 `git push` / `gh pr create` 的模板，而不是只检查被改的那份。这只是本次采用的一种验证方式，也可以用别的方式枚举入口。
- 适用条件：程序校验有“只能判断形式”的边界时。做法：在 PR body 里写明留给人工 review 的部分（本例是同义改写的重复规则、证据归类），不要宣称程序已证明语义。
- 适用条件：修改 review 或派工自己所用的模板时。做法：声明合并部署前的验证滞后，并规划合并后的真实运行验证。

## 5. 流程改进
- 已落地：lessons 新格式、校验、硬规则核对表（均已随 PR 合并）。
- 待办（未实施，不得声称已落地）：合并部署后，挑一个已合并 PR 实际跑一次复盘；观察硬规则核对表是否真的拦住重复错误，两者目前都无证据。
- 共享经验调整：本次 lessons 按复盘任务限制压缩到 ≤8 条。去重合并后只保留 3 条硬规则 L1/L3/L4、有价值的观察项 L2/L5/L9/L11，以及新增的 L29（迁移计次口径）。其余观察项（L6–L8、L10、L12–L28）为 Seen 0–2 次的低频项，已从共享文件移除。它们仍保留在 PR 合并后的 `docs/retrospectives/lessons-migration.md` 等历史记录里（本复盘未核对该文件）。
- 已知冲突：PR #62 自身的格式要求编号永久不变、不得消失，而本任务限制为最多 8 条。压缩会让下一次按 PR #62 校验的复盘因编号消失而被拒；需要维护者决定是放宽上限，还是接受人工改写作为新基线（PR 说明人手改文件不受限制）。本复盘无法替他决定，按任务约束执行。
