## 最佳实践与适用边界

从 PR 正文可以提炼出一条有参考价值、但**不应被当成唯一正确架构**的做法：

- **草稿发布 + 人工/本机签名的交接模式**：当签名凭据必须留在特定机器的钥匙串、且不愿意把证书放进 CI secret 时，可以采用"CI 只产出未签名的草稿 Release，由专属机器定时轮询草稿并补齐签名、公证、发布"的模式。适用条件：① 确有"凭据不能离开某台机器"的强约束；② 该机器能稳定可用（launchd/cron 等）且有人负责监控（本 PR 用"草稿超过 12 小时未发布就报警"兜底）；③ 发布产物的文件名、清单格式与原有约定保持不变，避免下游（如自动更新检查）产生歧义。不适用于：凭据可以安全放入 CI secret、或没有专属常驻机器可用的团队。
- 这一做法本身**未经独立复审确认**，其有效性目前只有作者自述的"跑了一轮未发布的草稿构建"作为证据，建议后续如有同类 PR 再出现，应在复审或后续 PR 中补充"合并后首次真实生产发布是否成功"的证据。
