## 经验教训
1. 「提前检查」口径必须和夜间检查一致：首版方案读源码文字，与夜间按真实登记名匹配不同，会放过已删除测试（复审第 1 轮，事实）。
2. 一个修复易牵出同类隐藏故障：原文核对此前没有任何地方运行，一跑就发现 8 项同类失效（事实）。
3. 闭环时机要在方案里自洽（合并即关，失败由工作流新开 issue）。
4. 评论版式：修订过程要放折叠区。

## 最佳实践（有适用条件）
- 当同一条规则在 PR 阶段和夜间各有调用点时，复用同一判定函数，并用同一夹具及全量数据对拍两边的输入；验证方法：对拍相等 + 套到旧做法上变红（PR 正文自述手动验证过一次，非登记负对照）。
- 对「名字匹配」类检查，用测试框架真实登记的名字而非源码文本；测试覆盖改名、删除、注释残留、加载失败。
- 引用数字写明命令，复审复跑一致（对应已有 L34 的做法）。
