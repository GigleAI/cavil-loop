## 经验教训
- 同一「PR 关联哪个需求」逻辑连续被指出多个变体（复制、跨行、关闭兼容），逐点补丁导致多轮；最后靠改设计（不改旧代码、只消费其一致结论）收口。（推断：若首次来源核验时就枚举配置状态 × 输入 × 消费者，可少几轮；证据为复审第 2 节的维度清单。）
- 复用为别的用途设计的函数时，兜底行为可能与新用途相反。
- 对「默认关闭」功能，新增对拍只在开启模式跑，测不出关闭兼容性；关闭模式需与固定基准对拍。
- 「写后读回」要覆盖中间状态，不只调用顺序。
- 为让测试通过而缩小原需求范围，须交人确认，且题目要用使用场景表达。

## 最佳实践（有适用条件）
- 适用：重构被多个入口共用的解析规则时。行为：先列配置状态、输入边界、全部消费者，再对固定旧基准对拍；验证：关闭模式与旧版逐条一致，每个调用点有负对照。
- 适用：存在「默认不通知 / 条件才生效」的写操作序列。行为：每步写后读回并断言中间状态；验证：注入「返回成功但不生效」。
- 做对的：方案阶段把与 issue 正文不一致的人工决定写成表（PR 正文）；PR 单列「还没验证的」；每轮自带硬规则核对表。
