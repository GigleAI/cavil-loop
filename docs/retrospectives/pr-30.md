## 返工原因（已确认事实）

根因是环境变量命名冲突：单次派工（review）的模型覆盖被直接放进持久配置同名的 `WORKER_MODEL` 环境变量传给 dispatch 子进程；子进程启动后会重新 `source` 配置文件，配置中的同名赋值（包括新示例中的空字符串）会覆盖掉传入的环境变量值，导致：
- 普通任务配置了模型时，会串到 review 的 Codex 调用上；
- review 显式指定了模型、但普通模型配置为空时，review 的显式覆盖被清空。

同批新增的回归测试（`tests/worker-selection.test.sh:55-71`）只在**当前 shell** 内读变量、匹配源码字符串，没有真正跨越 dispatch 会重新 source 配置的子进程边界，因此该测试在 bug 存在的情况下依然报告 11/11 全部通过——这是一次「测试通过但功能有真实缺陷」的典型案例，缺陷是被独立复审用手工构造真实子进程调用命令发现的，而不是被测试发现的。

## 最佳实践（本次验证有效，非唯一架构）

1. **单次覆盖参数与持久配置分用不同变量名，并在配置加载之后显式应用覆盖。** 适用条件：当接收方是会自行重新读取同一份配置文件的子进程时（本项目 dispatch 脚本即如此）。此为本次采用的一种解法，不代表所有环境变量传参场景都必须如此设计。
2. **回归测试要跨越 bug 实际发生的执行边界（如子进程重新加载配置），而不是只在测试进程内做字符串匹配。** 判断标准：测试是否调用了与生产路径一致的真实命令/函数，而非仅断言源码文本包含某片段。
3. **用负对照验证新增测试的有效性**：临时回退到修复前的实现重跑测试，确认测试确实会失败（本次为 14/14 → 12/14），才能证明新测试真的在防止该 bug 回归，而不是碰巧同样通过。
4. **独立交叉复审（review 使用不同 agent/session）在本次拦住了实现方自己测试未覆盖的真实 bug**，验证了 issue #28 所设计的「普通 Claude / review Codex」分离机制本身的价值；但复审会话的 token/成本目前没有独立可核算的用量记录，无法量化本次复审的实际开销。

## 适用边界

- 上述关于环境变量覆盖与测试边界的教训，仅适用于「子进程会重新加载同名配置」这一类场景；对于参数直接以函数入参传递、不存在重新 source 配置行为的代码路径，不构成同样的风险。

## 待泛化的流程改进

以下发现具有跨项目参考价值，需经独立去项目化审查后才可能纳入公开的 cavil 通用模板，本报告仅记录候选内容：
