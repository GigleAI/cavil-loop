## 经验教训

1. **自动复审的"通过"结论可能建立在尚未合并代码的旧版基础设施之上，而不是本 PR 的实际改动。** 本次复审用的是主分支已部署的旧 `codex.sh`，导致复审 footer 无法展示 PR 新增字段，容易被误读为功能未生效或 footer 被关闭。复审虽然在文字中提到了这一限制，但没有在结论首行/摘要处显著提示，最终靠人工主动追问才澄清。（证据：上述三条评论）

2. **人工是发现该盲区的直接来源，而非自动化流程主动上报。** 这说明当前的复审 checklist 没有把"改动的脚本/模板是否恰好也是复审工具自身依赖的路径"作为显式自检项。

3. **设计方案中"缺证据就显示未知，不编造模型名"的兜底规则本身工作正常**——复审 footer 显示"模型未知"是该规则按设计生效的表现，不是 bug，这一点被正确诊断。

## 最佳实践（有适用条件）

- **修改会被复审/CI 工具自身依赖的基础设施（如 token-usage driver、通用 prompt 脚本）时，应在 PR 描述或复审结论中主动声明"本次复审/验证使用的是已部署旧版工具，新字段效果需在合并部署后的下一次真实调用中端到端验证"**，而不是等待人工发现异常再解释。适用边界：仅当改动对象恰好是复审流程本身要读取执行的脚本/模板时才需要此提示；对不涉及复审工具链的普通业务代码改动不适用。
- **验证声明应区分"本地/测试环境跑通"与"生产真实调用链路验证"两个层级**，尤其是涉及"合并后才能生效"的软链接/部署依赖场景，避免用测试通过掩盖生产效果未知的事实。
- **人工在合并前对可疑现象（如 footer 缺字段）主动提问，是有效的最后一道核查手段**，即便自动复审已给出"通过"结论，也不应替代人工对实际输出的直接观察。

## 流程改进建议（项目内）
- 复审 prompt/流程可以增加一步自检：识别本次改动的文件路径是否与复审工具自身运行时依赖的脚本路径重叠；若重叠，在复审结论的显著位置（而非仅正文细节）注明"新增能力需在部署后的下一次真实派工验证"。**此为本次未落地的改进建议，尚未在任何 prompt 中实施，不可视为已生效流程。**

## 待泛化的流程改进（供后续去项目化审查）
- **"修改工具链自身"场景下的自证悖论**：当一个变更的验证方式恰好依赖被修改对象的旧版本运行时，自动化验证结论容易产生误导性的"通过"外观，而看不出新功能是否真正生效。这类自举/自我验证盲区具有跨项目通用性（例如修改代码检查工具本身、修改日志采集脚本本身等场景），值得抽象为一条不依赖本项目术语的通用原则：**验证工具变更时，若验证过程复用了被改动对象的运行时环境，需显式识别并声明这一情形，不能把"验证流程跑通"等同于"改动本身已被验证"。** 该候选内容需在后续独立的去项目化审查中确认后才可考虑纳入公开模板，本次不直接发布。
