## 经验教训
1. **快捷键测试漏了焦点位置的组合。** 新测试在拖宽后按 Esc，焦点仍在外层页面，没有覆盖"先点隔离框内容再按键"的路径，复审才发现。浏览器里 iframe 一旦拿到焦点，键盘事件不会冒泡到外层。全局快捷键的测试要把焦点所在位置作为变量。这是 `client/src/renderer/` 的目录经验，已记为新条目 L64。
2. **浮动层会遮挡其下的交互元素。** 首轮 CI 抓到面板盖住卡片，后加"卡片点得到"一步断言。这是已确认的一次返工；只有 PR 自述的修复，没有单独证据链接，所以不单独计次。
3. **安全隔离和便利功能冲突时，把代价摆给人选。** worker 没有自作主张削弱同源隔离，而是列出 A/B/C 三种取舍，并用 Chromium 原型实测 A 和 B 的行为。B 的复制失效只是按浏览器行为推断，评论里明确标了未实测。

## 最佳实践（有适用条件）
- 适用条件：同一规则有多个调用点。做法：抽成一个函数，用同一输入对拍各调用点，并分别做负对照。本 PR 的 PR 归组由 `prNest.ts` 供看板和表格共用，头像地址只由 `avatar.ts` 生成。验证方法：`prNest.test.ts` 对拍，以及各调用点的负对照（复审独立复跑 20 项变红）。
- 适用条件：客户端有"只和指定域名通信"的约定。做法：在真实窗口记录实际网络请求，断言允许域名有请求、禁止域名零请求。验证方法：界面测试请求记录，加把策略改回通配的负对照。
- 适用条件：返工后正文引用测试数字。做法：写明口径。本 PR 正文的 189 是不依赖后台的子集，复审全量复跑为 351，口径分开写没有冲突。
- 适用边界：这些做法不是唯一正确架构，只适用于上述条件。
