## 返工原因（均来自复审评论）
第 1 轮（https://github.com/GigleAI/cavil-loop/pull/98#issuecomment-6540708334）：
1. 关闭通知只在入队时检查「是否还有别的 PR 开着」。重试时没有重查，所以新 PR 已开仍会误报「没有落地」。
2. 打开 PR 列表读取失败被当成「没有 PR」，照样发通知。
3. daemon 通知只检查写身份非空，没核对允许名单，名单外账号能评论并指派机器人。
4. 安装入口的新旧配置兼容测试用 awk 抽三行再 eval，没有跑真实入口，也没有独立负对照。
5. PR 正文写 770/0，复审实跑为 771/0。

第 2 轮（https://github.com/GigleAI/cavil-loop/pull/98#issuecomment-6541045282）：
1. 一项负对照因目标原文已变而没准备成功，失败计数在子 shell 里丢失，整套仍报绿。
2. PR 正文的 834/0 与复审实跑的 833/0 对不上，且三项负对照的失败条数也与记录不符。

## 有效做法
- 把「是否机器人需求」「重新指派」「账号资格」「新旧名选择」各收成一份共用实现，两个调用点各配负对照。
- 重试前每次现读完整的发送资格，而不是只在入队时判断（事实：第 2 轮复审复核，原场景重跑后不再发送，https://github.com/GigleAI/cavil-loop/pull/98#issuecomment-6541045282）。
- 安装入口改为在隔离目录里真跑 `setup.sh`，断言实际建标签的请求，并与公共库对拍。
- 负对照准备失败写进父进程可读的记录，并增加自检开关证明整套会变红。
- 交人时单列未验证项，并给出分步的部署后验收步骤。

## 经验教训
- 新增对外写入路径时，要把「谁能写、该不该写、状态读不到怎么办」一次性列全，每个入口都要核对。本 PR 的第 1 轮打回都属于这类。
- 负对照的准备步骤本身也要有失败传播和自检。
- PR 正文里的数字要在最终提交上复跑后再写。本 PR 两轮都在这点上对不上；复审同时指出的差异原因（如 7 对 8）未查明，不能推断为生产缺陷。
- 用量、耗时：评论里虽有 footer，但不能据评论轮数推算调用次数或耗时来源，无法量化各返工环节的成本。

## 最佳实践（含适用条件）
- 条件：同一规则在多个入口生效。做法：抽成一份实现，再用同一批输入对拍各入口。验证：每个调用点单独改坏后测试应变红。
- 条件：先判定、后写外部系统，且中间有重试或延迟。做法：写前重读并重判全部条件，读失败视为未知而留队。验证：注入读失败和中间状态变化。
- 条件：测试含变异或负对照。做法：准备失败要传到退出码。验证：故意给一个找不到的原文，整套应非零退出。
- 以上是本 PR 采用的做法，不是唯一正确架构。
