## 返工原因（事实）
1. 方案阶段：原子替换被当成并发保护，会让两个项目互相抹掉记录。复审用真实写入函数受控交错复现，修订方案加了按真实文件划分的共享锁。
2. 识别信任框时只匹配短语，正常对话里出现同样文字就会杀会话并转人工。后改为标题、整行信任选项和末行底栏三者同时满足，并用真机截屏作夹具。
3. 配置软链接解析连续出了 5 个变体：
   - 缺 Python 时静默回退到原路径，拆掉软链接；
   - 先消 `..` 再跟链接，写错文件；
   - 不检查中间分量是否为目录，普通文件后接 `/..` 仍写入旁边的文件；
   - 目标不存在时丢掉末尾 `/`、`/.` 的目录要求；
   - 每次都是补一个样例，直到改成以内核真实打开结果为标准答案、按组合整体对拍。
4. 测试基础设施：一个负对照的准备步骤在子 shell 里失败，失败计数传不回父进程，整套仍报全绿，「18 项」只是 gate 计数。后改为失败写文件、父进程统一计红，并加故意失败的自检。

## 经验教训
- 有破坏性后果的状态识别，不能靠单个短语。
- 「模仿内核/系统规则」的实现，加上用另一个模仿实现当测试答案，会让漏洞两边一起漏。
- 解析失败后回退到未解析的输入继续做破坏性写入，等于把失败伪装成成功。
- 测试自身的失败路径要能传到退出码，否则「全绿」不可信。
- 复审最后一轮的评语已明确写出「路径安全三轮出现相关变体，必须按 L1 集中核对」。worker 此后才一次性列全规则，并改用真实系统结果对拍。

## 最佳实践（有适用条件）
- 适用：对外部 CLI 或内核行为做等价判断（路径解析、屏幕状态识别）。
  做法：用真机截屏或内核真实打开结果作标准答案，并配「相同文案但不是真弹框」的放行用例。
  验证：把错误的宽松实现作为负对照，断言必须变红。
- 适用：多个进程共写同一用户配置文件。
  做法：锁按文件真实路径划分，持锁后才读、判断、写，并在替换前比对内容。
  验证：受控交错测试，且对去锁的实现做负对照。
  边界：不认锁的外部进程仍有竞态，需如实披露。这不等于唯一正确架构。
- 适用：任何负对照或夹具准备步骤。
  做法：准备失败必须计为失败，并有故意失败的自检。
- 本 PR 的做法：同一判定函数服务四个入口，并对每个入口单独做负对照；PR 正文分栏披露「还没验证的」；不拿 relabel 当书面确认。

## 流程改进
- 复审对同一根因（路径解析）连续出现变体时，复审评论明确引用 L1，并列出输入、读、写、消费者、重跑的核对矩阵。这条流程有效，但矩阵到第 5 个变体才补全「目标不存在 × 后缀」这一格，说明矩阵应在第 3 轮就做完整。
- 人工重新送审时，复审把轮次重置为第 1 轮，同时在评语中保留历史返工说明。该做法合理。
- 以上均为建议，未声称已落地。

## 待泛化的流程改进（候选，需另行去项目化审查，不自动发布到 cavil）

- 测试基础设施自身的失败要能让整套测试变红，并附故意失败的自检。
