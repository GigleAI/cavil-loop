## 2. 结果与证据
**已确认事实**
- Issue #56 的根因：`claude --continue` 不带 `--model` 会沿用会话当初的模型；`FABLE_MODEL` 默认值被钉在旧版本号（issue 方案评论，含实测对照表）。
- 最终实现：
  - 续接前在 worktree 里起一次不保存会话的 `claude -p` 探测，读 `system/init` 里的模型。探测成功就追加 `--model`。
  - extra flags 已有 `--model`、含不可确定拆词的写法，或探测失败时，都不追加，维持老行为。
  - `FABLE_MODEL` 默认改为 `fable`。
  - 老的 `claude-fable-*` state 记录仍归入 fable 队列。
- 最终复审通过：https://github.com/GigleAI/cavil-loop/pull/57#issuecomment-6052507710。该评论报告 365 项断言通过，并说明新测试对上一版有负对照。
- Q1（老会话是否切到新模型）：人只翻了 label，没有文字答复，也没有改勾选，按默认 A 执行。这是推断，不是书面确认（PR body「拍板情况」）。

**未验证**
- 生产 daemon 上的真实续接派工、部署后的模型切换、macOS 真机，都没有证据（PR body 和多轮评论自述）。
- 合并不代表这些已验证。三个项目本地的 `FABLE_MODEL="claude-fable-5"` 是否已清理，没有证据。
- 本 PR 的派工和复审用的是部署中的旧 driver。
- 调用次数、token 和耗时占比无法量化。评论里有单轮 footer，但没有按来源汇总的数据，不能由此推断返工的主要耗时来源。

## 4. 经验教训
1. 复刻外部工具的优先级或解析规则，会被逐点发现遗漏。复审连续 3 轮发现同类变体后，才从「补规则」改成「问权威方」。早点枚举全部来源，或直接委托给工具自己解析，可以减少返工。
2. 把参数从一个上下文搬到另一个上下文（daemon 拼命令，worker 在 tmux 的 bash 里执行）时，目录、`~` 展开和转义语义都可能不同。测试只用普通临时目录和绝对路径，抓不到这些差异。
3. 新增运行时依赖（如 `timeout`）要与安装检查一致，否则会静默失效。

## 5. 最佳实践（附适用条件与验证方法）
- **适用条件**：需要得到「外部工具会选哪个值」，且规则复杂或会随版本变化。
  - **做法**：优先让工具自己解析，例如无副作用的探测。
  - **验证**：用真实工具对照至少 3 种配置来源；用假工具钉住接线。
  - **边界**：探测有成本，且可能触发 hook 或网络请求，要披露并给出失败退路。这只是一种实现，不是唯一正确架构。
- **适用条件**：必须自己解析 shell 参数。
  - **做法**：用白名单接受能证明与 shell 一致的写法，其余不处理，并记日志。
  - **验证**：接受的样本逐项与 bash 自己的拆分结果比对；拒绝样本逐项断言。
- **适用条件**：修复型测试。
  - **做法**：每条都对旧实现做负对照，并让两份不同取值的数据区分正确与错误路径。
  - **边界**：旧版没有对应函数时，必然失败的断言不算独立证明（复审已指出）。
- 用 git worktree、不同工作目录等真实布局建测试，不只用普通临时目录。
