# PR #38 复盘：轮询身份与写身份分离（`WRITE_GH_TOKEN`）

## 来源
- Issue: [GigleAI/cavil-loop#36](https://github.com/GigleAI/cavil-loop/issues/36)（需求与背景，含 A/B 两种切分方案的讨论）
- PR: [GigleAI/cavil-loop#38](https://github.com/GigleAI/cavil-loop/pull/38)（实现，`Closes #36`，2026-09-22 创建并合并）

- 独立复审：PR #38 下 1 条 codex review（round 1，通过）

## 需求与结果（已确认事实）
Issue #36 陈述：daemon 与 worker 共用同一把 `GH_TOKEN`，2026-09-18 账号被封后轮询与写能力同时丧失（该陈述来自 issue 正文，本次证据范围内未见外部佐证链接，作为项目内部既有事实记录）。PR #38 最终实现：新增 `WRITE_GH_TOKEN` 配置项 + `gh_write_token()` / `gh_write()`；daemon 侧的 label 翻转、告警 issue 开关、post-merge-retrospective 的 `git push` 全部改用写 token；worker 侧交接文件仍叫 `GH_TOKEN`，只在 `secret_env_file` 一个取值点改变来源；`setup.sh` 为 `coding-agent.config` 和 EnvironmentFile 新增/已存在两种情况均补 `chmod 600`；`_lib.sh` 显式 `export GH_TOKEN` 以兜底裸赋值不可见的坑。留空 `WRITE_GH_TOKEN` 时完全回落单 token 行为。

测试证据：新增 `tests/write-token-split.test.sh`（15/15）、扩展 `tests/secret-env-not-in-argv.test.sh`（26/26）、既有 10 个测试全绿；单 token 模式下与旧实现 `tmux_env_args` 输出逐字节 diff 为空；系统性负对照（逐项退回旧实现，对应断言必须变红）全部符合预期；独立复审 round 1 一次通过，未要求返工。这些属于沙盘/单元测试层面的已验证事实。

## 明确未验证 / 未发生的事项（PR 正文第 5 节自陈，需如实保留）
- **不是真的两个账号**：`luosky-bot-poller` 尚未创建，PR 中"双 token 测试"实际两处都填的是同一把真实 token，只证明"`GH_TOKEN=... gh` 这条前缀路径能通过认证"，不证明两个独立身份已分别工作。
- **没有跑生产派工**：poll 周期用的是 sandbox 配置（触发 label 指向不存在的名字、`MAX_CONCURRENT_WORKERS=0`、关闭 auto-cleanup 和复盘），"daemon 真的用写 token 翻了一次真实 label"这件事没有发生过，只有假 `gh` 下的断言。
- **细粒度只读 token 是否够覆盖 daemon 全部读调用**：是从调用清单推断，未实测。
- **自我指涉盲点再次出现**：本仓库技能目录软链接指向 main checkout，本 PR 改的 `_lib.sh` 正是复审自己要用的脚本，合并前复审看到的仍是旧版行为——PR 正文称这是该项目第 4 次遇到此问题。

## 设计阶段的演变（有效做法示例）
1. **不轻信 issue 自带的现状盘点，独立复核代码**：issue 正文倾向方案 A（按进程切），agent 在设计方案阶段重新读代码，发现 daemon 除翻 label 外还有两处写（`post-merge-retrospective` 的 `git push`、告警 issue 开关），这意味着方案 A 下 poller 也必须拿 `Contents: Write`，与 issue 想去掉该权限的初衷矛盾。据此把推荐方案从 A 改判为 B，并实测方案 B 的改动量只比 A 多约 4 行（而非 issue 预估的"8 处调用点 + `run_gh`/`run_gh_capture`"）。（[issue #36 方案评论](https://github.com/GigleAI/cavil-loop/issues/36#issuecomment-5771504273)）
2. **人类简短提问被认真展开解释**：luosky 只问了一句"what is EnvironmentFile"，agent 用表格和实测说明其含义、路径、平台差异，并顺带指出该文件权限也从未被 `setup.sh` 管理（[issue #36](https://github.com/GigleAI/cavil-loop/issues/36#issuecomment-5771632056)）。
3. **人类一句建议触发方案迭代并暴露隐藏 bug**：luosky 建议"放 `coding-agent.config` + 600 权限"，agent 采纳的同时做了实测，发现一个**环境相关的假阳性**：在 config 里写裸赋值 `GH_TOKEN=xxx`，若该变量此前已在环境中被 export 过（本机因早年手工配置过而如此），`gh`/`git` 子进程仍能读到值，测试"通过"；但换成全新变量名 + `env -u` 清空环境重测，才发现裸赋值实际不会被子进程看到——这个坑在已有安装上测不出来，只在全新安装/cron 部署上才会静默发作（[issue #36 修订版方案](https://github.com/GigleAI/cavil-loop/issues/36#issuecomment-5771691189)）。

## 待人类拍板的问题未获书面确认（已确认事实）
方案中的 Q1（poller 权限切分走 A 还是 B）自始至终没有被勾选，agent 该条评论 `updated_at` 与 `created_at` 相同（未被编辑过），也没有文字回复"OK"。唯一的确认信号是 label 被重新打回 `pending/agent`，而这正是约定的"确认后重新标 `pending/agent`"的信号——按项目约定"都不勾 = 走默认"，最终按默认方案 B 执行。这是本项目此前已记录过的确认信号弱证据模式（勾选/文字确认之外，也可能仅凭 relabel 推断），本次是又一次实例，PR 正文对此也如实自陈（"方案确认情况（如实说明）"一节）。

## 经验教训
- 设计方案阶段独立复核代码比全信 issue 正文的"现状盘点"更可靠，遗漏关键写路径会导致按错误前提选错架构。
- 测试环境变量的 export/可见性语义时，若复用已被 ambient 环境预先 export 过的变量名，会掩盖真实的失效路径，得到假阳性结论；应使用全新变量名 + `env -u` 隔离后重测。
- 涉及密钥的配置文件权限治理容易被安装脚本遗漏（本例中 `setup.sh` 从未对 `coding-agent.config` 或 EnvironmentFile 做过 `chmod`，umask 下可能落地为同机任何用户可读），且新建与"已存在的老安装"两种情况需要分别处理（后者不能覆盖内容）。
- "都不勾选、仅凭 relabel 确认"是本项目已反复出现的确认模式，复盘/审计时必须逐条核实评论 `created_at`/`updated_at` 与正文内容，不能仅凭标签变化或最新评论作者推定已获书面同意。
- 沙盘/单元测试全绿、独立复审自陈"通过"、PR 已合并，三者都不等于"生产环境双账号已实际分别工作"——本 PR 在正文中清晰区分"跑过"与"没跑过，得说清楚"两栏，是值得保留的披露方式。
- 修改 CI/复审工具自身依赖的基础设施脚本时，天然存在验证结果版本滞后的自指盲点，PR 正文主动声明（而非被追问后才解释）是更可靠的做法。

## 最佳实践（附适用条件）
1. **设计方案落地前对 issue 自带的事实盘点做独立代码核实**——适用于任何"根据现状描述来决定架构切分点"的场景；不适用于纯粹的产品/优先级判断（那类判断本身就该问人）。
2. **测试环境变量可见性/export 语义时使用全新变量名 + 显式清空环境**（如 `env -u`），避免开发机既有状态掩盖真实行为；适用于任何依赖 shell 环境变量传递凭据或配置的项目，不代表所有环境变量问题都要如此测试（无跨进程传递需求时不必要）。
3. **负对照（逐项退回旧实现，断言必须变红）适合用来证明新测试确实能分辨新旧实现**，而不是"正确输入→正确输出"这类滤不掉错误实现的断言；成本是需要多写一次"故意退回"的验证步骤，适合改动涉及安全/权限边界这类高风险场景，不必用于所有小改动。
4. **PR 正文用"跑过 / 没跑过"两栏明确区分已验证与未验证的范围**，比笼统宣称"已测试"更利于复审和复盘；适用于任何涉及外部账号、生产环境或人工后续步骤才能完全生效的改动。

## 流程改进
- 对于"人工确认仅体现为 relabel、无书面勾选/文字回复"的模式，建议后续复盘固定检查评论的 `created_at` 是否等于 `updated_at`（未被编辑过则说明未勾选），并将其作为判断"是否获得书面确认"的标准步骤，而不是从标签变化直接反推。
- 安装脚本（`setup.sh`）对承载密钥的配置文件权限治理，建议作为一类固定检查项：新建文件是否显式 `chmod`、已存在文件是否也补做（且不覆盖内容）——本项目已在两个不同的密钥相关 PR 中发现类似遗漏。

## 待泛化的流程改进
以下发现在去除项目身份、术语与链接后，可能对通用 coding-agent 工作流有参考价值，留待后续独立的去项目化审查判断是否收入公开模板：
- 当一个决策要点被表述为"issue 正文已盘点清楚"时，负责实现该决策的一方（无论是人还是 agent）应把"独立复核该盘点是否完整"作为方案阶段的标准步骤，而非直接采信；遗漏关键事实可能导致选错整体架构方向，事后改起来代价远高于设计阶段多花的核实成本。
- 测试"某个值是否会被子进程/下游环境看到"这类问题时，测试者应主动排除"当前测试环境本身已存在同名状态"造成的假阳性，具体方法是换用测试环境中从未出现过的标识符，并显式清空相关环境状态后再验证；否则可能得出与生产/全新环境不一致的错误结论。
- "确认信号"可能弱于表面看起来的样子（例如仅是流程性动作而非书面同意），复盘类工作在判定"是否已获确认"时，应有明确、可复用的核验步骤（如比对时间戳、查正文），而不是依赖间接信号做主观推断。
