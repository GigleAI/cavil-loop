**返工原因（均来自复审评论）**
1. 链接识别连续多轮出现漏判和误判：括号、HTML 属性、普通文字被当链接、代码块后的引用定义。第 4 轮后 worker 把「是否换做法」做成选择题，维护者选 A，改用随仓库携带的 markdown-it-py（https://github.com/GigleAI/cavil-loop/pull/620#issuecomment-7054420883）。
2. 换解析器后，地址拆分又出现三个变体：`%23` 被当成锚点分隔符、`?plain=1` 查询参数、外部地址让 `urlsplit` 抛异常而中断整篇检查（https://github.com/GigleAI/cavil-loop/pull/620#issuecomment-7054971880 、https://github.com/GigleAI/cavil-loop/pull/620#issuecomment-7055127715 、https://github.com/GigleAI/cavil-loop/pull/620#issuecomment-7055263896）。
3. 文档里照做的强制刷新命令在分开安装时退出 2；常驻站会构建工作区未提交内容，文档最初没写。托管复审的去向被写成交人，指南与图源都漏了（https://github.com/GigleAI/cavil-loop/pull/620#issuecomment-7053672694 、https://github.com/GigleAI/cavil-loop/pull/620#issuecomment-7053899054）。
4. PR 正文的对拍数字不准：旧解析 6 处应为 8 处，链接 285 条应为 307 条（同第 1 轮评论）。
5. 返工回复把实现演变放在折叠区外，被两次要求移入折叠块（https://github.com/GigleAI/cavil-loop/pull/620#issuecomment-7054096910 、https://github.com/GigleAI/cavil-loop/pull/620#issuecomment-7055263896）。

## 经验教训
- 自写 Markdown 链接识别连续四轮被找出新漏洞，才交人决定改用成熟解析器；换成熟解析器之后，解析器之外的地址处理仍是同一类问题。（事实）
- 推断：若在第 2 轮就把换做法的选择题交出，可能少几轮返工；评论没有直接证明这一点。

## 最佳实践（有适用条件）
- 适用：要复刻外部标准（Markdown、URL）的检查器。做法：先评估成熟解析器，并说明引入成本。验证：与真实渲染结果对拍。
- 适用：解析 URL 类输入。做法：在未解码文本上先拆路径、查询、锚点，再各自解码；外部地址先分类排除，单条出错只报该条、继续查整篇。验证：用编码分隔符、外部地址后紧跟坏链接的用例，走整篇和限定范围两个入口。
- 适用：文档里有给人照做的命令。做法：在只有 HOME/PATH 的环境里按字面执行，并覆盖分开安装、脏工作区、别的分支三种情形。该做法在本 PR 中经复审复跑确认有效。
- 适用：正文引用对拍数字。做法：写明文件范围与复跑命令；复审复跑不同时以复跑为准。
