## 经验教训
- 做得好的地方（事实）：
  1. 方案阶段就划清「不改」的范围（安装方式正文、client/README.md 里指历史版本的「预览版」），并说明理由，复审认可。
  2. 标题改动会连带改变页内锚点，方案提前识别并同步改两处链接。
  3. 复用已有的文档检查（解析真实 README 的相对链接与锚点），而不是新写测试。
  4. 复审分开对待「复跑得到的数字」与「worker 自报的实验」。
- 失败教训：本 PR 未暴露新的流程问题。

## 最佳实践（有适用条件）
- 改标题、章节名等会成为锚点的文字时，先搜索全仓对旧锚点和旧称呼的引用，再用能解析锚点的检查验证；适用于有此类检查的文档仓库。
- 「去掉某称呼」类需求，先区分「描述当前状态」与「描述历史版本/安装方式」，不一刀切全局替换；验证方法是 grep 旧称呼并逐条解释保留项。
