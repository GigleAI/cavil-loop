## 经验教训

1. **增量扫描不能用固定条数的窗口**。
   - 方案首版每轮只读最近 30 条。停机积压 31 条时，最早那条永远进不了读取范围。
   - 处理记录随窗口裁剪后，还可能把人删掉的指派加回来。
   - 修订后改为按编号续读、分页读到上次进度为止（<https://github.com/GigleAI/cavil-loop/issues/690#issuecomment-7150073832>）。
   - 新开 L81。
2. **「读不到」在方案和代码两个阶段各漏了一次**（L36）。
   - 方案修订版把连续 30 轮读不到记成放弃并放行进度。
   - 代码首版把不认识的状态词当成已关闭、把缺正文当成没有来源，进度越过后不再补指派（<https://github.com/GigleAI/cavil-loop/pull/695#issuecomment-7151168169>）。
3. **写前复核漏了后读到的那份状态**（L41）。
   - 写前只看普通条目接口的打开状态。PR 详情已显示关闭时，仍给它加了指派并记作完成（同上）。
   - 方案首版同样只核对「打开、作者、无 assignee」。
4. **同一根因的变体，自称「一次列全」后仍漏了空串**。
   - 第 1 轮返工用两条校验收口，但来源分支名和目标分支名只查类型、不查非空。
   - 第 2 轮复审要求列出完整的输入校验表。
   - worker 随后把列表、条目、PR 详情、写后读回、进度文件列成一张字段表，标明哪些可以合法为空，第 3 轮通过（<https://github.com/GigleAI/cavil-loop/pull/695#issuecomment-7151480398>、<https://github.com/GigleAI/cavil-loop/pull/695#issuecomment-7152040937>）。
5. **开关的实际接受值与文档不一致**。
   - 文档和模板写「只有 `true` 开启」，实现却接受 `1`、`yes`、`on`。
   - 修复后只认字面 `true`，并补了行为测试。
   - 只此一例，未新开规则。
6. **主干已红的测试挡住了合并**。
   - 引入问题的是 #697，不是本 PR；本 PR 是查明并修复的一方。
   - 证据不说明本 PR 犯了这个错，所以不计次，列入下文「流程改进」。

## 最佳实践

- **每轮扫描新增条目、且每条只处理一次时**：
  - 做法：用持久化进度加分页，失败的条目挡住进度，但后面的条目照常处理。
  - 验证：超过一页的积压、失败条目被挤出首页后恢复、人删掉的写入不被加回。
  - 这是本次采用的一种做法，不是唯一正确的架构。
- **外部读取的结果参与「记完成」判断时**：
  - 做法：列一张字段表，逐项标明「必须非空」「只认已知值」「可以合法为空及其含义」；初判和写前重算共用同一份校验。
  - 验证：按表逐行做「故障一轮、下一轮恢复后补上」的跨轮用例。
- **写入之前**：
  - 做法：把整条判定重读、重算，与初判的依据整体比对；后读到的详情状态（关闭、合并）也要进入比对。
  - 验证：在「第二次读详情那一步才发现变化」的时点注入变化。
- **复审用独立故障注入，不只复跑既有测试**：
  - 本 PR 两轮打回都发生在既有回归全绿的情况下。
  - 问题是复审注入外部响应才复现的（<https://github.com/GigleAI/cavil-loop/pull/695#issuecomment-7151168169>）。
- **交付里分栏写清实测与未测**：
  - PR 正文写明本机没跑全量、没做压测、前后对比只是一次性核对。
  - 复审通过评论写明 CI 未完成、部署后验收未执行。

## 适用边界

- L81 针对「每轮增量扫描、每条只处理一次」的自动化。一次性全量扫描、由事件推送驱动的处理不适用。
- 「读不到的条目永不放弃、只降频」适合漏处理的代价高于重复读取的场景。它带来的读取成本没有压测数据。
