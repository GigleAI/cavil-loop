## 经验教训
1. 重构抽出共享函数后，要同步检查所有引用被删原文的辅助资产（负对照、文档片段）。默认回归全绿并不能证明这些资产仍有效。本次靠复审跑静态检查才发现（已确认）。
2. 设计阶段的两处返工（预期丢失、迟到响应归属）都是「设计复审先于编码」拦下的，实现阶段没有再出这两类问题（已确认）。

## 最佳实践（有适用条件）
- 先判定后写入、且两步之间用户可能改变环境时：把用户看到的确认清单原样传给写入层，写前只核对承诺项、不重算。验证方法：覆盖「原本没有」「承诺后被删」「正常」三种时序，并含正向创建断言。
- 异步读取可能迟到时，用「每次选择一个递增序号」而不是比较资源名。验证方法：受控放行 A→B→A，旧成功和旧失败各一次，并配退回「只比名字」的负对照（本 PR 手动验证了这一项）。
- 「读不到」与「确认没有」分开处理，预览和写前都不能把读取失败当作不存在。
- 作者在 PR 正文里把没跑的验证（完整窗口套件、整批负对照）和不稳定的失败如实列出，复审也据此判断。

## 流程改进
- 重构后，交付前在 PR 作者侧跑一次负对照静态检查（`node test/mutation/run.mjs --check`）。本次的缺口是该检查只在复审时跑。这是建议，尚未落地。
- 待泛化的流程改进（需另行去项目化审查，不自动发布）：凡是「默认跳过、仅定期执行」的检查，要有一个不执行主体、仅校验其前置条件（如替换原文是否存在）的快速门禁，随普通 CI 或自审运行。
