## 3. 经验教训
1. **同一规则有两份实现时，分别断言数字不够。** 补算（Python）是 `codex.sh`（jq）计价规则的第二份实现。第 1 轮漏了 3 类分支，其中部分项有价这一类正是驱动已处理的分支。修复后用同一份输入让两边各算一遍并比对，才能补上这类缺口。
2. **累计值不能在归属不全时拆给某个单项。** 记录里的 token 是全部调用的累计值，另有认不出模型的调用时，不能当作单一模型的用量。这条是复审通过实测样本发现的，作者自测没有覆盖。
3. **"如何得到"与"用的哪种来源"是两个维度。** 合并为一个字段会抹掉可信度归属，并让报告文字出错。
4. **真实链路上的测试可能区分不出错误实现。** 过期标记那条真实链路测试在旧代码上也绿，因为内置表当天没过期。作者因此补了替身日期的函数级测试。
5. **边界要显式声明。** 多模型、归属不全、哪里都没价、`{}` 关闭估算，这几种情况都保持"没有金额"而不编造。

## 4. 最佳实践（有适用条件）
- **适用条件**：同一业务规则在两种语言或两个入口各有实现。
  **做法**：用同一份输入驱动两边，比对全部输出字段，覆盖多种配置，再用错误变体做负对照。
  **验证**：去掉某个分支，交叉核对必须变红。本 PR 的做法是去掉"部分计价"后红 5 条。
- **适用条件**：对历史数据做事后推算。
  **做法**：先列出可推算的前提（归属完整、有用量、有价），不满足就保留"无法估算"；推算结果同时记录方法与来源。
  **验证**：对每个前提构造"刚好不满足"的样本。
- 这些是行为原则，不是唯一架构。拆成两份实现是否合理，本 PR 证据不足，未评估。
