## 经验教训

1. **正文测试命令带省略号，换来一整轮返工。** 代码首轮就是对的，返工只为把命令写全（https://github.com/GigleAI/cavil-loop/pull/693#issuecomment-7150650408）。这是 L34「写明命令与口径」的又一种形式：计数没错，但命令不可复制。
2. **跨目录的写死清单会在发版时才暴露。** 主干新增驱动的改动没碰客户端目录，客户端检查没有触发，过期预期一直留到手动发版才变红（https://github.com/GigleAI/cavil-loop/pull/693）。这与 L80 记录的是同一个缺口。本 PR 是修复方，不是引入方。
3. **修过期预期时保持测试独立，做对了。** 没有把期望改成从被测实现推导，也没有绕过发版门槛（https://github.com/GigleAI/cavil-loop/pull/693）。
4. **「合并」与「已发版」分开声明，做对了。** PR 正文、复审通过评论和 daemon 通知都写明客户端正式版尚未发出，并登记了谁做、做什么、怎么触发（https://github.com/GigleAI/cavil-loop/pull/693#issuecomment-7150847184 、https://github.com/GigleAI/cavil-loop/issues/574#issuecomment-7150876026）。
5. **推断：PR 用 `Closes #574` 让 issue 在客户端正式版发出前就自动关闭。** 维护者的要求是「打一个正式版看看」，而 issue 关闭时这件事还没做完，只靠 `pending/human` 和待办清单提醒（https://github.com/GigleAI/cavil-loop/issues/574#issuecomment-7150876026）。没有人或复审把这点指为问题，证据不足，本次不立规则。

## 最佳实践

- **适用：PR 正文或交人评论里写测试命令时。** 写出工作目录、前置步骤和完整命令，不用省略号代替参数。验证方法：把那一行原样粘到干净终端，能得到正文里的计数。
- **适用：某处新增的枚举项被另一个目录的测试写死时。** 在同一提交里更新那份预期并跑对应目录的测试；修过期预期时手工写出期望值，不从被测实现推导。验证方法：故意漏掉或多加一项，测试应当变红。
- **适用：修复只是解除发布阻塞、真正的发布在合并之后时。** 把后续动作登记为合并后待办，交付文字里明确「尚未发布」。验证方法：看发布页或运行记录，不看 PR 是否已合并。
