### 3. GitHub Project v2 看板 iteration 继承失败，最终归因不明

- 作者按模板要求如实上报失败，未擅自提权，向人类提出 A（开放看板写权限，一次性解决）/ B（人工每次手动补）两个选项并给出各自代价，等待拍板；**证据中未见到人类对该问题的最终选择**。

### 4. 自举边界（self-referential bootstrapping）问题再次出现
- 本项目技能目录通过软链接指向 `main` 分支 checkout；PR 修改自身依赖的 token-usage driver 脚本时，PR 自己以及复审产生的 footer 仍调用**旧版**（`main`）driver，因此复审自己的评论 footer 依旧显示不出模型名。作者在 PR 正文与首条评论中主动写明"这是自举边界，不是本改动失效"，并给出同一时间窗口新旧 driver 的负对照（token 数、金额逐字相同，只差模型名后缀）作为佐证（[PR body](https://github.com/GigleAI/cavil-loop/pull/31)、[PR comment](https://github.com/GigleAI/cavil-loop/pull/31#issuecomment-5710284750)）。
- PR 明确引用了此前 PR #27 遇到的同类问题，说明"改动 CI/复审自身依赖的基础设施脚本"在本项目里是可重复出现的一类风险，而非一次性意外；这次证明"提前声明 + 同窗口负对照"的应对方式可以复用且有效，避免了被误判为"改动没生效"的返工。

## 经验教训
1. **有效做法**：定位并修复"bug 为何能一直存活"的传播链（错误示例文档），而不只是修补表层症状，能降低同类问题复发概率。
2. **有效做法**：复审用"旧测试跑新实现"、"端到端解析而非只比对正则"、"变异测试+真实数据可达性核查"三种方法，比单纯读代码更硬，且对发现的非阻塞缺口给出了量化依据（0/95000 条真实记录命中），而不是主观判断"应该没事"。
3. **待解决/未闭环**：Project v2 看板的字段写权限失败后，作者正确地"如实上报 + 给选项 + 不擅自提权"，但人类是否已经拍板、iteration 字段最终为何变得一致，两者均缺乏可查证据；这暴露出当前流程对"迭代继承是否真正成功"缺少可留痕的核验手段。
4. **反复出现的风险点**：修改 CI/复审自身依赖的基础设施脚本时，验证结果天然存在"版本滞后一个发布周期"的自指问题，必须显式声明这一边界，否则容易被误判为改动无效（此前 PR #27 已踩过同一坑）。
5. **证据边界**：本报告全部结论均来自 PR/issue 的评论文字（含作者与复审自述的测试通过数字），无独立 CI 日志或第三方复核；复审执行体也是同一自动化账号（`luosky-bot`）下的另一次会话（footer 标注为 `agent=claude`），其"独立性"仅体现为不同调用上下文，而非不同身份或系统。是否有真实生产 daemon 派工验证过新 footer 的实际渲染效果，证据未覆盖，**不能视为已验证**；PR 合并也不代表该改动已经在生产环境实际运行过。

## 最佳实践（附验证方法，非唯一架构结论）
- 当一次生成需要同时产出"供人阅读文本"与"供程序解析字段"、且要求两者互不影响时，可用改动前的历史测试直接跑在新实现上做回归对比，能低成本证明"未预期变更范围为零"——前提是旧测试文件仍可从版本历史 checkout 出来。
- 变异测试可用于评估"新增断言能否真的区分错误实现"，但发现的覆盖缺口是否需要立即补齐，应结合真实数据的可达性判断（如实际日志/记录中该状态出现的频率），并把判断依据的具体数字写清楚，而不是仅凭主观感觉标"不阻塞"。
- 遇到写入外部系统（如 GitHub Project v2 GraphQL 字段）被拒绝时，应分层排查：先确认 token/OAuth scope 是否具备，再确认账号对该具体资源的协作者角色权限是否具备——这是两个独立维度，混淆会导致误判和白费力气重新申请错误的权限。
- 修改 CI/复审工具自身运行时依赖的脚本时，应在提交说明中主动标注"验证结果在合并前存在版本滞后"，并用同一时间窗口的负对照（除脚本版本外其余变量不变）证明改动本身生效，而不是被动等待被质疑后才解释。

## 待泛化的流程改进（供后续去项目化审查，不代表已发布到公开模板）
- 候选 1：同一次生成同时产出"人读格式文本"与"程序解析字段"时，除新增覆盖新格式的测试外，用改动前的历史测试跑一遍新实现，作为低成本的"未预期变更范围为零"验证手段。
- 候选 2：外部平台的 API/OAuth scope 权限与账号对某个具体资源（看板、仓库等）的角色权限是两个独立的检查维度；诊断"写入被拒绝"应显式分两步排查并分别记录结果，避免把"缺少角色权限"误诊为"缺少 scope"。
- 候选 3：修改 CI/自动化评审流程自身运行时依赖的基础设施代码时，验证证据天然存在"版本滞后"的自指边界；应在交付说明中主动声明该边界并提供同窗口负对照，而不是被动等待质疑后才解释——这类问题往往在同一代码库中反复出现，值得作为固定检查项。
