## 返工原因（均有评论证据）
1. **读取边界反复漏口**：托管条目的外部内容保护要求评论只经受保护命令读取，而范围脚本多次另走 REST 读正文。
   - 第 1 轮，方案模式绕过：https://github.com/GigleAI/cavil-loop/pull/624#issuecomment-7055127030
   - 第 2 轮，方案基线与指纹仍独立读取：https://github.com/GigleAI/cavil-loop/pull/624#issuecomment-7055510153
   - 第 3 轮（重新计数后的第 1 轮），复审点明「连续三次」：https://github.com/GigleAI/cavil-loop/pull/624#issuecomment-7055774446
   - 第 4 轮，代码模式找基线仍读评论原文：https://github.com/GigleAI/cavil-loop/pull/624#issuecomment-7056019606
   - 最终做法：托管加外部保护时，方案每轮全量；代码基线由 agent 从受保护读取输出里抄下，经 `--baseline-mark` 交给脚本，脚本不发评论请求。
2. **指纹绑定到未审版本**：评论在展示与指纹之间被改，会把未审版本记成基线。最终改为全文与指纹出自同一次读取，写前只核对版本未变。
3. **读取失败被当成「没有基线」**：和外部内容段「重试一次、仍失败交人」冲突，见 https://github.com/GigleAI/cavil-loop/pull/624#issuecomment-7056160102。
4. **测试入口覆盖不足**：直接调用拼装函数，子 issue 手工拼接，继承了派工环境变量，见 #624 第 1 轮评论。
5. **交付文字问题**：返工回复把修订过程摊在主文，PR 正文的测试数字没有标注对应提交与环境（#624 第 2 轮评论）。

## 经验教训
- 读取边界类问题被指出第二次时就该列全输入、读、写入口，而不是只修被指出的那一处。本 PR 到第 3 次才系统收口，后来还漏了代码基线这一路。该判断属于推断；依据是第 4 轮仍指出新旁路，见上文链接。
- 为「首轮列全」这一目标做的设计，自身也经历了「每轮挖出新问题」。这是观察，不能据此说明新规则无效，效果需合并后的轮次数据判断。

## 最佳实践（有适用条件）
- **适用**：脚本既要读受保护内容、又要算差异或基线。做法是让受保护读取成为唯一的正文入口，其他环节只接收它交出的最小片段。验证方法：把评论接口设成必定失败，再断言仍能算出结果，且请求记录里没有评论请求。本 PR 的 e32779e 采用了这个测试。
- **适用**：需要「审阅时看到的版本」和「记录的基线」一致时。做法是在同一次读取里输出全文与指纹，写前只核对版本未变。验证方法：在展示与写入之间编辑内容，断言不写基线。
- **适用**：失败分流有多条规则可选时。做法是明确区分「读完了但无结果」和「读取失败」，并指向已有的失败规则，不另造一条。验证方法：对真实派工产物逐句断言两种处置。
- 这些是本次采用的一种做法，并非唯一架构。代价是托管加外部保护的条目上，方案复审不再收敛（worker 已披露：https://github.com/GigleAI/cavil-loop/pull/624#issuecomment-7055979522）。

## 流程改进
- 复审第 1 次指出读取边界问题时，要求 worker 给出完整输入来源表，不等第 3 次。
- 交付评论的验证数字固定写成「提交 + 环境 + 命令」。
