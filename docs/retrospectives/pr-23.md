## 经验教训
- **技术状态码不应该直接暴露给非工程背景的评论读者**，即使含义在代码里是准确的。首次编写面向人类的输出文案时就应做"假设读者不懂内部术语"的自查，而不是等人类追问后才翻译。
- **金额/成本类展示的限定语（"参考估算，非账单"）需要在每一处出现的地方重复强调**，光在 PR 描述里说一次不足以让读到具体评论 footer 的人理解其局限。
- **对"本轮做了什么验证" vs "还有什么没验证"要分层说清楚**：本次报告明确区分了"本机手动复审已跑通"和"真实 daemon 自动复审派工尚未单独验活"，这种诚实边界声明值得保留，但也说明该功能离"完整生产验证"还有距离，不能视为已经在自动化关卡中稳定运行。
- Open Question 的复选框可以被作者直接编辑来拍板，而不产生新评论；仅凭"最新评论是谁发的"判断用户是否已反馈是不够的，需要核对被编辑评论的 `updated_at` 与正文内容（本 PR 场景下由方案设计者自身处理，未见处理失误，但该模式本身是通用注意点）。

## 可复用最佳实践（附验证方法与适用边界）
1. **静态价格/配置快照需要来源、核对日期与显式覆盖开关**：适用于任何"内置默认值 + 允许用户覆盖 + 可完全关闭"的配置项设计，不仅限于价格表。验证方法：检查文档/字段是否同时包含来源链接、核对日期、过期提示三项，缺一项都视为未完成。适用边界：仅适用于外部数据本身有稳定权威来源（如官方文档）且更新频率可预期（如 90 天量级）的场景；若数据源本身高频变动，静态快照策略需重新评估。
2. **面向人类的评论文案应在提交前做"去术语化"自查**：适用于任何自动化评论/报告类输出。验证方法：让不熟悉代码库内部字段命名的人读一遍文案，能否不看代码就理解结论；本次未做到这点，导致两轮返工，属于失败教训而非成功案例。
3. **明确区分"手动验证通过"与"自动化流程在生产中验证通过"**：适用于任何涉及自动化关卡（如 CI、自动 review、自动派工）的功能交付。验证方法：报告中必须分别列出"本机手动执行结果"和"自动触发路径是否实际跑通"，缺后者时要如实注明为待验证项，不能因为手动路径通过就默认自动路径同样可靠。本次 PR 做到了这一点（明确写"自动关卡的真实 daemon review 派工尚未单独验活"），可作为正面示例。

## 待泛化的流程改进
以下发现具有跨项目通用价值，建议在后续独立的去项目化审查中评估是否纳入公开 lessons 模板（本次不直接提交到公开仓库）：
- **成本/金额类自动化输出，应在首次实现时就同步设计"人类可读结论 + 机器可读状态"两套表达，而不是先做机器字段、事后再翻译成人话。** 这样可以避免"功能正确但表达方式让人无法验收"导致的返工轮次。该模式不依赖本项目的具体价格表实现，适用于任何需要向非工程干系人展示自动化计算结果（成本、风险评分、置信度等）的系统。
- **"自动化关卡是否在真实触发路径下验证过"应作为交付报告的必填项，而不是可选说明。** 手动模拟验证与自动触发验证是两类不同强度的证据，混淆两者容易让"看似完成"的功能在真实使用场景中失效。此原则不限于 review 关卡，也适用于任何依赖事件触发（如 webhook、定时任务、标签变化）的自动化流程验收。
