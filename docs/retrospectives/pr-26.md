## 3. 经验教训
1. **反复返工的成因是状态/并发组合路径没被回归覆盖**：入口"已打开脚本但未取锁"竞态、慢 fetch 持独占锁、人工告警被无变更部署/部署失败覆盖、告警创建失败后遗忘待办、旧 unit 指向稳定路径时漏 reload。每轮回归只覆盖成功路径或单一起点（评论 r1–r3 自述）。
2. **合并 main 引入新约定（读写身份分离）会让"测试全绿"失效**：部署器的裸 `gh api` 与 `gh_write` argv 相同，文本断言区分不了，需要断言身份（调用时的 token）。上一轮据"合并干净+测试全绿"判定集成完整，实际漏了该维度（开发方在后续评论中自认）。
3. **文档承诺须按实测校验**："可回退"未经实测即写入文档，被人工追问后才发现不成立。
4. **GitHub 的 mergeable 只覆盖 PR 对 base，且不同合并方式结果不同**；两个 open PR 的交叉冲突需主动查。

## 4. 最佳实践（附适用条件与验证方法）
- 涉及锁/租约/原子切换的变更：适用于多进程共享可变目录时。用"在关键间隙暂停真实入口、触发切换与清理后放行"的回归，并以退回旧实现的负对照确认会变红。
- 持久化"待办事实"与"通知结果（issue 号）"分开保存：适用于通知可能失败、需重试的告警。验证：通知失败 → 无变更再运行 → 重试成功的连续用例。
- 合并 base 后，枚举 base 新增的横切约定（身份、权限、路径解析）并对新入口逐项核对；验证方法为断言行为维度（如调用身份）而非调用文本。
- 文档中的运维承诺（回退、升级）在写入前用本地实跑验证。
- 交人前同时检查 `mergeable`、`rebaseable` 及与其他 open PR 的改动文件交集。
- 以上是本次采用的做法，不是唯一正确架构。
