## 最佳实践（有适用条件）
1. 自动写 GitHub 的任务，在「查找 → 写」之间重读目标，并逐项比对身份和状态。读不全就零写入且显式标红。适用于有时间间隔的先判后写。验证方法：用有状态的假服务注入「查到后目标被关闭或标记消失」，断言零写入和重读次数。
2. 零写入和写入都要有到达性断言，即断言假服务确实收到了写请求。这样「没写」不会被误当成「写成功」。
3. 外部读取区分 404 与其他失败。只有 404 才算「不存在」，其他失败算未知。
4. 给人照做的运维步骤，把文档里的命令块抽出来用假 `gh` 字面执行。限制：假 `gh` 不能证明真实权限。
5. PR 正文写明测试命令与口径，并披露自己没验证的部分。独立复审复跑后数字一致。
6. 新增任务只授予它需要的权限，其余任务权限不变。适用于改动 CI 工作流的 PR。

## 待泛化的流程改进
候选，需要独立去项目化审查后才能考虑进入通用模板，自动程序不会直接发布：
- 「失败自动登记」类自动化应只做追加（新建或评论），不修改已有条目的状态。读不全时宁可不写并让任务标红。
