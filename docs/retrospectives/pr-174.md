## 经验教训
1. **同一规则的"输入"没有端到端接通**（推断为根因）：共享颜色函数只有一份，但卡片、表格调用点把草稿参数固定为 `null`，读取层也未取字段，于是三个界面对同一条草稿 PR 结论不同。第一版 worker 已披露这个限制，但复审认为维护者的新要求已把这些界面纳入范围，不能用"已知限制"代替。
2. **测试把错误行为写成预期**：草稿卡片预期写成 `open`（绿）。这类用例即使全绿，也不能证明符合"与 GitHub 一致"。
3. **行为改动后注释/README 没同步**：新旧约定相邻共存，下一位维护者可能按旧句删掉回退路径。
4. **PR 正文命令未按原文执行就写成"已跑"**：区间命令实际不可执行（worker 称当时是逐个跑的，正文写法有误）。
5. **维护者偏好**：界面类方案要给高保真设计稿，不要字符画。

## 最佳实践（有适用条件）
- 适用：同一视觉/业务规则有多个展示位置且依赖多条数据读取路径时。做法：先列"输入字段 × 读取路径 × 展示位置"矩阵，对同一条数据在所有位置对拍；验证方法：同一条草稿 PR 三处一致的界面断言，加每个调用点/读取映射各自的负对照（本 PR 最终做了，14 项变红）。
- 外部状态读不到时区分"未知"与"否"：详情失败回退看板值，两处都无则不判草稿，关闭/合并优先（本 PR 502 场景覆盖）。
- 合入主干后核对主干新约定（#171 把时间线条目改为可折叠 `details`，徽章测试等待条件随之修改），而不是只看无冲突。
- 边界：以上是本次采用的做法，不是唯一架构；只适用于有多展示位置的规则。

## 流程改进
- 复审第 1 轮曾"准备→运行"命令不可执行；建议 PR 正文命令复制到干净 shell 原文跑一遍再贴（已由 L34 覆盖）。
