## 结果与证据
**已确认事实**
- 方案第 1 轮被打回，理由有四点：重试条件自相矛盾、已有 Done 仍可能残留待办标签、共用清单与旧路径「逐字节不变」冲突、可见区仍要人确认（https://github.com/GigleAI/cavil-loop/issues/159#issuecomment-6670843853）。修订版把三条路径的标签集合分表列明，并改用独立重试队列，第 2 轮通过（https://github.com/GigleAI/cavil-loop/issues/159#issuecomment-6670933148）。
- 代码复审第 1 轮实测出一个组合缺陷：本机清理持续失败时，标签重试到上限后队列记录被删，下一轮重新入队并从 0 计数。7 轮内出现 2 次「放弃」日志（https://github.com/GigleAI/cavil-loop/pull/163#issuecomment-6671552367）。
- 修复方式：标签结束时记为「已结束」而不删；入队保留已有值；清理成功后才删。新增 4 份负对照，把新测试套到旧提交上得到 71 通过 / 11 失败（https://github.com/GigleAI/cavil-loop/pull/163#issuecomment-6671773617）。第 2 轮复审亲手复跑后通过（https://github.com/GigleAI/cavil-loop/pull/163#issuecomment-6671908387）。
- daemon 检查打回：测试分片检查「最慢文件同路其他文件合计 ≤5 秒」变红。原因是新增测试改变了总量，requester-bot 的参考时间已过时（198 秒，实测 205–206 秒）。更新为 206 后 CI 全绿（https://github.com/GigleAI/cavil-loop/pull/163#issuecomment-6672107653）。第 3 轮复审通过（https://github.com/GigleAI/cavil-loop/pull/163#issuecomment-6672148900），随后自动合并（https://github.com/GigleAI/cavil-loop/issues/159#issuecomment-6672162429）。

## 经验教训
1. **重试上限的记录不能与上游去重状态绑死**（已确认）。上限耗尽后若删记录，而上游「未处理」状态还在，就会重新入队，计数归零。组合场景（清理失败 × 标签失败）没有被分别覆盖的用例发现，靠复审用真实子进程实测才暴露。
2. **新增较慢测试文件后，要复跑测试分组的自检**（已确认）。功能测试全绿，仍被 `tests/run.test.sh` 的分片检查拦下。
3. **推断**：方案复审阶段把「重试 vs 处理完毕」的矛盾拦在编码前，可能减少了实现返工。没有对照数据，不能量化。

## 最佳实践（有适用条件）
- 适用：有「重试次数上限」的队列。行为原则：「已耗尽」状态要独立持久化，直到上游条件真正解除。验证：用「上限设小 + 上游持续失败」的多轮测试，断言上限后不再读写，并对「结束时删记录」做负对照。
- 适用：设计失败恢复的多步写入。区分「已确认不用做」「暂时不知道」「部分成功」三种结果，只有全部确认才算完成。验证：跨轮故障注入。
- 适用：新增旧版本对拍基准。零写入类断言旁要加「确实执行到判断」的到达性断言。
- 本次采用独立队列，只是一种实现，不是唯一正确架构。

## 流程改进
- 在新增测试的 PR 自审里加一步：复跑测试入口自身的分组检查，并在需要时更新参考时间。
- 复审时对「有上限的重试」主动构造「上游状态不推进」的叠加场景。
- 待泛化的流程改进（需另行去项目化审查，本报告不直接发布）：有上限的重试，其耗尽状态应独立于上游去重状态。
