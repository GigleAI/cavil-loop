## 经验教训
1. **固定宽度区域加裁剪，会把数量可变的入口藏起来。** 顶栏外层没有横向滚动，不代表内部每个入口都可达。原有的 1024px 顶栏检查只测外层容器，示例数据也只有 2 个来源，区分不出"全部可用"和"藏起来所以不溢出"。
2. **跨引擎的主题切换有时序间隙。** Chromium 在事件发出时已重绘完，WebKit 没有，所以只在 CI 的 WebKit 上才会红。
3. **测试环境不同，结论就不同。** 本机只能跑 Chromium，必须等 CI 的 WebKit 结果，本机全绿不能代替。
4. **运维命令不属于界面方案。** 这次撤回比逐点补丁更有效，与"同根因连续变体时换思路"一致。

## 最佳实践（有适用条件）
- **适用：** 数量由用户数据决定的界面区域（来源、标签、列）。
  **做法：** 提供滚动或展开等实际可操作的溢出方式，并用超出可视宽度的数据在多种窗口宽度下，经真实用户操作访问末尾项。
  **验证：** 断言过滤结果或保存的选择确实变化；把旧样式放回去，测试必须变红。本 PR 的做法是 20 个来源，加真实滚轮和点击。
- **适用：** 异步更新（事件驱动）的视觉状态检查。
  **做法：** 轮询可观察状态（窗口模式加每个元素的计算样式），不用固定延时，也不放宽断言。
  **验证：** 把产品改成不切换，测试仍要变红。
- **适用：** 多处共用同一颜色规则的界面。
  **做法：** 用同一个函数（本 PR 为 `labelStyle`），并在每个出口各自断言。
