**已确认事实**
- 2026-11-10 的定时发版运行排队约 20 分钟。其间 main 前进了两个提交，脚本要求检出等于 main 最新提交，于是在第一步失败（issue #329 正文与方案评论）。
- 改动内容（PR 正文）：
  - 在「计划」和「按计划打标签」两种模式下，把「等于 main 最新」放宽为「在 main 历史上」。
  - 计划只读一次远端，之后全程用这个值。
  - 打标签仍只打在门禁测过的提交上。
  - 分叉、读不出先后关系都失败。
  - 本机手动模式不变。
- 方案阶段被复审打回一轮，原因是「无需人操作」与「请人确认」自相矛盾（https://github.com/GigleAI/cavil-loop/issues/329#issuecomment-6755494068）。修订版通过（https://github.com/GigleAI/cavil-loop/issues/329#issuecomment-6755547717）。

## 经验教训
1. 测试夹具与真实运行形状不一致，会让缺陷长期漏过。原测试把「运行的检出」模拟成「克隆远端最新」，掩盖了打标签那一步同样会失败。本 PR 的修复是把夹具改成「停在触发时提交」（issue 方案评论已指出此根因；PR 正文说明新场景套到旧脚本会变红）。
2. 方案评论的「要人做什么」前后矛盾，会被方案复审打回。这类问题在写完后通读开头与结尾即可发现。
3. 与改动无关的主干红灯会阻塞托管合并。本次是 `footer-ci-wait` 把「与 main 分叉点的脚本」当旧基准，#293 合入后基准本身已含新字段，比较必然不等。这属于推断：该测试写法与已有观察项 L47「旧基准取固定提交」同类。但错误来自 #293，不是本 PR，所以不计次。

## 最佳实践（有适用条件）
- 适用条件：同一规则被「计划」和「打标签」等多个入口共用，且涉及读取易变的远端状态。
  - 做法：只读一次，后续判断复用同一个值。
  - 验证：每个入口各有通过、分叉拒绝、读失败三类断言；故障撤掉后同一检出可正常计划。
- 适用条件：把「读不出」当「不允许」。
  - 做法：先后关系只认退出码 0/1，其余失败。
  - 验证：注入 git 故障的场景。
- 适用条件：宣称测试数字。
  - 做法：写明命令与基准提交，交付前复跑。
  - 验证：本 PR 两轮复审复跑的当前数字与正文一致。
- 适用条件：被无关红灯阻塞时。
  - 做法：单独提交，并在评论里披露范围超出。
- 以上是本次采用的做法，不是唯一正确架构。
