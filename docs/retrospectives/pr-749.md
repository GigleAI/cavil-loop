## 返工原因（已确认）
1. 方案第 1 轮被打回（https://github.com/GigleAI/cavil-loop/issues/747#issuecomment-7230126197）：方案把迭代/状态/里程碑三种系统菜单排除在「框外点击」保护之外，改前图是原型而非真实客户端。第 2 版改成页面内列表并换真实截图后通过。
2. 代码复审第 1 轮（https://github.com/GigleAI/cavil-loop/pull/749#issuecomment-7230726708）三项遗漏：
   - 方向键选中后再点高亮项不保存。
   - 点同一格内、列表外的空白不收起（把整个 td 当作框内）。
   - 拖列被 pointercancel 取消后松手仍保存。
   原因：保存只挂在「值变化」事件上；框内判断粒度过粗；拖动监听缺少取消与卸载清理。原测试未覆盖这些组合。
3. 第 2 轮（https://github.com/GigleAI/cavil-loop/pull/749#issuecomment-7230825160）：修问题 1 时新增的 mouseup 提交没限定按键，右键也保存迭代。第 3 轮修复并补回归后通过。
   推断：修一类输入路径时若不枚举全部鼠标按键，容易引入同类变体。

## 经验教训
- 把系统原生弹层改成页面内元素，才能让「框外点击」规则对所有控件一视同仁；复审据此打回排除范围的方案。
- 用「值变化」触发保存会漏掉重复点击当前项；换成显式提交入口后，又要限定按键并做一次性去重。
- 「框内」应按实际浮出的操作区域判断，不应按整个单元格。
- 指针拖动类交互要成套处理 cancel、失焦、卸载。

## 最佳实践（有适用条件）
- 适用：有拖动、弹层、选择列表的桌面/网页界面。方法：为每种交互列出输入路径（左/右/中键、键盘后再点击、取消、失焦、卸载），每条各写一个真实窗口回归，并断言写请求次数。验证：把组件换回旧提交，新用例应变红。本 PR 对 3 个回归、右键回归做了这种对拍（自报，复审亲跑了修复后的结果）。
- 方案阶段若有「改前」图，使用现有客户端的真实截图，原型只作设计稿并标注。
- PR 正文明写未测环境（WebKit），复审也不把它当作已通过。
- 以上均非唯一架构；页面内列表只是满足本场景的一种实现。
