## 经验教训
1. **追加第二个快捷键会改变原有判断的粒度**（已确认）。判断单位如果是「动作」而不是「本次实际匹配的键」，给动作追加带修饰键的键后，普通键也会被放行。这个缺陷在方案阶段被复审发现，代码阶段才用单元和窗口测试固化，没有发生线上缺陷。
2. 可见区排版问题（macOS 限制折叠、修订过程外露）是方案阶段的两轮返工。已有流程规则覆盖，不新增条目。

## 最佳实践（有适用条件）
- 适用条件：同一动作有多个触发键，且存在「输入框内是否放行」之类的上下文保护。
  - 做法：保护判断下沉到每个键，并按「动作 × 键 × 光标位置」穷举单元测试，再用真实按键的窗口测试验证。
  - 验证方法：在搜索、回复、设置三类输入框打字，确认文字完整且不触发动作，再按修饰键组合确认动作能触发。
- 手选值与默认值共用同一条计划规则，再用矩阵对拍证明不碰控件时结果不变。这符合 L3，只对「默认值兼容」类改动适用。
- 主要平台无法实测时，把限制、依据、影响和验收动作放在可见区，不把 Linux 通过写成 macOS 已验证（与 L11 一致）。
- L4、L34、L36 在本 PR 中也有对应的做对案例：真实窗口按键加假 GitHub 写请求断言、复审复跑计数一致、里程碑三态读取处理。本次没有改写这几条的「这样做是对的」，Seen 次数也不变，因为没有新的错误。
