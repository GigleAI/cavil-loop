## 经验教训
1. **返工原因（已确认）**：把「tag 已存在」当成「版本已发布」。tag 是多步流程的中间产物，页面才是最终产物。脚本在 HEAD 已有 tag 时返回「无事可做」，流程据此跳过后续步骤，失败后无法自愈。首版 50 条测试全绿但没覆盖「中间成功、后一步失败、全新环境重跑」。复审靠故障注入发现。
2. **推断**：方案阶段列了「无新提交不发」，但没列出「流程中途失败后的恢复」这个状态。这是对原因的推断，评论中没有直接说明。
3. 一个 PR 内只返工 1 轮、1 个根因，没有触发 L1（同根因第 3 个变体）。

## 最佳实践（有适用条件）
- 适用：流程包含多个有副作用的步骤（推送 tag、建页面等），并且可被定时或手动重复触发。
  - 「已完成」按最终产物判断，不用中间产物代替。
  - 查询失败当作「未知」并失败，不当作「没有」或「已有」。
  - 验证方法：故障注入，让前一步成功、后一步失败，再用全新 clone 重跑，并配旧实现的负对照。
- 流程文件中的 shell 步骤可用 YAML 解析读出、用 `bash -e` 真跑，加上可注入失败的假 `gh`，在没有 actionlint 和真实 Actions 时降低风险。这是本次采用的一种做法，不是唯一方案。
- PR body 分栏披露「实测过的 / 还没验证的」，并写明合并后验收和回退步骤。这与 L11 一致。
- 同一个「tag 是否已有页面」判断出现在两个步骤时，两处用同一查询，各自做负对照。这与 L3 一致。
