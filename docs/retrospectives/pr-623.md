## 经验教训
1. 配置读取这类同根因问题在第 3 轮才一次收口。收口方式是：项目清单只留一份，配置读法只留一个函数，并用同一组配置走完全部入口（https://github.com/GigleAI/cavil-loop/pull/623#issuecomment-7055799292）。这已有效，但收口前已多走了两轮。
2. 「读不到」被当成「没有」反复出现：第 3 轮的配置筛选，第 6 轮的缺字段回退默认前缀。
3. 「服务启动了」不等于「验收完成」。验收记录要绑定核验开始时的进程身份（第 1、2 轮）。
4. 缓存只存与路径无关的内容，路径相关判断每次重做（第 5 轮，已用三种请求顺序实测，旧提交上 3 项红）。
5. PR 正文测试数字多次与复审复跑不符（第 2、6 轮、重派后第 1 轮）。
6. 手动回退文档没有遇错即停，修复后按文档原文执行测试（第 1 轮）。
7. 对拍测试的基线在主干合并后口径漂移（重派后第 1 轮）。

## 最佳实践（有适用条件）
- 适用于有多个入口读同一份外部配置或状态的功能：先枚举全部入口，让它们调用同一个读取函数，再用同一组边界输入（空值、重复赋值、引号、不可读）跨入口验证。
- 适用于「就绪」状态会触发对外行为的流程：就绪只在核验完成后写入，并把核验开始时的身份在写入时比对。
- 适用于带缓存的服务：缓存键只覆盖内容，凡是依赖请求路径的判断都放在缓存之外，并用多种请求顺序加冷热缓存做测试。
- 合并主干后核对新入口登记（本 PR 处理 skill-deploy 冲突，见 https://github.com/GigleAI/cavil-loop/pull/623#issuecomment-7056681913）。这只是单个 PR 的做法。
