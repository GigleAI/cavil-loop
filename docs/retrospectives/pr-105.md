## 经验教训
1. 写给外部机器人照做的对接文档，同一动作（在哪个条目上回复、翻哪个标签）在约定段与流程表里说法不一致。既有 1126 条测试全绿，是复审用真实轮询脚本按文档字面操作才复现。证据：https://github.com/GigleAI/cavil-loop/pull/105#issuecomment-6551408884 。
2. 合入主干后，主干新约定（负对照开关）需要逐项补到本 PR 新增测试，worker 做了且分两种模式验证。

## 最佳实践（有适用条件）
- 适用：新增写给人或外部程序照做的操作文档。做法：至少一次按文档字面操作，并让「按字面做」的结果由真实脚本和状态式假 GitHub 断言（派工对象、最终标签）。验证：把文档改回错误写法，该场景应变红。本次补的对照测试只证明「轮询按条目自己的标签派工」这一事实，不证明机器人照做。
- 适用：新开关要求不打断现有项目。做法：开关关闭时对拍成品逐字节一致，并另造带现有项目追加要求的场景，开/关两种情况下断言最终出口；对每个渲染入口和模板出口各做负对照。本 PR 用此法；这是一种可行做法，不是唯一架构。
- 对拍基准取「改动前的拼装代码拼本版模板」，避免以后任何改模板文字的 PR 都变红（PR 正文说明，复审未发现问题）。
- 交付评论分栏列「还没验证的」，并写明合并部署前线上仍是旧版。

## 流程改进
