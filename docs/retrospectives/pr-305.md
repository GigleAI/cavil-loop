## 经验教训
1. 方案阶段独立复审的价值：第 1 轮抓到“新的一致性断言会推翻既有保护”的方案缺陷，在写代码前改掉（证据同上）。
2. 内部状态影响行为却不在界面显示（残留的查证问题挡住收起），是典型“看不见的原因”；本 PR 用枚举式一致性测试限定范围防再犯。
3. 只靠进入/离开事件维护的布尔状态，漏一次事件就会卡死；事件负责即时响应，再按真实状态周期复核。

## 最佳实践（有适用条件）
- 当“是否执行某动作”依赖多个内部字段时，可枚举字段组合，断言判定与用户可见内容一致；范围须排除有意保留的例外（人工解锁等），并为例外单独写回归。验证：给枚举加一个隐藏字段应使测试变红。
- 事件驱动的暂停/悬停状态，适用时在暂停期间对照浏览器真实状态复核；验证方式是在真实窗口里吞掉“离开”事件，看是否恢复。
- 清理规则放在唯一写入口，各入口（同步、查证结束、读回旧记录）各有一条测试。这是一种实现，不是唯一架构。
- 无法在本机验证的平台（Mac）明确列为合并后未验范围并写明验收步骤。
