## 经验教训

1. **“读不到”与“确定没有”要按字段穷举，不能按已知故障点逐个补。** 首版只处理了整次读取失败；缺账号名、缺类型、空类型、未知类型、读不懂的父地址、怪异的权限值分两轮才被点全（https://github.com/GigleAI/cavil-loop/pull/701#issuecomment-7152653352 、https://github.com/GigleAI/cavil-loop/pull/701#issuecomment-7153252813 ）。方案阶段已写了“读不到 ≠ 没有”，实现却只落到请求失败这一层。这是 L36 的又一次发生。
2. **写入持久状态的功能，方案要先写退出路径。** “不写”不等于“恢复原状”，方案复审靠一次真实 git 实验就证伪了（https://github.com/GigleAI/cavil-loop/issues/699#issuecomment-7151828324 ）。这个问题在写代码前被拦下。新开 L82 记录。
3. **新增默认开启的开关会改变别的测试的基线。** 本机快速检查全过，但几处对拍测试因新开关多读 GitHub 而失败，第一次返工交付时 CI 是红的（https://github.com/GigleAI/cavil-loop/pull/701#issuecomment-7153252813 ）。新开目录经验 L83。
4. **改变既有配置项的含义时，旧说明要一并改写。** 两行身份配置从“固定署名”变成“兜底”，模板前半段仍是旧说法（https://github.com/GigleAI/cavil-loop/pull/701#issuecomment-7152653352 ）。只出现一次，且复审模板已有“改了行为而文档没跟上”的检查，本次不单立规则。

## 最佳实践

每条写了适用条件和验证方法，不代表唯一正确的实现。

- **外部资料决定“换 / 保留 / 撤回”三种结果时**：在实现处列一张表，写明每个输入字段何时判不了、何时不合格、何时合格；枚举型字段只认白名单，不补默认值。验证方法是每个“判不了”分支各配一条“先生效、再给坏资料、再执行”的跨轮用例，再配明确不合格的对照用例，证明没有把所有情况都一律保留（https://github.com/GigleAI/cavil-loop/pull/701#issuecomment-7156533982 ）。
- **测试断言最终产物**：本 PR 的测试跑真实派工脚本和真实 worktree，真提交后读作者与提交者四项；仓库配置和全局配置用不同身份，能分出值的来源（https://github.com/GigleAI/cavil-loop/pull/701 ）。适用于结果由多层配置继承决定的功能。
- **负向断言要有正向对照**：断言“开关关着时没查权限”的同时，断言派工确实跑了（同上）。
- **修对拍失败时不删断言**：在对拍里关掉新功能，新功能的默认行为由独立测试覆盖（https://github.com/GigleAI/cavil-loop/pull/701#issuecomment-7156533982 ）。只适用于对拍本意是比较另一项功能关闭时的行为。
- **复审用最小真实实验验证机制**：方案复审两轮都用临时仓库实测 git 配置继承，并写明该实验不能替代项目回归（https://github.com/GigleAI/cavil-loop/issues/699#issuecomment-7151828324 ）。
