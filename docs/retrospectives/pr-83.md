## 经验教训
- 本 PR 没有暴露新的失败。设计阶段的一处误判（子项需要单独写附加段）在实现时重读派工脚本后更正，并在 PR 正文如实说明。这是已确认事实，见 PR 正文「和方案不同的一处」。
- 推断：一次通过很可能得益于方案阶段已把验收标准写成可实测项（issue #82 方案评论里的 4 条），但没有对照实验，不能断言因果。

## 最佳实践（有适用条件）
1. **同一规则要进多份指令时**：只保留一份原文，测试走生产拼装函数对拍成品，并对每个写入点单独做删改负对照。适用于提示词/模板类交付；验证方法是任意删一处测试变红（PR 报 12 个变红，复审复跑确认）。
2. **检查命令类交付**：在真实 git worktree（bare origin + PR 引用 + 假 `gh`）里用子进程实跑，断言判定结果与工作区/HEAD 不变，并用「错误实现」夹具（用本地 HEAD、不确认分支）确认夹具能区分对错。
3. **失败要可见**：检查取不到数据时明确判「检查失败」而不是「无冲突」，宁可交人也不放行。适用于任何「查询失败可能被当作否」的门禁。
4. **披露验证滞后**：改的是 worker/复审自己运行时依赖的指令时，单列「还没验证的」并说明部署前仍用旧版。
5. 方案与实现不符时，在 PR 正文单独列出更正，而不是悄悄改。
