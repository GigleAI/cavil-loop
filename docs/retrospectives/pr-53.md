## 3. 经验教训
- 没有出现返工。主要原因是范围很小,方案阶段已把"老 label 是否覆盖"这类不可逆风险摆成选择题,默认选了最安全的 A。这是推断。
- 人工只 relabel、不留文字时,PR 如实写出"这是推断的确认",复审又核对了方案评论的 `updated_at`,没有把推断说成人工确认。这印证了现有经验第 2 条。
- 方案提到的"label 名字是写死的"这个相邻问题被明确划出范围,没有顺手改,也没有悄悄忽略。
- 验证缺口(没跑真实 `setup.sh`)在 PR body 和复审里都明说了,印证现有经验第 3 条。

## 4. 最佳实践(有适用条件)
- 条件:改动是生成式配置或默认值,而且存在"权威来源"(例如仓库当前的 labels)。做法:把生成逻辑抽出来,用假的外部命令记录调用,再与权威来源逐项比对。验证方法:对旧实现做负对照,确认检查能拒绝未修版本。
- 条件:对已存在的资源有"覆盖还是跳过"的选择,且覆盖不可逆。做法:默认跳过,把覆盖作为选项交人。验证方法:断言调用中没有强制覆盖参数,并测已存在资源保留原值。
- 条件:人工确认只靠 relabel 推断。做法:在 PR 和交人评论里写明依据和执行的是哪个默认项。验证方法:核对方案评论的 `created_at`、`updated_at` 和正文。
- 以上是本次采用的做法,不是唯一正确的验证架构。
