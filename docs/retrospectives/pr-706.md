## 最佳实践（有适用条件，供参考，非本项目唯一正确做法）
- **退出 / 清理 trap 应在"设置时"固化要用到的值，而不是依赖执行时才展开的变量**：适用于任何用 `trap ... EXIT` 或类似退出钩子做资源清理（锁文件、临时目录）的 shell 脚本，尤其是函数内部用 `local` 变量、又开了 `set -u` 的场景——变量作用域结束后，trap 真正触发时引用它会直接报错而不是静默跳过。验证方法：故意让脚本在变量作用域结束后真实触发一次退出路径，确认清理仍执行、不报 `unbound variable`。
- **外部工具的返回码不可完全信任时，应解析其输出内容而非只看 exit code**：适用于任何"工具即使结果是失败也可能返回 0"的场景（本例是 `notarytool submit --wait`）。验证方法：构造一个会被工具判定为失败/非法状态的输入，确认脚本能通过解析输出正确识别失败，而不是被误导为成功。
- **模拟操作系统级行为差异（如"文件是否曾被运行过/标记过"）时，测试夹具要用对应真实状态的拷贝，不能用同一份文件复用于不同阶段**：适用于涉及 Gatekeeper、quarantine 标记等 macOS 特定保护机制的测试脚本。这是本 PR 修复的第 4 点，其普适性边界是"模拟系统级安全标记"这一类场景，不要套用到与文件运行历史无关的测试上。
