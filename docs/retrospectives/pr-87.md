## 结果与证据
已确认事实：
- 合并结果：每轮只在目标分支或 PR 有新提交时才判一次冲突；2 天内有更新的同仓库 PR 发评论并改标 `pending/agent`，更老或外部仓库的只提醒（PR 正文）。
- 与方案的偏离：方案写「用 GitHub 的能否合并字段」，实现改为本机 `git merge-tree`，理由是该字段会过期（PR 正文的实测，复审明确说没有重复实测这一现象）。
- 复审第 1 轮发现：写评论、翻标签前重读了 PR，却只核对提交与标签，未核对 `state=open`、目标分支，导致改投分支或已合并关闭的 PR 仍被派工。修复后重核打开状态、合并状态、目标分支、提交、同仓/外部属性与标签保护，缺字段则不写；新增 3 个场景和 2 个负对照（修复评论）。
- 测试：修复评论与第 2 轮复审均称 `tests/pending-human-conflict.test.sh` 68 通过 / 0 失败，7 个负对照全部变红；第 2 轮复审复跑了该测试与部分回归，数字一致。
- 人工授权：方案 Q1 的勾选 B 出自谁未验证；有 luosky 的 2 天限制评论和重新打标签。PR 与复审都如实写明，没有把勾选当作已确认。

未验证（均见各评论的披露）：合并部署前线上 daemon 仍是旧版；真实的「交回 worker → 解冲突 → 再交审」链路、两台机器同时判出冲突的竞态、另一台机器 git ≥ 2.38、真实首次拉取耗时。合并不代表这些已验证。用量/耗时无法据评论轮数推算，评论里的 footer 仅为各 agent 单轮自报，不能量化返工成本。

## 经验教训
1. 返工原因（已确认）：副作用前的「重读」只复核了部分身份字段，复审用同一套假 GitHub 夹具复现。复审还指出夹具缺少真实 API 的状态字段，使「缺字段当有效」蒙混过关。
2. 修复时没有只补点名的两条，而是一次列出写入前依赖的全部字段，这是对 L1 精神的提前应用（本 PR 仅 1 轮，不够计次）。
3. 推断：L4 方面，夹具与真实接口形状不一致是漏洞来源之一，但复审表认为 L4 已做到，故不计次。

## 最佳实践（有适用条件）
- 适用：daemon 先判定、后写 GitHub（评论/翻标签）且两步之间有间隔时。做法：写之前重读，并逐项比对判定时所依据的身份与状态（是否打开、目标分支、提交、属性、标签保护）；对不上或缺字段则不写、不记已处理。验证：跨快照测试 + 去掉某项核对的负对照。
- 同一规则有 worker 与 daemon 两份实现时，用同批输入对拍并分别做负对照（本 PR 6 个 PR 对拍，复审复跑确认）。
- 方案与实测冲突时，在 PR 正文单独说明偏离与证据。
- 去重标记按「会不会因自身副作用改变触发条件」分开设计（提醒评论会刷新更新时间）。这是本场景的一种实现，不是唯一架构。

## 流程改进
- 设计阶段对「先判后写」类功能，要求列出写入前需复核的全部字段。
- 夹具按真实接口字段补齐，缺字段默认判不通过。
- 已知遗留窗口（取目标分支提交到写评论之间、双机竞态）未被测试覆盖，需要时另开 issue。
