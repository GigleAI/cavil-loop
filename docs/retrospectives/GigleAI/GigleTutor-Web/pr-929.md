## 经验教训

1. **"隐藏"不是"删除"，同一类 bug 在本 PR 中重复出现两次**：无论是页面内手选（`sessionPick`）还是二级筛选（年级/章节），worker 最初都只做了"渲染期用 `id` 比对，不匹配就当作没选过"，这只能保证**当前这一帧**不用旧值；一旦后续状态变化又"凑巧"变回原值（如 A→B→A、或换账号后映射到同一个 chip），旧状态会原样复活。根因是把"状态隔离/归属判断"和"状态清除"当成了同一件事。**这个错误在同一个 PR 里被同一个 reviewer 指出两次**，说明第一次修复时没有把教训推广到结构相同的第二处代码。
2. **把"可以发请求"和"身份/上下文已确认"混为一谈，会导致误删有效缓存**：KP 深链场景下，`profile` 还在加载、`active_syllabus_id` 暂时是 `null`，但列表请求本身不需要等它（可以直接发全量请求）。worker 最初把"列表 ready"这个信号也拿去判断"教纲是否变了"，于是把"暂时不知道"误判为"变成空了"，删除了本该保留的历史手选记忆。
3. **活文档（spec）是唯一真值时，局部行为改动容易漏改分散的旧描述**：为响应一句人工 UX 反馈删除了一处 UI 文案分支，代码、测试、spec 的"结论段"都同步改了，但 spec 中另一处（Design 一末尾）残留了与新决定相反的旧描述。若后续有人只读 spec 实现，会把刚删除的行为重新加回来。文档去重必须做**全文关键词检索**，而不是只改"看起来相关"的那一节。
4. **设计前置评审能在写代码之前拦住行为矛盾**，本 PR 的设计阶段（issue #926）连续 4 轮 codex 评审都在实现开始前就发现了"手选生命周期与验收标准自相矛盾""KP 深链入口事实错误""异步边界未覆盖"等问题，全部在写代码前解决，避免了这些问题演变成代码阶段的返工。这是本次流程中效果最好的部分。

## 最佳实践（可复用，已有证据支持）

- **验证约定的状态失效语义**：当前渲染不使用旧值，还要验证 A→B→A 等往返后不会恢复本应失效的选择。显式清空是本次采用的方式，按上下文重建状态等实现也可满足要求，不强制特定架构。
- **区分"未加载完成（unknown）"与"已确认变化（known-different)"两种状态**，只用后者驱动缓存失效/清除逻辑；前者只用于决定是否等待渲染，不用于决定是否清除已有状态。
- **把"过程记录"（历次修订对照表、reviewer 意见处理记录）折叠进独立区块**，正文只保留当前有效的设计结论和需要人工决策的问题——这不仅是可读性问题，本 PR 的 codex reviewer 明确将"过程信息留在正文"判定为设计不通过的理由之一。
- **UI 文案变更要联动检查所有引用同一行为的文档位置**（spec 全文、i18n 注释、PR body），而不是只改觉得相关的那一段。

## 项目特有经验（不写入 lessons，仅记录于此）

- 本仓库题库的"教纲/年级/语言过滤"三层规则耦合复杂（`SYLLABUS_GROUPS` 分组 + 题面语言过滤 + KP 深链），后续在 `src/pages/QuestionBank.tsx` 及 `src/services/questions.ts` 一带做类似改动时，应优先参考本 PR 沉淀到 `src/pages/AGENTS.md` 的规则（生效值两层模型、两层失效判据、语言过滤范围限制不写入 UI 文案等）。
- `useLoginSegmentKey`（模块级登录段）在本页被明令禁用（会引发 `useAccountScope.stillMine()` 误判，历史上踩红过 PhotoSolve 用例），本页身份判据只能走组件内 epoch / `useUserScopedState`。
- 已知不覆盖的产品边界：跨设备/跨标签页修改当前教纲后，本页手选记忆只能等到本页真正重新读取到新 profile（5 分钟 staleTime）才失效，"换出去又换回同一本且本页全程未观察到"这条路径明确不覆盖。

## 流程改进建议（未声称已实施，仅为建议）

- 建议评估：对于类似"默认值 + 边界情况"这类需求，是否可以在设计评审的第 1–2 轮就把"允许延后决定的边界问题"与"阻塞实现的核心矛盾"分层展示，减少反复重写全文档的成本（本次 8 轮设计修订中，多轮只是折叠块内容调整，正文核心结论早已稳定）。
- 建议在 worker 的"回应单条人工反馈"流程模板中提示：修改行为文案/逻辑时，若项目使用"活 spec 作为唯一真值"模式，应对 spec 全文做关键词检索复核，而不仅修改判断相关的段落。该提示已写入共享 `prompts/lessons.md`，由后续合成 prompt 加载；未修改基础模板。

## 适用边界

- 上述"状态失效两层实现"和"unknown vs known-different"经验，适用于任何"记住用户临时选择/缓存，但特定事件后应重置"的前端状态管理场景，不限于本仓库或本框架（React + react-query）。
- "活文档全文检索"经验适用于任何以单一 markdown/spec 文件作为实现与验收唯一真值、且该文件会被多处引用的项目结构；对不采用这种"spec 镜像 PR body"模式的项目，价值有限。
- 本报告不能确认该功能在生产环境的真实运行效果（无生产 SQL 执行、无生产环境人工验收记录），仅能确认代码已合并入 `main` 分支且自动化测试（含 reviewer 独立复现部分）通过。
