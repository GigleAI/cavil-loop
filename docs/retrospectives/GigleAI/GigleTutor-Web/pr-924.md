## 经验教训（本次真实发生的返工）

设计阶段 3 轮 review 抓到 2 类真问题：① `pg_read_all_data` 不含 `BYPASSRLS`，会导致零策略表（`auth.users`/`private.credit_purchases`）静默丢失或导出直接失败（https://github.com/GigleAI/GigleTutor-Web/issues/923#issuecomment-5642298955）；② 看门狗"48小时告警"的口径与"每日检查一次"的调度频率不自洽，需要改成"漏一次约24小时内发现、非严格时限"（https://github.com/GigleAI/GigleTutor-Web/issues/923#issuecomment-5642402785）。

实现阶段至少 6 轮 review 抓到的真实缺口（均有可复现的复现脚本证据，非猜测）：
1. **缩水守卫形同虚设**：临时导出文件在落盘前被 `listBackups` 当作"上一份备份"纳入比较，导致缩水检测永远通过；运行期失败（连接失败/版本落后等）绕过告警口。https://github.com/GigleAI/GigleTutor-Web/pull/924#issuecomment-5642982432
2. **告警去重被 GitHub API 默认 100 条 limit 截断**：目标 issue 排在第 101 条时判定为"不存在"，导致重复开新 issue、旧 issue 永远关不掉。https://github.com/GigleAI/GigleTutor-Web/pull/924#issuecomment-5646319993
3. **目录权限收紧失败被空 catch 吞掉**，且 `pg_dump` 自建输出文件默认 644（umask 导致），即使父目录已收紧到 700，导出期间的临时文件仍短暂处于宽权限状态。https://github.com/GigleAI/GigleTutor-Web/pull/924#issuecomment-5653421736
4. **缺少整轮硬期限**：连接/子进程挂起时不会触发统一告警口，锁与进程常驻，后续每日调度都无法获取锁。https://github.com/GigleAI/GigleTutor-Web/pull/924#issuecomment-5653488127
5. **超时机制连续三轮踩同一类坑**：a) `Promise.race` 只让等待方失败，原任务仍在跑，会在文件收尾阶段跨过期限后照常轮转、写成功心跳（https://github.com/GigleAI/GigleTutor-Web/pull/924#issuecomment-5653546885）；b) 取消令牌未贯穿心跳更新内部"先 GET 再 POST"的两步（https://github.com/GigleAI/GigleTutor-Web/pull/924#issuecomment-5653657604）；c) 闭环告警在"准备参数文件"到"真正 spawn"之间同样缺检查点（https://github.com/GigleAI/GigleTutor-Web/pull/924#issuecomment-5653718665）。这三处是**同一类根因**（"最后一次取消检查"与"真正产生副作用"之间隔着未被覆盖的 `await`），直到第三次才做了一次系统性审计并逐一钉死。

此外，人工执行 SQL 时遇到 Supabase SQL editor "选中文本时 Run 只跑选中部分"导致的语法错误，worker 通过本地 PostgreSQL 复现四种可能报错并精确定位根因，改用 `$$…$$` 美元引号占位符 + 三步执行说明解决（https://github.com/GigleAI/GigleTutor-Web/pull/924#issuecomment-5653238908 、 https://github.com/GigleAI/GigleTutor-Web/pull/924#issuecomment-5653275313）。

## 最佳实践（附适用条件）

- **入口级/接线级回归测试是纯函数单测的必要补充**：本 PR 两个最早的 P1（缩水守卫、失败不告警）均是"单测全绿、链路是坏的"——纯函数测试通过不代表真实调用链正确。适用条件：脚本/服务存在"多个模块拼接成一条调用链"且各模块分别有单测时，应额外补至少覆盖关键失败路径的端到端/入口级测试。
- **RED→GREEN 验证**：reviewer 明确要求"撤掉修复、证明测试确实变红"，worker 照做并贴出前后对比日志。适用条件：任何声称"已修复且有回归测试"的场景，尤其是安全/可靠性相关修复，建议保留撤销验证的操作习惯，而非仅凭"测试变绿"下结论。
- **生产验证优先用真实但可回收的资源**：本 PR 用开发库反复验证设计假设，仅在设计和实现都收敛后才在正式库跑首份备份+还原演练，且演练库用后即销毁——将"高风险操作"的验证成本前置到低风险环境。适用条件：存在可用的非生产等价环境（如结构相同的开发库）时适用；无此类环境时该模式不可直接复用。
- **对"官方能力状态未知"的表述要收窄为可证实的事实**：worker 多次将"仓库里没有自建备份链路"与"线上一定没有备份"区分开，明确标注后者为无法核验（因缺少 Supabase 控制台访问权限），未替用户下结论。适用条件：任何 agent 无权访问的第三方平台配置状态，均应采用此种"仅陈述已证实事实+明确标注未知"的写法，不能因为看不到就默认为否定。

## 流程改进建议（仅为建议，未声称已落地）

- 对涉及"限时/取消"的异步流程，建议在**第一次**实现时就做一遍"每个检查点 → await → 副作用"的系统性审计（本 PR 第 4 轮修复中做的那种审计表），而不是等 review 发现一处修一处、连续三轮才做完整审计——这类问题的根因具有高度同构性，一次性审计的性价比明显更高。
- 对"按 marker 在 issue 列表中查找是否已存在"这类模式，建议将其列为项目通用契约/共享工具（本 PR 已复用 `nightly-infra-alert.sh`），并在该工具的测试套件中固化一条"数量超过默认 limit"的边界用例，防止未来其他调用方重复踩同一个分页坑。
- 建议为"仅打印/脱敏用途的工具函数"（如本 PR 中把整行当作 key 打印导致密码泄露到会话日志的那个工具）补充格式不符预期时的失败安全测试用例，作为项目通用测试清单的一项。

## 适用边界

- 本复盘中的具体数字（30 小时阈值、15 分钟整轮期限、7+4+6 的 GFS 保留策略等）是该项目的场景化选择，不应作为其他项目的默认值直接套用。
- 由于未提供 review 轮次对应的调用次数、token 用量或耗时的可靠汇总数据（评论中虽附带各轮的耗时/token 数字，但缺少跨轮次的统一口径与聚合方式），本报告不对"本次任务主要耗时来源"下结论。
- "codex review 多轮"这一模式本身是该仓库的 agent 工作流设计（bot 对 bot 的对抗式审查），其价值（持续发现真实缺陷）与代价（六轮以上的迭代成本）需结合具体项目的风险等级权衡，不代表所有项目都需要同等强度的审查轮次。
