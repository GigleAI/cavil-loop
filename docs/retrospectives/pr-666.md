# PR #666 复盘：让草稿读回用例只在「发版状态核对」生效时通过

## 来源
- PR：https://github.com/GigleAI/cavil-loop/pull/666（已合并，只改 `client/test/unit/dev-release.test.ts` 一条用例，+8/−2）
- 触发：每晚负对照自动报告 https://github.com/GigleAI/cavil-loop/issues/663 ：「发开发版：发完不读回核对」没变红。
- 方案轮往返记录：https://github.com/GigleAI/cavil-loop/issues/663#issuecomment-7072850307 ；方案复审通过：https://github.com/GigleAI/cavil-loop/issues/663#issuecomment-7072956963

## 结果与证据
已确认事实：
- 根因：发布后有两道读回核对（发版状态、标签位置），报错共用前缀「发完再读」；原测试只断言退出码 1、该前缀、没有公开发版，第一道被关时三条仍成立（PR 正文 https://github.com/GigleAI/cavil-loop/pull/666）。
- 修法：断言第一道专属文字，并断言假 GitHub 请求记录中发布之后没有标签读取；不改脚本、不改负对照条目。
- 测试证据：PR 正文与复审都记录 `dev-release.test.ts` 70 通过、typecheck 通过（复审独立复跑一致：https://github.com/GigleAI/cavil-loop/pull/666#issuecomment-7073743100）。
- 一次 daemon 打回：Client 检查中与本 PR 无关的用例超时（60s），worker 重跑失败任务后全绿，代码未改（https://github.com/GigleAI/cavil-loop/pull/666#issuecomment-7073877727 ，复审 https://github.com/GigleAI/cavil-loop/pull/666#issuecomment-7073926289 ）。
- 合并：autopilot 自动合并（https://github.com/GigleAI/cavil-loop/issues/663#issuecomment-7073951124 ）。

未验证（推断）：
- 负对照是否真的重新变红：开发期按规定不跑，PR 正文标为推理，须由合并后 main 上下一次每晚运行确认；目前没有该运行的证据。
- 用量、token、耗时：各评论 footer 有分项数字，但缺乏完整口径（部分模型/会话未知），不据此推算主要耗时来源。

## 经验教训
1. 测试只断言多道防线共享的报错前缀时，一道防线被关，另一道会兜底让测试仍绿，测试因此分辨不出被测防线（事实，来自 #663 与 PR 正文）。该缺陷是此前引入的，不是本 PR 犯的，故不计次。
2. 方案复审两轮打回的是版式/交接问题（开工方式表述有歧义，「或勾好选项」），不是技术问题（https://github.com/GigleAI/cavil-loop/issues/663#issuecomment-7072850307 内的复审记录）。

## 最佳实践（有适用条件）
- 适用：同一故障路径有多道相似防线、测试需要证明「是某一道拦下的」时。做法：断言该防线专属的输出，并用行为证据（假外部服务的请求记录）确认后一道防线没被走到，而不是断言另一道的措辞不出现。验证：把被测防线关掉，两条新断言都应变红（本 PR 仅推理，待每晚负对照确认）。
- 用例经子进程跑真实脚本、断言运行输出与假 GitHub 收到的请求，符合既有 L4 做法。
- PR 正文区分实测（70 passed）与推理（负对照效果），符合 L34 做法。
