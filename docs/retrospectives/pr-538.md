# PR #538 复盘：满负载下客户端 e2e 连跑三遍

## 来源
- 需求：issue #534 要求在 28 核机器、1 分钟平均负载 22–37 下，对主干连续全量跑三遍 e2e，并单跑 `blocked.spec.ts` 检查启动超时。https://github.com/GigleAI/cavil-loop/issues/534
- 方案：经 2 轮复审。第 1 轮因缺少对维护者回复的引用被打回，第 2 轮通过。https://github.com/GigleAI/cavil-loop/issues/534#issuecomment-6878006932
- 人类反馈：维护者只回了「开搞吧」。https://github.com/GigleAI/cavil-loop/issues/534#issuecomment-6877931613

## 结果与证据
- 已确认：PR 只新增一份运行记录 `client/test/e2e/load-runs/issue-534.md`，没有改代码，已合并。https://github.com/GigleAI/cavil-loop/pull/538
- 返工原因（已确认）：第一轮三遍都有 4–5 个负载采样落在 22–37 以外，复审判定不计入验收，因为方案要求每分钟采样都在区间内。中位数在区间内不能抵消。https://github.com/GigleAI/cavil-loop/pull/538#issuecomment-6879296936
- 解决方式：补负载的程序改为每 2 秒按系统正在运行的进程数增减忙循环，不再每分钟看一次滞后的负载平均值。重跑三遍，每遍 229 过、0 失败、2 跳过，范围外采样为 0；单跑 `blocked.spec.ts` 14 过，没有出现启动超时。这些是 worker 的自报，PR 正文写了命令和口径。https://github.com/GigleAI/cavil-loop/pull/538#issuecomment-6880655824
- 复审独立复跑的只有 `npm test`（2262 条）、typecheck、不加负载的 `blocked.spec.ts`（14 过）。三遍满负载结果和负载采样未被独立复算。https://github.com/GigleAI/cavil-loop/pull/538#issuecomment-6880713457
- 已确认的限制：结果只覆盖开跑时的主干 `6a646d27`，不含跑完后合入的 PR #537。
- 量化：评论里有各轮耗时和 token 数据，但本复盘不据此推断主要耗时来源。

## 经验教训
1. 验收条件写成「每个采样都在区间内」时，控制手段的响应速度也要匹配。每分钟看一次滞后的负载平均值，补得太晚、撤得太多，第一轮因此作废（已确认）。
2. 先把「不算数」的一轮如实保留在记录里，再重跑，复审能核对（已确认）。
3. 合并后主干又前进时，写明结果只覆盖哪个提交，这是诚实的做法（已确认）。

## 最佳实践
- 适用条件：验收含「全程处于某区间」的资源条件，并且人为制造负载或资源压力。
  - 做法：用高频反馈控制，例如按运行进程数而不是滞后均值。
  - 验证：按每个采样统计范围外的个数，而不是只报中位数。
- 适用条件：多轮运行中有一轮不合格。
  - 做法：保留原始数字并标明不计入验收。
  - 验证：复审可对照新旧两轮。
- 适用条件：只把运行记录作为交付物。
  - 做法：正文、运行记录两处的数字来自同一次脚本计算。
  - 验证：逐行核对两处是否一致。

## 流程改进
- 方案阶段若预见补负载的方式，应直接把控制频率写进方案。本次方案只写「每分钟记 uptime、N 按实测调整」，实际执行才暴露滞后问题（推断）。
- 三遍满负载运行没有被独立复算，这是现有流程的局限；是否需要复审复跑，由人决定。
