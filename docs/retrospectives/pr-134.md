## 经验教训
- 同一对象存在两份实现（发送端/参考消费者）时，来源判断这类前置分流也要纳入对拍；本次只对拍了「选中哪条评论」，漏了「该不该走新路径」（事实，见复审第 2 轮）。
- 并发写入窗口靠「多读一次」消不掉，只能消除写入动作本身或改用条件写入（事实：复审第 1 轮、修复评论）。
- 删除某个核验后新测试仍全绿，说明该核验缺独立负对照（事实）。
- 方案阶段对同源问题逐点补洞，浪费了多轮；第 3 轮后才一次列全输入表（事实；耗时/token 无法从此归因，缺少可量化数据，不做量化结论）。

## 最佳实践（有适用条件）
- 适用：多端共同解释同一份数据的协议。做法：先枚举写入方每一步、消费方可能读取的每个时点，在每一步之后跑一次独立写的消费者参考实现；验证方法：受控交错测试 + 退回前几版规则的负对照变红。
- 适用：外部接口缺少条件写入时。优先让「写入」不修改他人可能同时编辑的内容（如另发记录），而不是缩小窗口；验证：在请求处理前注入外部编辑，断言字节保留。这只是本次采用的一种实现，不是唯一架构。
- 测试中「旧版本」基准用固定提交（验证：对负对照逐条确认真的变红）。

## 流程改进
- 方案复审中同源问题第 2 次出现时即要求输入/读写总表，不等到第 3 轮。
- 对拍清单应包含「分流/来源判断」，不仅是最终选择结果。
