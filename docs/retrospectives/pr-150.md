## 经验教训
- 同一条异步有效性规则分散在多个入口，各自实现，导致补一个漏一个（对应 L3）。第 2 轮修复统一为 `openSession` 的同一判断，四类入口用同一组往返输入对拍。
- 「只和 github.com 通信」这类边界，只收紧策略字符串不够。第 1 轮复审用真实 Electron 请求拦截发现越界。修复后 worker 的界面测试记录窗口真实请求，既断言允许的请求发出，也断言额外域名零请求。
- 嵌套分页：外层读完页、内层子列表只取第一页，会漏数据；任何一页失败都不能显示成完整讨论。
- 负对照自身要验证：worker 自述有一项「后续页失败当读完」的负对照第一次对错了行而没变红，后来才改对位置。候选读取的跨打开负对照做了也不变红（那层检查冗余），最终如实说明，复审接受。

## 最佳实践（有适用条件）
- 适用：界面有多个异步调用，且用户可能切换对象再返回时。做法：用「本次打开」的身份统一判定迟到响应，有效性判断集中到一处；用真实窗口里受控暂停请求的方式验证，再对每个入口做负对照。若负对照不变红，先确认该检查是否真的冗余，而不是硬凑。
- 适用：有网络出口白名单要求时。做法：策略层与进程层双重限制，并以实际请求记录断言「允许的发出、禁止的没发出」。
- 适用：交付说明。做法：把「还没验证的」单列（真 Mac、真实 GitHub 写操作），不把假 GitHub 的通过当作生产验证。
