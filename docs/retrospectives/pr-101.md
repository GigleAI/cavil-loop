- 复审第 1 轮实跑发现：curl 默认展开地址里的 `[1-2]` 和 `{a,b}`，一次叫醒发出多次请求。多个状态码拼成 `200200`，成功被误记为连接失败。8 秒延迟的两次请求使整次叫醒达 16.31 秒。原有 1118 条测试全绿，仍漏掉这个输入。

## 经验教训
1. 事实：把运维者配置的值交给带展开语义的工具，会出现输入被改写的问题。把地址经标准输入传给 curl 解决了「不进命令行」，没有关闭 URL 展开。测试用的地址只是普通路径，没有元字符。这是复审靠真实输入发现的，不是自带测试发现的。
2. 事实：测试 1118 条全绿，不代表输入空间被覆盖。该输入类别（配置值含元字符）在初版没有任何测试。
3. 推断：初版负对照很充分（57 个），但变异都围绕设计里列出的失败模式。对「工具本身的默认行为会改写输入」这一类没有变异。

## 最佳实践（有适用条件）
- 适用条件：配置值或外部输入被传给 curl、shell、jq 等有默认展开或转义语义的工具。行为：真跑一个含该工具元字符的输入，断言对端实际收到的请求，并确认关掉对应开关后测试变红。验证方法：服务端记录请求数和路径。
- 适用条件：同一能力有多个入口（叫醒、结果通知）。行为：逻辑只放一处，每个入口用同一输入各做断言和负对照。本 PR 的修复只改一处，两条路径的测试都变红，说明这样做有效。这是一种做法，不是唯一架构。
- 适用条件：返工后测试数字有出入时。行为：以独立复跑为准并在评论中更正。本 PR 复审把 1124 更正为 1125。
