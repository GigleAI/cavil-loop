## 经验教训
- **「原文逐字复制」承诺与上游渲染信息量不匹配。** 同一 HTML 对应多种作者原文时，靠 DOM 结构猜来源不可靠。更稳的做法是使用上游自带的元数据，或收窄承诺。这一点已推断为新经验。
- **「成功」反馈与实际内容脱节。** 按钮显示「已复制」，实际少一个字符。只看按钮文字不能证明复制正确，必须读回剪贴板完整字符串。本 PR 的测试已经这么做，缺的是边界输入。
- **边界输入应一次录全。** 第 1 轮修复只补了 6 个样例，漏了「手写 `<pre><code>`」。第 2 轮把能想到的结尾情形一次录全。
- **耗时与成本。** 评论里有各 agent 的耗时和 token 数据，但这里没有把它们汇总归因，主要耗时来源无法量化。

## 最佳实践（有适用条件）
- 处理由渲染产物反推原文的功能时，如果不同来源会渲染成相同输出，优先用上游提供的原始信息；没有就收窄承诺并写明限制。验证方法：把「渲染结果相同的两种输入」都录成回归样例，读回真实剪贴板。
- 默认关闭的跨渲染偏好（换行开关）用全局单一开关，存入视图设置，比逐块状态简单。适用条件是该偏好属于个人阅读习惯。这不是唯一正确的架构。
- 隔离 iframe 内复制：先「选中 + 复制命令」，失败再用剪贴板接口，都失败则显示「复制失败」并保留选中。这是本次实测可行的一种做法，不是通用结论。
- 不引入高亮库，只复用 GitHub 已渲染的高亮标记并补配色表。适用条件是内容来源已带标记。代价是没写语言的代码块保持单色。
- 样式函数只保留一份，由讨论区和回复预览共用，并用同一份输入对拍。这做到了 L3 的要求，没有违规。
