## 经验教训
1. 「先检查、后动作」的条件必须在持锁之后检查，而且互斥范围要覆盖「检查 → 读配置 → 建目录 → 取项目锁」整段。只加一次存在性检查不够（第 1、2 轮）。
2. 切换调度任务时，先启新任务、确认后再停旧任务。故障注入测试要覆盖启用失败、启动失败、停用失败。
3. 重复运行的入口（如安装脚本）不能把已有状态当成首次安装重新初始化。这个问题在迁移前就存在，新流程把它暴露出来。
4. 有多个实现或调用点时，每个调用点都要单独做负对照。复审第 1 轮指出只做了一侧。
5. 推断（未实测）：复审用受控交错复现并发问题，比单纯读代码更有效。第 3 轮说明原复现不再复现，这是复审自述。

## 最佳实践（有适用条件）
- 适用于多进程共享状态、带恢复语义的迁移或切换。先列出所有能在中途触碰该状态的入口（轮询、安装、周报、迁移自身）并一次收口。worker 在第 2 轮修复评论里这样做了，复审也认可。验证方法：对上一版代码跑同一套真实子进程测试，应能复现失败。
- 测试断言文件内容、目录是否存在、主轮询是否运行，而不是匹配源码文本。第 2 轮 worker 删掉了一条源码文本断言，改成放锁行为探测。
- 交人评论把「实测 / 未验证 / 合并后待办」分栏写明。适用边界：本例是纯后台 shell 脚本，使用假 systemd，结论不外推到别的架构。
