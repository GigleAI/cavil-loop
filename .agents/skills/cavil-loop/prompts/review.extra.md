## 交人评论怎么写（给人看的，不是交差报告）

review 评论同样是给人看的（下一轮的 agent 只是顺带读者），而且人常常是在手机上的 GitHub app 里看。写完先自问一句：
**人扫一眼能不能知道「发生了什么」和「要不要人动手」**——答不上来就重写。

1. **开头一行 `##` 标题**，一句话说清本轮是什么事：「已修复 review 指出的 3 条」
   「方案改走 B：不再自动接管旧安装」。别让人从第一句开始猜。
2. **结论先行**。标题之后第一段直接给判断：哪条属实、哪条是真 bug、有没有要人做的事。
   结论埋在第五段等于没写。
3. **一条一节**。多条问题 / 多个改动用 `###` 加序号分开，一节只讲一件事。
   一段里塞三件事，人就只能逐字读完才敢往下翻。
4. **对拍用表格**。前 / 后、期望 / 实得、「退回旧实现会怎样」——表格一眼能比，
   同样的内容写成句子就得在脑子里对齐。
5. **分清实测与推理**。每个数字标明怎么来的（实测 / 负对照 / 推算）；没跑过就写没跑过，
   别用「已验证」盖过去。
6. **写明「要人做什么」**。需要拍板的放主文、给 checkbox；本轮不需要人动手的，
   就直说「本条不需要人做任何事」——这一句能省掉一次来回。
7. **外面只放要人看的，其余折叠**。折叠区外只放：一句话说明发生了什么、结论是什么，本轮问题的回答，要人拍板或注意的事（失败、限制、风险、待办）。设计细节、取舍过程、历史轮次、测试证据、长命令输出、逐条日志各自放进本条评论里的 `<details><summary>…</summary>` 折叠块（`<summary>` 后空一行，否则里面的 markdown 不渲染）。判据是内容性质不是长度：证明你想清楚了的过程，折叠；人不看就可能拍错板的，留在外面。
8. **自包含，链接只当出处**。维护者只读交给人的这一条，不翻 worker 和复审之间的来回。凡是要人读、要人照着做、要人拍板的内容都直接写进这条：要人动手的步骤按顺序写全文（在哪个页面点什么 / 跑哪条命令 / 看到什么算成功 / 出错怎么退回）；之前几轮（包括复审阶段）得出的结论、限制、待办、测试结果整理进这一条（要人处理的放折叠区外，测试证据和过程放本条的折叠块），复审写交人评论时把 worker 的要点搬过来。文档、上一条评论、复审评论的链接可以附在旁边当出处，不能代替内容——不许写「见上一条」「照文档做」「见 reviewer 那条」「见 worker 上一条」。发出前再问一句：**只读这一条评论、不点任何链接，能不能知道发生了什么、要做哪几步？** 不能就重写。
9. **❌ / ✅ / ⚠️ 默认不标，只标要人看的那几条**。标识是例外，不是每节、每条都配一个：只标在需要标的那一条开头，一处一个；不需要标的就不标，正文叙述里也不乱撒。❌ = 有问题（打回的点、测试红、做不到或被拦住的项）。⚠️ 只标两类事：要人采取行动的事（拍板、动手、确认），或无需动手、但人需要知道且会影响其判断的真实风险 / 限制 / 未验证范围；两类都不是的不标 ⚠️——「本项目暂无硬规则」「本次不需要新测试」「某项不适用」这类没有事项的说明不标，也不为它们单开一节「需要人注意」。✅ 只标本该做、做了、而且人得知道它做对了的事（跑过的测试、新旧实现对拍、负对照变红、复审要求的修复已复核）；普通描述、计划、分析结论、不适用的项不标 ✅，没跑过、没核对的一律不标 ✅。复审结论标题以 ✅ / ❌ 开头是另一条专门约定，不受「默认不标」影响。
10. **写明是人还是 agent，不用「你」「我」**。一条评论可能出自 worker agent、复审 agent 或 daemon，读者是人，同一个条目里 agent 之间也互相留言：写「我」分不清是哪一方，写「你」分不清是对人说还是对 agent 说。评论和 PR 正文里不用第一、二人称（「你」「我」「我们」，英文 you / I / we），指人时也不用「他」「她」：人这一方写「人」（要更具体时写「维护者」「提出者」），agent 这一方写「agent」（要区分时写「worker agent」「复审 agent」），daemon 发的写「daemon」。引用人的原话、代码和命令输出照原样保留，不算违规。

### 评论里有要人拍板的问题时：固定骨架

只要这条评论里有要人拍板的问题（勾选题、「要不要这样改」），就按这个顺序写，上面各条照样适用：

1. **标题直说两件事**：这个改动做了什么、要人选什么。例：「## 多认出 4 种编号写法；要人选：中文编号要不要也算」
2. **先用一个真实例子讲清以前怎样、现在怎样**：拿一条真实输入，说改之前系统怎么处理、改之后怎么处理。没有例子的抽象描述，人读不出差别
3. **一张前后对比小表**：最多三四行，每行一个普通人在意的结果（多做到了什么、原来能做到的有没有变坏、有没有出错）
4. **「要人选的只有一件事」**：一句话说清问题，再各用一句话写「现在是怎样」「实测影响多大」（没实测就写推算 / 未测）。不止一件就写「要人选的有 N 件事」，每件一行，完整题目放在后面
5. **选项**：按拍板问题的格式写——选了之后 worker 会做什么、好处、代价，再加一句「不勾会怎样」
6. **过程细节全部折叠**：验证命令、日志、测试数字放进 `<details>`，不放主文

设计方案有固定的几段（功能范围、影响面、验收标准……）：第 1–4 步放在方案最前面，固定的几段接在后面，完整题目放进「待澄清问题」。

**问题标题和选项里不许出现代码里的名字**：变量名 / 函数名 / 参数名 / 文件名、内部概念名（只在代码和讨论里这么叫的模块代号、口径名、组件名）、测试编号、复盘经验编号（L3 这种）。不得已要提，就在同一句里用一句白话解释它是什么；人在 GitHub 页面上直接看得到、要亲手操作的东西（标签名、PR 编号）不算——拍板问题的规则里也有这一条，两处是同一条。

**发出前自查**：把这条评论只读标题、第一段和选项，一个不熟代码的人能不能做出选择？不能就重写。

反面（读不懂的那版，别照着写）：标题和第一段就是代码里的内部名字（某某探针、某某口径、复算器、硬规则编号）；结论夹在一大段验证细节中间，读完不知道要选什么；选项写成「放开含 CJK 的 ordered 兜底」这种只有写代码的人看得懂的话。

反面样本（`GigleAI/cavil-loop#26` 的实况，别照着写）：没有标题、开头就是三条 bullet、
每条一整段密排叙述、证据混在句子里、读到最后也不知道要不要动手。

## 负对照（本项目的测试约定，GitHub#103）

负对照 = 把被测代码复制一份、故意改坏一处（或换成旧提交），确认测试会变红。它只在每周自动发版时跑（GitHub#195）：发版前把 shell 测试和客户端的全部负对照跑一遍，有红就不发版。其余时候——worker 本机、复审本机、PR 和主干的 CI——一律不自动跑。Mac 打包只在推到 `main`、客户端发版标签和手动触发时做，PR 上不做。

- 复审不跑负对照，也不要求 worker 跑；不因 PR 里没有负对照结果或 Mac 打包结果打回。PR 的测试证据是默认回归（命令 + 通过 / 失败数）
- PR 里新写或改过的负对照合并前不会被跑过：交付评论里要写明这一点（下次每周发版时第一次跑），复审只核对它们挂在开关下、改的原文确实存在于被测文件里，不要求变红的结果
- 哪类代码要新写负对照（GitHub#178）：出错时不报错、只是悄悄给出错误结果的地方——计数、去重、金额；往 GitHub 写东西（评论、标签、合并）；凭据和权限；删数据或改登记；区分「读不到」和「没有」的判断；同一条规则写在多处（多份 prompt 模板、多个调用点）。这几类缺负对照，打回。纯展示（通知文案、提示条、设置页、配色和布局）只要求普通测试，不因缺负对照打回
- 新加的负对照必须挂在开关下（每一项经 `tests/lib/mutation.sh` 的 `mutation_gate`）；默认模式下也会跑的负对照，打回
- 默认回归里只靠「没发生」撑着的断言（调用 0 次、状态没变、零写请求），旁边要有一条「确实发生了」的断言（派工数 > 0、确实收到那条写请求、确实走到了被测那一步）；缺了打回
