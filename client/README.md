# Cavil Loop 客户端

`client/` 是一个本地桌面客户端（Tauri：界面 TypeScript + React，后台 Rust），把多个 GitHub Project 看板和仓库合进一个视图。它只和 `api.github.com` / `github.com` 通信（例外四处：头像图片从 GitHub 的头像地址 `avatars.githubusercontent.com` 加载，#155；讨论里的图片从 GitHub 自己的附件地址和图片代理加载，GitHub#205，以及仓库文件地址 `raw.githubusercontent.com`，GitHub#267；自动更新下载更新包时跟着 GitHub 的跳转到 `release-assets.githubusercontent.com` / `objects.githubusercontent.com`，只有外壳的更新插件访问它们，窗口的 Content-Security-Policy 不放开，#184；讨论里引用的 Release 附件图（地址形如 `github.com/<owner>/<repo>/releases/download/<tag>/<文件>`）由后台取回：登录凭据只发给 `api.github.com` 查附件，图片文件从同样这两个地址下载、不带凭据，窗口的图片名单不放开，GitHub#395）。设置页可以检查、安装本机的 cavil-loop daemon，并从仓库列表把仓库接上它（#314 / #315）：这时客户端在本机代跑 daemon 自带的脚本（状态检查、`setup.sh --yes`、断开项目、换新 Mac 后台任务配置、读 / 改项目常用配置项，#388）和固定的 `git` / `systemctl` / `launchctl` 命令，并读 daemon 的项目登记和项目配置里的 agent。窗口只能发几种固定请求，命令全在 Rust 后台执行、参数逐个校验（仓库名、agent 必须是 daemon 自带的、目录必须是 origin 指向所选仓库的 git 仓库）；子进程的环境按白名单给，客户端自己的 GitHub 凭据不交给这些脚本，daemon 用 `gh` 自己的登录；为此碰到的网络只有从 github.com 克隆 / 拉取 daemon 和要接上的仓库（`setup.sh` 建标签时经 `gh` 访问 GitHub）。设计与拆分见 GigleAI/cavil-loop#135，本目录的第一块是 #136（骨架），#138 加上了查看与修改，#137 加上了搜索筛选与表格视图，#151 把外壳从 Electron 换成 Tauri（安装包从 134 / 139.5 MB 降下来），并把 GitHub 凭据整段收进 Rust 后台，#155 加上了头像、详情折叠与浮动、PR 跟在关联 issue 下面、⌘+ / ⌘- 缩放。#214 在表格每个分组底部加了「＋ 新建 issue」：创建时只按这一组算出的清单（迭代 / 状态 / 里程碑）写，写前现读核对里程碑，对不上一条都不写。#304 让仓库顺序可以拖动：表格左侧的仓库列表、看板的泳道标题都能拖，表格分区、按仓库分组、新建 issue 的仓库列表跟着同一份顺序（`shared/repoOrder.ts`）；顺序只存在本机，不进视图设置，导入网页视图不会动它。搜索藏掉一部分仓库时拖动，只重排看得见的那几个仓库的位置，看不见的留在原位；看得见的全部记住，看不见的最多记 500 个。#398 在显示仓库的三处——看板的泳道标题、表格的仓库分段标题、表格左侧的仓库列表——各加了一个「在 GitHub 打开这个仓库」的图标按钮，点它在系统浏览器打开 `https://github.com/<组织>/<仓库>`；原来的收起 / 筛选 / 拖动不变（按钮和它们并排，不套在里面）。左侧列表里的按钮只在鼠标移到那一行或键盘焦点落在那一行时显示。地址只在 `src/shared/repoWeb.ts` 一处拼，按钮是 `src/renderer/RepoWebLink.tsx` 一个组件。#405 把新建 issue 窗口里的标签、里程碑、迭代收进看板勾选框下面同一个折叠块，每次打开都收起；收起那一行写明三项的值，迭代 / 里程碑的文字和展开后下拉框选中项由同一组函数生成（`src/data/newIssueFields.ts`，「当前迭代」用的名单也只在那里算一次），收起时三个控件不渲染、值留在窗口自己的状态里。

## 第一次用：从安装到接上第一个仓库

只要一个 GitHub 仓库，不需要 GitHub Project。全程在 macOS 上。

1. **先装 daemon 要用的程序**（客户端只检查缺什么，不替人装）：`git`、`gh`、`tmux`、`jq`、`flock`、4 以上的 `bash`（macOS 自带的是 3.2），以及要用的 agent 程序（如 `claude`）。用 Homebrew：`brew install gh tmux jq flock bash`。然后在终端里跑一次 `gh auth login`——daemon 用 `gh` 的登录，不用客户端的。
2. **下载客户端**：打开本仓库的 [Releases](https://github.com/GigleAI/cavil-loop/releases) 页，找标签以 `client/v` 开头的最新一条，下载里面的 `.dmg`。目前只有开发版（标签 `client/vX.Y.Z-dev.N`，标着 Pre-release，只有 Apple 芯片的包）；还没有正式版，Intel 的 Mac 暂时没有安装包（要用只能照下面「开发」自己构建）。
3. **安装**：打开 dmg，把 App 拖进「应用程序」；第一次打开照 dmg 窗口里写的办法做。
4. **登录**：打开 App，点「用 GitHub 登录」，在浏览器里输入 App 显示的短码并同意授权。
5. **添加仓库**：设置 →「数据来源」，填 `owner/repo`（或仓库网址）。这时看板上已经能看到这个仓库开着的 issue / PR。
6. **安装 daemon**：设置 →「本机 daemon」→「安装」。它从 github.com 克隆 GigleAI/cavil-loop 到 `~/.agents/skills/cavil-loop`，并给 Claude Code 建同名软链；下面的检查清单列出还缺哪些程序，装好后点「重新检查」。
7. **把仓库接上 daemon**：回到「数据来源」，在仓库那一行点「接上 daemon」：选本机已有的同仓库目录或让它克隆一份、选 agent；预检通过后点「开始」，它代跑 daemon 自带的 `setup.sh --yes`（建项目配置、在仓库里建 `pending/agent` 等标签、登记并启动后台轮询），输出边跑边显示。
8. **派第一个活**：在看板上新建一个 issue（按 `C`），给它加标签 `pending/agent`。daemon 在下一轮轮询（约一分钟）接走，标签变成 `doing/agent`；做完后翻成 `pending/human`，客户端发系统通知。

**只加仓库、不加 Project 时**：迭代和状态这两个值存在 Project 里，仓库本身没有。默认的「按迭代分列」下，所有卡片都在「未加入看板」一列；想要有区分度，在视图设置里改成按里程碑分列，或切到表格视图按仓库 / 里程碑分组（仓库没建里程碑时，按里程碑也只有一组）。以后建了 Project，再在「数据来源」里把它加进来即可。

这样装的 daemon 是一份普通的代码目录，不会自己更新：要更新时在设置 →「本机 daemon」里点「更新 daemon」。

**改一个项目的常用设置**（#388）：设置 →「本机 daemon」→ 那个项目的「配置…」，弹出一张表单——用哪个 agent、哪个模型、同时最多几个 worker、各种重试次数和轮数、评论语言、几个开关。改过的行标黄并写着原来的值，填得不对的标红、不能保存；点「保存」后列出每项的原值和新值，以及保存前那份配置文件的备份位置。daemon 下一轮轮询（约 1 分钟内）按新值工作，已经在跑的 worker 不受影响。派工模式、复审关卡、托管、等前置这四项只显示现在的值；命令、钩子、令牌、目录不在表单里——这些仍然用弹窗左下角的「用编辑器打开配置文件」去改。配置文件里写成算式、引用了变量的项也只显示。**保存时不要同时在编辑器里改同一个文件**：弹窗开着时文件被别处改过，保存会整个放弃并提示重新读取；但两边真的同时存盘时，其中一边的修改可能丢失，客户端发现不了也找不回来（备份里只有保存前的那一版）。daemon 太旧、没有读写配置的脚本时，「配置…」和从前一样直接用编辑器打开。

## 开发

要装 Rust（`rustup`）。单元测试和界面测试会先 `cargo build -p cavil-harness`，把真实后台当子进程驱动。

```bash
cd client
npm ci
npm run test:rust              # Rust 单元测试（后台 + 外壳；先构建一次界面，外壳编译要用）
npm test                       # 单元测试（真实后台子进程），末尾打印「负对照：跳过 N 项」
npm run test:mutation -- --changed  # 负对照（MUTATION=1），只跑和本次改动相关的项（只在手动时跑；CI 只在每周发版门禁里跑全部）：基线约 30 秒，之后每项几秒到十几秒（只跑它点名的测试所在文件）
npm run test:mutation          # 全部负对照（很慢，每周发版门禁里自动跑，或手动跑）：先跑未改动的基线，再逐项改坏一处（含 Rust 后台），指定的断言必须失败
                               # 不再新增负对照（GitHub#234）：改动用普通测试覆盖；清单里已有的条目只在被改坏的代码变了时改指向新代码
npm run typecheck
npm run test:e2e               # 界面测试（WebKit；WebKit 起不来的机器加 CAVIL_E2E_ENGINE=chromium）
npm run test:tauri             # 真实 App（Linux：要 tauri-driver、WebKitWebDriver，CI 用 xvfb-run；约 6 分钟，同步节拍是正式的 60 秒）
npm start                      # tauri dev：本机跑起来（Linux 要装 libwebkit2gtk-4.1-dev；凭据只在内存里，退出即忘）
npm run dist:mac               # Mac 上：打 .app 和 dmg（要 dmgbuild：pip install dmgbuild）
```

## 规则（改代码前读）

- **GitHub 是唯一数据源**：缓存只从 GitHub 往下写。一个来源要么整个读成功、整条覆盖本地，要么沿用上一轮——任何一页失败都不能把半份结果写进去，否则「读失败」会看起来像「条目消失」。GitHub#229 的「先显示的修改」不进这份缓存：它们另存一行（见下文「修改先显示」），只叠在界面上；看板数据仍只装 GitHub 读回来的值。
- **缓存只属于一个账号**：退出登录清空缓存（GitHub#229：没确认的修改和它同一步删掉；本次运行记住的详情、标签 / 里程碑列表、新建 issue 的结果条也一起清空）；启动时凭据和上次读缓存用的不是同一把（只比对哈希），在 GitHub 确认账号前一律不显示旧缓存；一轮同步发出后有人退出 / 换账号，这一轮整个作废；来源在同步途中被删除（或删了又加）时，这一轮对它的结果不写入。
- **登录要么完整成功，要么什么都不留**：凭据只在登录最后一步写入，所有写入 / 删除在一条队列里依次执行；写完立刻核对这次登录是否已被取消、退出或被更新的登录取代，是就在同一步里删掉，不会误删排在后面的新凭据。
- **去重按条目本身**（`仓库#编号`），不按来源。迭代、状态属于各个 Project：两个 Project 值不同，同一条目在两列各出现一次；里程碑属于仓库。
- **凭据只在 Rust 后台**（#151）：登录、续期、凭据写入队列、可信名单、退出全在 `src-tauri/crates/core`，只有这一份实现。窗口里的应用逻辑只拿到「未登录 / 等待授权（短码、网址）/ 已登录（账号、会话编号）」，要发 GitHub 请求就交给后台代发——后台加上凭据，只放行 `api.github.com`（地址按解析结果比，不按前缀），窗口自己带的 `Authorization` 头被丢掉，会话结束后一律拒绝。描述凭据的几项设置（可信名单、缓存绑定的凭据、缓存所属账号、登录时的 Client ID）窗口既读不到也写不了。`test/unit/backend-boundary.test.ts` 把一次完整的登录、同步、修改、续期、退出里所有跨过边界的命令和回答扫一遍，里面不许出现任何令牌。钥匙串写入走 `security -i` 的标准输入，不进命令行参数（和 Electron 版同一个钥匙串条目，升级不用重新登录）。
- **连接断了只重发读请求**（GitHub#364，`src-tauri/crates/core/src/http.rs` 的 `send_with`，后台所有发往 GitHub 的请求——同步、详情、修改、登录、检查更新——都走这一处，规则只有一份）：后台整个进程共用一个连接池，同一轮同步里的请求复用已经建好的连接（GitHub 一侧空闲约 20–55 秒就关连接，所以跨轮仍要重新握手）。一条连接断了时按「断在哪一步」决定：① 新连接没建起来（域名解析、TCP 连接、TLS 握手失败，请求一个字节都没写出）→ 任何请求都重试；② 请求已写出、没收到应答头，或 ③ 应答头已到、正文没读完 → 只有读请求整次重发（`GET` / `HEAD`，以及发往 GraphQL、文档里只有查询的 `POST`；判断不出的一律当修改），修改请求不重发——GitHub 可能已经执行了，照旧报「连接中断」由人核对；④ 应答完整收到，不管状态码是多少都原样交回。① 只认解析器和连接器自己在失败时留下的记号（ureq 先解析域名、再从池里取或新建连接，所以解析失败一定没发出），不看错误类型或文字——域名解析暂时失败和发出后被重置报出来都是 `Io`；池里拿到的旧连接出错一律按 ②③ 算，因为证明不了请求没写出。最多发 5 次（间隔 0.2 / 0.5 / 1 / 2 秒），所有尝试和等待合计不超过 30 秒：每次尝试只拿剩下的时间，剩下的时间不够再等一个间隔就停；重试过还失败时错误文字末尾带「（已自动重试 N 次）」，N 是实际次数。测试：`http.rs` 里对着本机真实套接字逐种情况数服务端收到的连接和请求，`test/unit/connection-retry.test.ts` 让真实后台子进程对着假 GitHub 跑同步、发 `src/data/queries.ts` 里的每一份 GraphQL 文档，假 GitHub 的 `breakAnswer` 把应答在开头掐断或在正文中途截断。
- **测试模式**（`CAVIL_CLIENT_TEST_MODE=1`）只给自动测试用：可以把 GitHub 地址换成本机回环地址的假服务，换成别的主机会直接报错（判断在 `src-tauri/crates/core/src/platform.rs` 的 `select`）。
- 只和 `github.com` 通信（图片例外：头像 `avatars.githubusercontent.com` 和下文「图片只从 GitHub 的地址加载」列出的 GitHub 图片地址，只用来加载图片，不带凭据）；外链一律用系统浏览器打开，且只放行 GitHub 的地址。

### 查看与修改（#138）

- **修改直接发给 GitHub，成功后立即重读那一条**：只替换缓存里那一条（所在的每个来源各一份，同样受「退出 / 换账号 / 来源被删」的保护）；同步正在进行时再补一轮。重读失败不影响修改本身，界面会说明，下一轮同步补上。离线时所有修改入口变灰，不排队、不重试。
- **修改先显示**（GitHub#229，规则全在 `src/data/edits.ts`，controller 只负责存、发、喂读取结果）：标签单个增删、里程碑、看板状态、看板迭代这四种，点下去就显示新值，详情、看板卡片、表格一致（`getBoardData` 一处叠加），界面不再等 GitHub、不再整页变灰；同一条的修改按点的顺序一个接一个发，不同条之间互不等待。合并、关闭、交给 agent / 托管（见下文「关闭 / 合并 / 托管 / 交给 agent 不卡对话框」）、评论、改正文、新建 issue 不在此列。
  - **一个字段一条记录**：目标值、点之前的值、所有结局没定的请求；整条记录存在快照表的 `__edits__` 一行里（`EDITS_KEY`），和缓存同受会话检查、同一事务清空。先存成功再发；存不上就不发，并说「没能存到本机，这次修改没发出」。请求状态先存成「已发出」再真的发，所以发出前后被杀，重开后都读作「没确认」，不会当成「没发过」。重开 App 不会自动发出任何修改。
  - **确认时刻 C**：收到「已接受」= C；或者一次在目标请求发出之后才发出、读到的正是目标值的读取——仅当目标值和点之前的值、其他请求的值都不同（GitHub 上原本不可能有它）——也算 C。之后只有 C 之后才发出的、真的写进看板数据、带着这个字段的读取才算数：读到目标值 → 核对完（还有值不同的没答复旧请求时，观察到最晚那个发出后 2 分钟，期间重读两次）；读到旧请求的值 → 「没保存上，可能被它改回去了」；读到别的值 → 有人在之后改过，以 GitHub 为准。C 之前发出的读取一律不算。详情读取不算（它不带里程碑和看板字段，也不写看板数据）。
  - **晚回来的旧读取不落地**（PR #240 复审第 5 轮）：每次读取（整轮同步、单条重读）都记下发出时刻；看板数据按「来源 + 条目」记住已落地的最新一次读取。比它更早发出的单条重读晚回来时，不写进那个来源（内存、磁盘都不写）；整轮同步落地时，开始之后才重读过的条目保留那次重读的副本。所有落地在同一条写入队列里依次算、依次写：每次都在前一次写完、内存更新之后，按那时的内存算要写的行，所以后写的不会把先写的盖掉。重读仍然不占这一条的修改队列。
  - **凭 GitHub 的值做决定只认已落地的读取**（PR #240 方案修订 1）：读取时间只在本机写成功、账号没换、来源还在之后，和内存里的行一起提交；写盘失败、账号切换、来源被删的那次读取不留任何痕迹，不算证据。修改的核对、观察期收尾、重新发送前的检查、「读不到 GitHub」的显示，都通过同一个取值入口（`evidence`）从看板数据里取这一条的值，只认发出时间不早于这次检查的读取；单条读取的原始答复不交给任何调用者。有足够新的证据就按它判断（检查本身晚回来或失败也一样），没有就按「读不到」拦下重新发送。例外：这一条不在任何来源里时，用这次读取自己的标签、里程碑（看板字段不走例外）。
  - **GitHub 拒绝（4xx / GraphQL 报错）**→「没保存上」；**没收到明确答复（断线、超时、5xx、408 / 429）**→「没确认」。两种都保留新值、并排显示「GitHub 现在」的值和读到的时间，可「重新发送」或「放弃」。重新发送先读 GitHub：仍是点之前的值（或已经是目标值）才发；有人改过、或读不到，就拦下，要再点「仍然覆盖 / 仍然发送」（维护者在 #229 选的 A）。读和写之间的空档、观察期 2 分钟之后才执行的旧请求，都拦不住，写在 #229 的限制里。
- **新建 issue 不卡对话框**（GitHub#229）：发不出去的（离线、标题空）当场拒绝、对话框留着；其余点「创建」就关，结果显示在看板上方。① 全部成功：自动打开新 issue；② GitHub 回了编号但没加进看板 / 字段没设上：只给「打开 #N」「再试加入看板」（只对这个编号补，不再新建）；③ 没收到明确答复：一直算「不确定」，列出最近 10 分钟这个账号在这个仓库建的同标题 issue（只是链接），可复制草稿，不给带「创建」按钮的草稿，也不对任何候选补写；④ GitHub 明确拒绝：给「重新打开草稿」，原样填回。
- **关闭 / 合并 / 托管 / 交给 agent 不卡对话框**（GitHub#250，判断全在 `src/shared/ops.ts` 一处，发送入口、按钮、面板和看板上方的结果条都用它；controller 只负责存、发、重读、查证据）：点「确认」（交给 agent 没有确认框，点按钮即发）后对话框立刻关，结果条先写「正在关闭 issue #N…」，GitHub 一应答就更新；应答之后的重读在后台做，不再挡对话框。每次操作是一条记录，跟缓存存在一起（同一个账号、退出登录一起删，重启还在），面板关了再开、换条目再回来看到的是同一条。
  - **每一步分开记**：关闭 = 关 + 附带评论；合并 = 合；托管 = 加托管标签 + 加 `pending/agent` + 摘 `pending/human`；交给 agent = 后两步。每一步只有「等应答 / 成功 / 被拒（GitHub 明确拒绝）/ 不确定（断线、超时、5xx 等，没收到明确答复）/ 没发」五种，前一步不是成功后面一律不发；结果条逐步写清，不把部分成功说成全没做，也不把「不确定」说成「没发出去」。
  - **一条规则管防重复**：同一条上这五种操作互相冲突。只要这一条还有一次操作没结清，从哪里都发不出去（后台在发送入口拒绝，面板按钮变灰并写原因；回复、改标签 / 里程碑 / 看板字段不受影响）。结清只有三种：每一步都有确定结果、且有成功的步骤时等到一次应答之后发出并已落进缓存的重读（关闭 / 合并还要读到「已关闭 / 已合并」，超过 2 分钟没读到就给「去 GitHub 页面核对」「已核对，解除锁定」）；不确定的步骤被正面证据证实；人点「已核对，解除锁定」（只解本机的锁，不发任何请求）。任何一步不确定，整条就一直锁着；客户端自己从不把不确定的步骤再发一遍（人知情后重发见下文 GitHub#359）。
  - **证据只认正面的，而且必须是这次的**：第一个请求发出前先读一次这一条最新的 100 条评论和 100 条标签记录，记下已有的；之后查证只认这份名单里没有的记录（PR #255 代码复审第 1 轮：一分钟前同内容的旧评论、旧的「加派工标签」记录都不能证明这一次）。关闭 / 合并看应答之后（重启前没收到应答的，看发出之后）的重读是否已关闭 / 已合并；附带评论看有没有本账号发的、内容完全相同的新评论；加标签看有没有本账号加这个标签的新记录，或发出之后的重读里这个标签已经在（GitHub#359；`pending/agent` 被 daemon 接手后会被摘掉，所以它「现在不在」什么都不说明）；摘标签看新记录或重读时已不在。发出前那次读取失败的，这一步永远不能自动证实，只能人核对后解锁。读不到、查不到都只算「仍不确定」，绝不算「没发生」。
  - **没收到应答时客户端自己核对、查到就自己做完；没查到仍是「不确定」，人知情后才重发**（GitHub#359，核对结论 `opCheckSteps`、发送许可 `opPermit`、确认框文字 `opResendConfirm` 都在 `ops.ts`，各只有一份）：
    - **自动核对**：有步骤没收到应答时立刻核对一次，之后隔 3 秒、10 秒、30 秒各一次（只读；这期间结果条是「进行中」样式、没有按钮），再之后每一轮连上了 GitHub 的同步各核对一次（`catchUpChecks`）。结果条上不再有「重新查证据」「去 GitHub 页面核对」。
    - **一次核对读什么**：这一条的开闭状态、当前标签、发起之后的标签记录，一次请求读回（`readItemSnapshot`）；标签记录往前翻页，读到发起前已见过的那一条或读到头才算读全；把新记录按顺序套到发起前的标签上，结果必须等于当前标签。读失败、没读全、对不上、发起前那次读取失败、旧版本留下的记录（没有发起前的标签）都算「没读到」。
    - **核对结论只有这几种，没有「确定没生效」**：有正面证据 → 这一步完成；没读到 → 仍不确定；读全了、目标状态没达到、这个标签发起之后没有任何记录 → 仍不确定，结果条写「到现在还没查到；原来那次请求仍可能稍后生效」；读全了但这个标签有别的记录 → 仍不确定，写「这期间这个标签被人动过」。后三种都继续锁着、继续核对。
    - **自动接着做**：托管 / 交给 agent 里不确定的那一步被证实后，同一次操作还没发过的后续步骤自动发出，不用再点「补做剩下的步骤」。每一步发出前都要过发送许可，判两次（决定时一次，发出前现读一次）：读全了；这一条还开着；这次操作已完成的每一步结果都还在；这次操作涉及的标签，发起之后的记录只能是已完成步骤各自对应的那一条——多出任何一条都算有人动过，不看是哪个账号（维护者在网页上的操作和客户端是同一个账号）；这一步的目标状态还没达到（已达到就记为完成、不发）；操作发起不到 10 分钟且客户端没重启过。不通过就停，结果条写原因；没读到时不写原因、下一轮同步再判。
    - **停下之后**：托管标签被摘掉、条目已关闭 →「重新托管…」；派工标签加上后又不在了（daemon 取走，或人撤回——客户端分不清，两种都停）、等人标签被动过、超过 10 分钟、重启过 →「补做剩下的步骤」。
    - **「仍要重发…」**：只在改标签的步骤、核对结论是「读全了没查到、没人动过」时出现。点开是确认框，写明上一次请求仍可能稍后生效、这一步重发的后果（托管标签：之后叫停时迟到的那次会把托管恢复；派工标签：可能派两次工；等人标签：agent 交回后可能又被摘掉）；确认后先再核对一次——查到已生效就不发、直接接着做；仍没查到才过发送许可（不受 10 分钟和重启限制）并发出，之后接着做剩下的步骤。客户端自己从不重发任何一步。关闭 / 合并 / 附带评论只自动核对，没有这个按钮。
  - **按钮**：首步被拒 →「重新关闭 / 合并 / 托管…」，对话框里原样还原；托管 / 交给 agent 主步成功、后面的标签步骤被拒 →「补做剩下的步骤」，先重读，只补被拒或因此没发的那几步（已就位的跳过；成功过或不确定的派工标签永远不补）；GitHub#359 起，自动接着做停下时（见上一条）也是这两个按钮。
  - **草稿另一条规则**：关闭原因、附带评论、合并方式各看自己那一步——那一步确认成功才自动删；被拒、没发、不确定都留着，直到用它重做成功或人点「丢掉草稿」。结清、解除锁定、关掉结果条都不删草稿（关掉后面板顶部留一行「点这里找回」）。评论被拒或没发可「放进回复框」，不确定只给「复制原文」，还在等应答时都不给。用「放进回复框」发出的回复带着是哪次操作的草稿，结果记在那次操作上、与面板还开不开无关：发出 = 草稿用掉；明确被拒 = 还能再放；没收到应答 = 不确定，只给「复制原文」，不会再放进回复框（PR #255 代码复审第 1 轮）。这条回复也算这次操作的一步（代码复审第 2 轮）：还在路上时整条算「进行中」、没收到应答时算「不确定」，都锁住这一条，也不给「重新关闭」；「正在发送」先存进本机，存不上就不发；查证同样只认发送前没有的评论；证实发出后只算评论用掉，关闭原因等其余草稿照留，之后「重新关闭」不会再带回这条评论。每次操作和这条回复都只属于开始时的那次登录（代码复审第 3 轮）：从头到尾用同一个绑定该次登录的连接（后台对已结束的登录一律拒绝），每次等待之后都重新核对登录和记录、存盘没成功就停；中途退出登录或换了账号，什么都不发，也不会用新账号代发。
  - **完全成功的提示 5 秒后自己收起**（GitHub#256，GitHub#279 起由 10 秒改为 5 秒；判断在 `ops.ts` 的 `opAutoDismissable` 一处，面板和看板上方共用）：只有已经结清（不是等应答、不确定、等重读、卡住待核对，也不是人工解除锁定的）、每一步都确认成功、关闭 / 合并已重读到结果、没有重读问题、没留草稿、没有在途或不确定的回复，才在显示满 5 秒后收起，效果等于点 ×（记录记为已收起，重启也不再出现）。不看语气和按钮：合并成功但关联 issue 没读到时只剩 ×，这条照样留着。鼠标停在上面、键盘焦点在里面、窗口不在前台或被隐藏时暂停，恢复后从头再数 5 秒；同一条从面板挪到看板上方（或反过来）也从头数。暂停先跟着「进入 / 离开」事件走，但事件会漏（窗口在后台时鼠标移开、获得焦点的按钮消失、窗口回到前台没收到通知），所以暂停期间每秒按真实状态再看一次（浏览器自己的悬停状态、焦点所在、`document.hasFocus()` 与是否隐藏），窗口退到后台时也忘掉「鼠标在上面」，漏掉一次事件不会让提示一直停着（GitHub#296）。「这次没能查证：…」只在还有步骤「不确定」时成立、也只在那时写在提示里；「卡住」只在等重读时成立。离开那个阶段（后来的读取或记录证实了、人工解除锁定）时两者都在 controller 唯一的写入口（`setOp` 经 `opWithoutStale`）清掉，同步读到、查证结束、读回上次运行留下的记录都一样——提示上看不出的问题不会挡住它收起（GitHub#296：GigleTutor-Web#1462 的托管提示因此挂了几个小时）。看板和详情里纯成功（绿色、不带「注意」）的结果条同样 5 秒后收起，带「注意」的和错误的不收。
  - **颜色只在一处定**（GitHub#357）：提示条的颜色不按「这是哪种提示」写死，而是每条提示说出四件事——自己的请求是否正在跑、是否全部完成、是否被拒绝或最近一次处理失败、App 是否在后台重试——由 `src/shared/noticeTone.ts` 的 `noticeTone` 按顺序判断：正在跑 → 蓝（转圈）；全部完成 → 绿（5 秒后收起）；失败 → 红；后台重试 → 黄；都不是 → 保持这条提示原来的颜色。操作提示的四件事由 `shared/ops.ts` 的 `opFacts` 给出，新建 issue 的提示由 `createFacts` 给出，没保存上的修改、结果条、读不到 daemon 的提示也都走同一个函数。「绿色」和「5 秒后自己收起」是同一个条件（`opFullyDone`），所以绿色提示不会留在屏幕上。「正在查证 / 正在补做 / 正在再试 / 正在重新发送」和「上一次为什么没成」都记在提示自己的数据上（操作记录、新建任务、`state.editsResending`），不放在被点的那个界面组件里：入口在第一次等待之前设上「进行中」并清掉上一次的失败原因，任何出口（成功、失败、不能开始、提示被关、换账号）都清掉「进行中」，所以同一条提示在看板上方和详情里颜色一致，也不会同时显示「进行中」和「上次失败」。GitHub#359 起，操作提示里「没收到应答」这一类：客户端自己那一轮核对（立刻一次 + 之后三次）进行期间算「正在跑」（蓝）；那一轮之后——不管是没读成（「这次没能查证」）还是读全了没查到——每轮同步都会再核对，算「后台重试」（黄），不再是红；每轮同步的那次核对是后台循环，不把提示变蓝。一条提示说到好几个看板时（新建 issue 的提示），失败记在各自的看板上：「再试加入看板」没处理好的看板带一个记号，「在某看板改成…」没成的原因记在那个看板上，整条提示的颜色从所有还在的部分汇总——只有再次处理那一个看板才会清掉它的失败，另一个看板处理成功不会把它盖掉（`createFailures`）。新建时就没加入、还没人点过再试的看板不带记号，保持黄色。「进行中」只在本次运行里有效，重启后不保留。后台的循环（离线重试、每轮同步补读、看板的定时留意和写入后核对）不算「自己的请求在跑」。没收到应答本身不算失败：查证确实跑过并且没查出来（提示写着「这次没能查证」）才是红色。
  - **重读失败的提示是黄色警示，下一轮同步补读后清掉**（GitHub#279）：每一步都成功、但操作后的重读（这一条，或合并 / 关闭 PR 时它关联的 issue）没读成时，提示说「修改已生效，但重读这一条失败（…），下一轮同步会更新」，语气是警示（黄色、警示图标，`opTone` 一处判断），不再显示成成功。之后每一轮连上了 GitHub 的同步——读到新数据，或确认来源「没有变化」的都算——在收尾时用同一个重读函数把还挂着这句话、没被收起的记录再读一次（`catchUpReads`）：读成了就去掉这句话，整条完全成功的照上一条 5 秒后收起；没读成就换成这次的原因，下一轮再试。「来源没有变化」本身不算读到了这一条，不清掉这句话。断网、登录失效、每个来源都没读成的轮次不补读。补读是「安静」的：读成功、读失败、读完以后都不再排同步，所以 GitHub 读不到时不会循环请求。说明随记录存在本地，重启后第一轮连上 GitHub 的同步就补读。等重读超过两分钟被标成「卡住」（提示核对、可手动解除锁定）的记录，之后一次算数的读取把它结清时，「卡住」随之解除，同样可以自己收起；读到的仍不是结果（例如关闭了却还读到打开）时照旧算卡住。
- **改完之后列表跟着动**（#177）：合并或关闭 PR 成功后，除了 PR 本身，缓存里和它关联的 issue 也立即重读——关联取两处的并集：GitHub 报的「这个 PR 会关掉的 issue」（翻页读完，没有条数上限），加上缓存里侧栏「关联 PR」列着它的 issue；只重读缓存里有的。这份清单没读全（某一页失败）时，已读到的照样重读，结果里写明「没读全」，不当成完整清单。另外，任何一次修改成功后（包括成功但带警告的）约 5 秒再自动同步一轮，连续改几下只补一轮（从最后一次算起）；被拒 / 失败的修改不补，退出登录时取消。这一轮是给 GitHub 自己在后台晚做的事（看板「关闭 / 合并 → Done」之类的自动化）准备的：5 秒只是同步的时间点，不保证 GitHub 那时已做完，没做完的照旧等 60 秒的定时同步。
- **标签只发「加这个 / 删这个」**（`POST …/labels {labels:[一个]}`、`DELETE …/labels/<名字>`），从不整份覆盖——整份覆盖会把别人刚加的标签冲掉（负对照守着）。
- **合并一定带上看到的提交**（`sha`）：期间被推了新提交，GitHub 回 409，界面说「请刷新」，什么都不合；合并方式只列仓库允许的，默认是这个仓库上次选的方式（没选过就用最近一次在任何仓库选的；只记在本机，GitHub#175）；确认框只写一句「把哪个分支合进哪里、用什么方式」；不提供绕过分支保护的管理员合并。关闭 PR 先关、关成功才发附带的评论（结果怎么报、怎么防重复见上文 GitHub#250 一条）。
- **关闭 issue**（GitHub#180）：详情底部「发送」那一行左侧的「关闭 issue…」，只在详情现读到这个 issue 仍开着时出现（PR 的「关闭 PR…」在它上面一行，和 PR 状态图标、「合并…」放在一起，GitHub#260）。确认框里选关闭原因「已完成」（默认）或「不计划」，可附一句评论；发 `PATCH …/issues/<n> {state: closed, state_reason}`，关成功才发评论，评论没发出去只给警告、不再重发关闭（GitHub#250 起对话框不等结果，见上文）。原因只认这两个、条目必须是 issue，否则发送前拒绝。「重复」要指定重复的是哪一条、重新打开 issue / PR，都不在客户端里做，去网页。
- **里程碑**改的是这一条所在仓库里同名的那个；没有就拒绝并说明，什么都不发，不新建。
- **迭代 / 状态**只改那张卡所在 Project 的值，用那个 Project 自己的字段和选项 id；拖卡时卡上有两个 Project 就两个都改，其中一个没有目标迭代就整次拒绝。「未加入看板」的卡拖进迭代列先问「加入看板 X 并设为这个迭代？」。拖卡用的是页面自己的 HTML5 拖放；GitHub#295 起建窗口时关掉了 Tauri 自带的「拖文件进窗口」处理（默认开着，在 macOS 上它把每一次拖拽都当成自己处理了，页面收不到「拖过 / 放下」，卡片拎得起来放不下）。客户端没有任何功能用到拖入的文件，所以三个平台都关；拖进来的文件也不会让窗口跳去打开它（窗口不导航的规则挡住）。Mac 上没有自动检查覆盖这一点：界面测试跑在独立浏览器里、真 App 测试只在 Linux 上跑，而 Linux 的外壳本来就不拦拖拽，所以改回去也不会有测试变红，Mac 上拖卡要人手动试。GitHub 说这个账号不能改某个 Project（`viewerCanUpdate`）时，那个 Project 的入口变灰并说明，标签 / 里程碑照常可改。
- **详情的版式**（GitHub#260）：面板贴在「看板 / 表格」那一行下方（`BoardView.tsx` 的 `.below-bar`），看板上方的提示条、视图设置面板都在它下面那一块里、面板打开时让出面板的宽度（`--detail-space`，和看板为面板留的空位同一个值），所以提示条多少都不改变面板和讨论的位置。面板自己的提示不占行：纯成功的结果、完全成功的关闭 / 合并 / 托管 / 交给 agent 提示（`opAutoDismissable` 那一条规则）是标题栏里一行小字（后者带 ×），照旧 5 秒后收起、鼠标停在上面时暂停——它们会自己消失，所以从不藏进按钮里；带「注意」的和失败的结果、其余的关闭 / 合并 / 托管 / 交给 agent 提示（进行中、不确定、部分失败……）和草稿、没保存上 / 没确认的修改、有内容时的重读失败，都收进标题栏一个带数字的按钮（有在等应答的操作时转圈，有问题时红色），点开是浮层，里面就是原来那些提示和按钮；再点一下、点外面或 Esc 收起，新提示不会自己弹开。浮层关着时提示仍挂在页面上（只是藏起来），各自的计时和记录照旧。还什么都没读到时的读取失败仍直接显示在讨论的位置。标签 / 里程碑 / 看板字段由标题栏按钮整块收起或展开，存进视图设置（`detailFields`），按 L / M 时先展开再打开选择框。**回复框**（GitHub#322）：整张回复卡片都能点进输入——点 PR 状态那一行、发送那一行的空白处，光标就进回复框（按钮、下拉框、链接、可聚焦的图标照旧只做自己的事；拖选了卡片上的文字、回复框不能写——离线或正在发送——时不进）；光标在回复框里时整张卡片亮一圈边框。回复框至少约 4 行高，随文字长高到面板当前高度的 40%，再多就在框里滚动（窗口或面板大小变了就重算，缩小窗口后上限跟着变小）；只有真的拖过回复框右下角的，才以拖到的高度为下限；长单词换行，不出横向滚动条。空着时提示「按 R 随时跳到这里」。PR 的状态在回复框里、发送那一行上面：合并 / 冲突 / 检查 / 评审四个图标，颜色只在 `src/renderer/prStatus.ts` 一处判断，没列出的值（新值、还在计算）一律灰色「待定」，不会显示成绿色；鼠标停留（系统提示）和读屏读到的是原来那句话。
- **代码块**（GitHub#381）：讨论里的每个代码块，鼠标移上去或用键盘聚焦时右上角出现「换行」「复制」两个按钮（行内代码没有）。「复制」复制到的内容和 GitHub 网页上代码块自带的复制按钮相同：GitHub 的渲染结果在代码块外层带着它自己要复制的文字（`data-snippet-clipboard-copy-content`），它比显示出来的文字少末尾一个换行时就按它来，其余情况（没有这个属性，或它和显示的文字有别的出入）一律复制显示出来的全部文字，不按代码块的结构猜。所以：结束标记前留的空行会复制到；没写语言的代码块末尾不多带换行；手写的 `<pre><code>` 以换行结尾时，GitHub 把它渲染得和没写语言的代码块一模一样，那个换行复制不到（GitHub 网页上也一样）；手写的 `<pre>`（没有 `<code>`）GitHub 不给复制内容，原样全部复制，按钮显示「已复制 ✓」约 2 秒；两种写剪贴板的办法都被系统拒绝时显示「复制失败」，代码留在选中状态，按 ⌘C 即可。「换行」是全局一个开关，默认关（长行横向滚动）：在任一代码块上点，所有代码块一起切换，存进视图设置（`codeWrap`），重开客户端仍记得。语法高亮不带高亮库：写了语言的代码块 GitHub 的渲染结果里已带标记（`pl-*`），客户端只配上 GitHub 的浅色 / 深色两套颜色；没写语言的代码块 GitHub 不标，客户端也不猜。按钮和颜色在 `src/renderer/codeBlocks.ts`，讨论和回复预览共用同一份代码样式（预览没有按钮、不运行脚本）；按钮的点击由讨论框里唯一放行的那段脚本（`frameScript.ts`）处理——复制在框内完成，不经过窗口，窗口只收到「换行开或关」。改这段脚本要同步改它的校验值（`FRAME_SCRIPT_HASH`、`src-tauri/tauri.conf.json`、`test/mutation/mutations.mjs` 里引用它的三处），`test/unit/taskList.test.ts` 会核对。测试用的 GitHub 渲染结果由 `node test/fixtures/record-codeblocks.mjs` 录制，不手改。
- **详情**每次打开都从 GitHub 现读；GitHub#229 起本次运行读到的最近 50 条记在内存里（不写盘，退出登录清空），再次打开先显示上次的内容、标题下写「显示 HH:MM 读到的内容 · 正在更新…」，读回来再换；评论、评审、每个评审下的逐行评论全部分页读完（任何一页失败就整次报错，不显示半份讨论）；最新在上，正文最老所以在最下，逐行评论挂在所属评审下面。默认只展开最新一条（没有评论时就是正文），其余折成一行（作者、时间、开头约 80 字），点一下展开，面板上有「全部展开 / 全部收起」（#155；折叠用浏览器自带的 `<details>`）。GitHub 渲染好的 HTML 放在 `sandbox` 隔离框里（不同源、不能导航，有自己的 CSP），链接用系统浏览器打开。框里唯一能跑的是客户端自己的一段固定脚本（GitHub#193，`src/renderer/frameScript.ts`），见下一条。
- **开着的详情跟着同步更新**（GitHub#226，规则在 `src/renderer/autoRefresh.ts`）：不另设定时器，挂在看板的同步轮上（60 秒一轮、改完后 5 秒补的一轮）。一轮里装着这一条的来源（Project 或仓库）有一个完整读成功，而且读到的这一条「最后更新时间」和详情上次读取时看板上的不一样，就重读一次详情；只有别的来源成功、或这一条所在来源读失败（沿用旧数据），不算有新数据。打开中的 PR 若上次读到检查「进行中 / 等待中」或「能否合并」还没算出，每轮都重读，出结果就停——检查结果变化 GitHub 不算「这一条有更新」，所以检查结束后又被重新触发、而这一条本身没有别的变化时，不会自动发现，点「刷新这一条」。读回来的内容和屏上一样就不换（讨论区不重绘，选中的文字不丢）；回复草稿、编辑框、合并方式的手选、已展开的条目和滚动位置都不动。自动重读失败不弹错误条，屏上内容留着，下面一行小字「自动更新失败，显示的是 HH:MM 的内容」，下一轮再试。提交修改（合并、发评论、加标签、勾选择题……）一开始，所有还在路上的详情读取都作废（它们带的是改之前的 GitHub）；提交进行中到了同步轮不自动读；提交成功或失败后都立刻重读一次。
- **在详情里勾选择题**（GitHub#193）：正文和普通评论里的任务列表勾选框（`- [ ] A. …`）可以直接点，效果和在网页上勾一样——原文里那一个 `[ ]` 变成 `[x]`（或反过来），其他字节不动，然后重读详情（已展开的条目和滚动位置不变）。规则：
  - **只有能确定的才可点**：GitHub 说这个账号能改这一条（`viewerCanUpdate`），而且客户端按 GitHub 的 markdown 规则（`src/data/taskList.ts`，CommonMark + GFM 任务列表）从原文读出的框，和 GitHub 渲染出的框逐个一致（个数、勾没勾）；任何一项没读到或对不上，这条的框只读，下面写原因。评审意见和代码逐行评论里的框一律只读（去网页勾）。离线、有修改在途时全部变灰。
  - **写前现读**：GitHub 改评论没有「内容没变才写」，所以写之前按评论 / 正文的 id 现读一次：必须仍属于这一条、这个账号仍能改、原文和点的时候看到的一字不差，目标那个框正处在点之前的状态；任一不符就不写、重读、提示「刚被改过」。现读失败就报错，不拿旧原文写。现读和写入之间仍有空档（长度未测、给不出上限），这期间别人改了同一条会被覆盖——网页上勾选也一样。同一条评论一次只允许一个写入在途。写用 GraphQL `updateIssueComment` / `updateIssue` / `updatePullRequest`。
  - **框里的脚本**：时间线隔离框的 `sandbox` 有 `allow-scripts`、没有 `allow-same-origin`（碰不到窗口的对象、存储和后台通道），自己的 CSP 是 `connect-src 'none'`（发不出请求）。能跑的只有 `FRAME_SCRIPT` 这一段：它只把「哪条评论第几个框、勾没勾」和「哪些条目展开、滚到哪」用 `postMessage` 告诉窗口，变化的数据放在 `<body data-…>` 里，脚本本身是常量。`srcdoc` 框同时受窗口和自己两层 CSP 约束，所以两层都按内容哈希只放行它：窗口那层写在 `src-tauri/tauri.conf.json` 的 `script-src`，框那层由 `TIMELINE_CSP` 生成。改了脚本就要同时改 `FRAME_SCRIPT_HASH` 和配置里的哈希，`test/unit/taskList.test.ts` 核对三处一致。窗口只认来自当前这个框（`event.source`）、当前这次渲染编号的消息，而且自己再核一遍条目可点、序号在范围内。回复预览框不跑任何脚本。
  - **测试**：`test/fixtures/tasklists.github.json` 是 GitHub 自己对 18 种写法和两条真实评论的渲染（`node test/fixtures/record-tasklists.mjs` 重录，不手改），读框规则逐条和它对拍；`test/e2e/frame-policy.spec.ts` 两层策略各测各的（另一层在测试页里放宽），每组都要「框内脚本跑了」且「注入的脚本、事件属性一个没跑」；`test/tauri/real-window.spec.ts` 在真实 App、正式策略下真点一次，假 GitHub 恰好收到一次只差一个字符的修改，框里拿不到 IPC、发不出请求。
- **详情顶部的类型徽章**（#172，`src/renderer/KindBadge.tsx`）：issue 和 PR 靠图标形状（圆圈带点 / 分支）和全称（「Issue」/「Pull Request」）区分，底色是 GitHub 的状态色。类型、状态、关闭原因和草稿标记都取自看板里的这一条，打开就有；草稿标记优先用详情现读的（更新），详情还没读到或读取失败时用看板读到的，两处都不知道就不当草稿；只有仍开着的草稿 PR 变灰写「草稿」，已关闭、已合并优先。图标是内联 SVG，不加载任何外部资源。
- **状态配色跟 GitHub 一致**（PR #174 复审时维护者要求）：开着 = 绿；PR 关闭未合并 = 红；PR 已合并、issue 按「已完成」关闭（或没记关闭原因）= 紫；草稿 PR、issue 按「不计划 / 重复」关闭 = 灰（徽章文字补「（不计划）」「（重复）」）。哪种情况用哪种颜色只在 `src/shared/stateTone.ts` 一处判断，详情徽章、看板卡片、表格行都用它；色值是 GitHub 设计系统 Primer 的状态色（浅色 / 深色各一套，在 `styles.css` 的 `--state-*`）。关闭原因和草稿标记三条读取路径都读：Project（GraphQL `stateReason` / `isDraft`）、仓库列表（REST `state_reason` / `draft`）、改完后的单条重读，所以草稿 PR 在徽章、卡片、表格里都是灰色；徽章优先用详情现读的草稿标记（更新），详情没读到时用看板读到的。
- **同步中点刷新 = 重新开始**（GitHub#217，`restartSync` in `src/app/controller.ts`）：刷新按钮和 ⌘R 在同步中也能点，图标在转。正在读 GitHub 的这一轮被放弃——它读到的东西不进界面、不进缓存，也不再发下一页（已经发出的那一个请求由后台跑完、结果丢掉；后台没有取消单个请求的接口）——新一轮马上开始。正在续期登录或正在写缓存的那一段不打断（半路断开可能丢登录 / 让新旧两轮抢着写），做完马上重来。操作触发的同步（改完后的补读、新增来源等）仍是排队，不互相打断；定时节拍在同步进行中到来时不再排队（GitHub#324，见下一条）。详情的「刷新这一条」读取中也能点，新的读取作废旧的（同上一条的规则）。
- **定时同步不首尾相接**（GitHub#324，`timedSync` in `src/app/controller.ts`，外壳的节拍、窗口定时器和补跑闹钟都只走这一个函数）：以前一轮同步超过 60 秒（网络差、看板大）时，期间到来的节拍会排一轮紧接着跑，刷新按钮就一直转。现在：
  - 同步进行中到来的节拍**不排队**，只记下「这一段同步跨过了节拍」。
  - 跨过节拍的那一段同步结束（成功、失败、离线都算）后，定时同步最早在**结束满一个节拍（60 秒）**时开始：这之前到来的节拍只设一个闹钟到那一刻（最多一个，重复的不重设），闹钟响时按同样的规则再判一次。
  - 没跨过节拍的同步（一轮几秒的正常情况）之后不留间隔：下一拍到了就同步，节奏和以前一样，不依赖闹钟。
  - 操作触发的同步不受这个间隔限制，照旧立刻跑或排在当前一轮后面：改完后约 5 秒的补读、新增来源、登录后的首轮、重读失败后要的一轮、凭据失效触发的一轮；点刷新 / ⌘R 照旧立刻重来。它们一开始，等着的闹钟就取消，不会再多跑一轮。
  - 被「点刷新」放弃的旧轮迟到收尾时不碰这些状态；停止节拍、退出登录、换账号时闹钟取消，旧闹钟不会在新的登录里启动同步。电脑时钟被往回拨时，最多只多等一个节拍。
  - 限制：窗口隐藏时网页引擎会放慢窗口里的定时器，闹钟可能晚响；外壳的下一拍到来时已过了那一刻，会直接同步——所以慢轮之后最坏要等到下一拍（结束后不超过两个节拍）。正常快轮不用闹钟，#139 的「2 分钟内通知」不受影响。
  - 测试：`test/unit/timed-sync.test.ts`（真实控制器 + 真实后台 + 假 GitHub，时间由测试拨动；两个定时入口各跑同一组时间线）。
- **详情面板按「这一次打开」认回应**（`src/renderer/openSession.ts`，四种异步调用——读详情、读仓库候选、预览、修改——都走它）：每次打开一条（换到别的再回来、关掉再开都算新的一次）是一个新面板，上一次打开发出的回应一律不进新面板；同一次打开里，同类的新调用作废旧的（改完后的重读胜过慢的刷新，改了字后旧文字的预览不显示）。修改晚到时，结果显示在看板顶部（带编号），不动新面板的草稿、忙碌状态和对话框。负对照里有真实界面的项（`runner: 'e2e'`），`MUTATION=1` 时自动构建并驱动真实窗口（WebKit + 真实后台）。
- **图片只从 GitHub 的地址加载**：`github.com` / `api.github.com`、头像地址 `avatars.githubusercontent.com`（#155），以及 GitHub#205 维护者放开的 GitHub 自己的图片地址——附件 `private-user-images.githubusercontent.com`（GitHub 返回的正文里粘贴截图的地址，带有效期约 5 分钟的签名，不带凭据就能取）、2023 年以前的老附件 `user-images.githubusercontent.com`、图片代理 `camo.githubusercontent.com`（外链图片由 GitHub 代取）；以及 GitHub#267 维护者放开的仓库文件地址 `raw.githubusercontent.com`（提交进仓库的图片，例如没配公网出图地址时 agent 评论里的设计图；`github.com/<仓库>/raw/…` 的图片链接也会被 GitHub 跳转到这里，跳转目标同样要过页面策略——`test/e2e/image-redirect.spec.ts` 让浏览器经本机代理真实走一遍 302，不出本机。只有公开仓库的能显示，私有仓库的要凭据，客户端不带，仍会裂）。只按完整主机名放行，不放开 `*.githubusercontent.com`；名单在 `src/shared/avatar.ts` 一处，页面的 CSP（`src-tauri/tauri.conf.json`）由 `test/unit/detailHtml.test.ts` 逐项核对与它一致，「在浏览器里打开」的放行规则（`src-tauri/crates/core/src/engine.rs` 的 `GITHUB_IMAGE_HOSTS`，点图片打开原图）由 `test/unit/github.test.ts` 逐个地址核对。Electron 版还有第二层「主进程拦掉窗口发往其他主机的一切请求」，Tauri 用系统网页引擎，没有这一层（#151 方案里写明的取舍）；补偿是凭据从不进窗口，加载图片也从不带凭据。不在这些地址上的图片不加载，那一条下面会写「有 N 张图片不在 GitHub 的地址上…点『在网页上看』」。详情开着超过约 5 分钟后才第一次加载的附件图片可能因签名过期而裂开，重新打开这一条即可。
- **交给 agent / 托管**（GitHub#205）：详情底部发送按钮左边，条目开着就有，不用先回复。「交给 agent」= 加 `pending/agent`、摘 `pending/human`（先加后摘：第二步失败也不会两个都没有）；「托管（自动合并）…」先弹确认框，再加托管标签（默认 `autopilot`），然后同「交给 agent」——GitHub#250 起两者都不等结果，每个标签步骤分开报，托管标签加上了而派工标签没加上时结果条逐步写明，可「补做剩下的步骤」。三个标签名都在设置里改，要和 daemon 配置一致；托管标签留空就不显示「托管」按钮。确认框分三段（加 / 摘哪些标签、之后发生什么、怎么叫停），底部「不再提示」默认不勾（GitHub#231）：勾上并点「确认托管」后，按钮变成「托管（自动合并）」（没有省略号），点一下直接托管、不再弹框；点「取消」不记。设置页「流程标签」一节的「托管前先弹确认框」勾回来就又弹框。这一项存在本机设置里，单独一项，导入网页视图不会改到它。
- **有冲突时**（GitHub#205）：PR 和目标分支有冲突（GitHub 说 `CONFLICTING` 或 `DIRTY`）时，PR 状态框顶部一条红色提示，合并按钮变成「有冲突，不能合并」且不可点。
- **编辑正文 / 评论**（GitHub#205）：GitHub 说这个账号能改的正文和评论下面有「编辑」（评审意见、逐行评论不能在客户端改）。点开是整段 markdown 原文，保存时和勾选框一样先现读：仍属于这一条、仍能改、原文和开始编辑时一字不差才写，否则不写、提示「被别人改过」，编辑框里的文字保留。评论不能改成空的。同一条一次只有一个修改在途。
- **编辑标题**（GitHub#299）：详情标题右边的铅笔按钮，issue 和 PR 都有，只在 GitHub 说这个账号能改这一条时出现；离线、有修改在途时变灰。点开是单行输入框（预填当前标题），和所有确认对话框一样单按回车不保存，只有点「保存到 GitHub」或 ⌘↩ 才保存，有改动时按 Esc 不丢字。保存前先现读这一条的标题和权限（`CavilTitleSource`）：仍能改、标题和开始编辑时一字不差才写（REST `PATCH /repos/…/issues/N`，只带 `title`，去掉首尾空格），否则不写、提示「被别人改过」，输入框里的文字保留，详情重读后显示 GitHub 上现在的标题，从它再改即可。读不到或回应缺字段算「不确定」，同样不写；标题为空（只有空格也算）不让保存。成功后立刻重读这一条，详情、看板卡片、表格行都换成新标题；GitHub 回来的标题和要写的不一致时成功但带一句「请刷新核对」。限制：GitHub 改标题没有「原值还是这个才写」的条件写法，现读之后、写入之前那一瞬间别人恰好也改了，仍会被覆盖（正文编辑同样如此）。同一条一次只有一个改标题在途。
- **没变化就不整读**（GitHub#261，`src/data/changeCheck.ts`，接在 `src/data/sync.ts` 的每个来源前面）：每轮先用条件请求问 GitHub「这个来源变了没有」——GitHub 对「没变」回 304，不占额度。看板：REST 条目列表的每一页（只取响应头，带上看板的全部字段）+ REST 字段列表（状态列选项、迭代计划），再加一条 GraphQL 查全部看板的条目数（1 点；304 不带「下一页」链接，整页之后新加的条目只有条目数看得出来）；仓库：「最近更新的那一条」（一个请求）。只有全部请求都明确回 304、看板条目数也没变，才沿用上一份快照：这份快照原样不动（不改时间、不重写缓存、不当成新读到的数据喂给在途修改的核对），只有状态写「本轮确认过」（开着的详情照旧按它跟着同步）。其余一切——有一页回 200、页数变了、报错、缺版本标记（304 也一样，`GitHubClient.conditional` 一处拒绝）、条目数读不到——都照原来整份重读，读一半仍不落地。版本标记在整读**之前**取，整读和缓存都落地后才记下（只认它对应的那份快照，按读取时间对上）；一轮里凡是要整读的来源，旧记录在这一轮拿到结果时就作废，所以整读没落地（存失败、被拒、这一轮被放弃）时下一轮照样整读。记录只在内存里，换会话 / 退出 / 换账号 / 删掉来源（或删了又加）都清空，启动后第一轮总是整读。每个来源至少每 10 分钟整读一次：检查看不到的东西——保存的视图、看板标题、本账号能不能改这个看板，以及仓库里被删 / 转走 / 滑出 14 天窗口的条目——最长约 10 分钟才出现；**点刷新（或 ⌘R）一律整读**，不看检查结果。登录身份查询照旧每轮一次。`fullReadEveryMs: 0`（只给测试用）= 不检查、每轮整读。测试：`test/unit/change-check.test.ts`（真后台 + 假 GitHub；假 GitHub 的版本标记是回答内容的哈希，304 不带 Link，和 GitHub 实测一致）。
- **条目之间的关系跟着同步读、和条目存在同一份快照里**（GitHub#349，`src/data/relations.ts`；依赖图视图用它画图，见下文「依赖图（#350）」）：每个 issue 读四样——父 issue（带标题和状态）、子 issue 列表、被谁挡住、挡住谁（GitHub 侧栏的 *Blocked by* / *Blocking*）；关系另一头带仓库、编号、标题、状态、地址，它不在任何来源里也照样有，**不会为它去读没添加的仓库**。PR 在 GitHub 上没有这些关系，记为「确定没有」。不读评论里的等前置标记。

    | 仓库 | 条目列表本来就带每个 issue 的阻塞数、子 issue 数和父 issue 地址；只对三样里有任何一样的 issue 按节点 id 批量读，每 100 个一个请求 | 一个都没有时 0；否则每 100 个 1 次（本仓库最近 100 条里 11 个 → 1 次） | 每次 1 点 |
    | 某个 issue 的某个列表超出上面的个数 | 对它单独翻页读完（每页 100 个） | 每页 1 次 | 每次 1 点；真实看板上没有这种条目 |
    | 改完一条后的单条重读 | 同一段查询字段、同一个转换函数（`RELATION_FIELDS` / `readRelations`），超出一页同样翻完 | 0（翻页时同上） | — |
    「没有变化」的轮次照旧一个整读请求都不发，这些调用只在整读时发生（每个来源至少每 10 分钟一次，额度每小时 5000 点）。
  - **和条目一起成败**：一个来源的条目和关系全部读完才写入；任何一步失败（包括某个 issue 的关系翻到后面某页失败、仓库的批量读失败）这个来源整份保留上一次的快照——看板和表格这一轮也不更新——同步状态里记下本轮的错误和旧数据的时间，下一轮照常整读（失败的那轮不留「没有变化」的检查记录）。读了一半的列表不入缓存：列表没读到最后一页时，转换函数给的是「未知」，不是前几条。
  - **「未知」不是「没有关系」**：条目上没有关系字段 = 未知（这个版本之前写下的缓存），四样都为空 = 确定没有。升级后旧缓存照常显示条目，关系是未知，第一次整读成功后补上；关系未知的快照不会被「没有变化」的检查留住，一定整读。看板数据里另有一份「哪些来源的关系未知」的清单（`relationsUnknown`）。缓存格式版本不变（旧缓存不丢）。
  - **同一个 issue 来自两个来源**：取读到了关系的那一份；两份都读到时取**关系读得更晚**的那份——每个条目记着它的关系是哪一次读取带来的（整读的开始时刻，或改完后单条重读的时刻），不看条目自己的更新时间：阻塞者被关闭时，被挡住的那条自己的更新时间不变。所以一个来源这一轮读失败、沿用旧快照，另一个来源读成功时，用的是成功那份的新关系；两份同一时刻读到的才按其它字段的规则（更新时间较新的那份）。
  - **已知限制**：在 GitHub 上新增 / 删除一条阻塞关系或挪动子 issue 后，最迟要等每 10 分钟一次的整读才看得到——「有没有变化」的检查会不会因此判为有变化没有实测（要在真实 issue 上改关系才能测）。条目自身的变化（关闭、换标签）不受影响。当前账号看不到的关联 issue（GitHub 回空）不出现在列表里。

## 界面的样子（#181）

- **颜色只在一处定**：`src/renderer/styles.css` 顶部的设计变量（浅色一份、深色一份，跟随系统）。issue / PR 的状态色仍只由 `src/shared/stateTone.ts` 决定。图标是 `src/renderer/Icons.tsx` 里自己画的线条图，不引入图标库、不从网络加载。
- **标签颜色一个函数**：看板卡片、详情、表格的标签都走 `src/renderer/colors.ts` 的 `labelStyle`——浅色下实心底、黑白字里挑对比度高的；深色下 18% 透明底 + 同色边框 + 提亮到 4.5:1 的字。
- **可读性和窄窗口有测试**：界面测试「GitHub#181 look」在真实窗口里把登录、看板、详情、表格、设置每段可见文字和它实际背后的底色（逐层叠加、算上透明度）比对，浅色和深色都要 ≥ 4.5:1（大字 3:1，变灰的按钮按规范豁免）；深色下三处标签必须是半透明底；1024×700 的窗口里两层顶栏不重叠、不横向滚动。讨论框（隔离的 iframe）不在这项检查里。

规则：

- **谁接键**，按顺序：没登录一律不响应；**输入法正在拼字时一律不响应**（⌘↩ 不会把没拼完的字发出去，Esc 只取消拼字）；对话框、选择框、快捷键一览开着时只有它自己的键（Esc 只关最上面那一层）；光标在输入框 / 下拉框里时单个字母就是打字，只有 ⌘ 组合键生效（回复框另有自己的 ⌘↩ / ⌘⇧P / Esc）；其余情况全局键和详情面板的键生效。设置页（GitHub#369）没有看板和详情面板的键，换成它自己的 Esc：光标在输入框里时也认（第一下离开输入框），所以 `resolve` 多看一项「现在是哪一页」（`KeyContext.page`，App 按当前页设）。⌘ 和 Ctrl 都认（发布的只有 macOS 版；Ctrl 给 Linux 上的自动测试），按键提示按平台写 ⌘ 或 Ctrl。
- **快捷键只替你点按钮**：每个键调用的就是那个按钮自己的处理，按钮变灰时（离线、正在发送、内容为空、上一次操作没结清）或不显示时（issue 已关、PR 详情里没有「关闭 issue」、设置里托管标签留空）键也不做事。按钮上印着各自的键。关闭 issue 的 `X` 只打开确认框（GitHub#413），合并、关闭 PR 不配键，关闭和合并都只能在确认对话框里确认；「交给 agent」「托管」按下就写 GitHub，所以要带 ⇧，防止光标意外不在输入框时误按一个字母；对话框里单按回车什么都不做（焦点在按钮上也一样），只有点按钮或 ⌘↩ 才确认。
- **要用到看板的键**（`/`、`C`）在别的页面按时，先切回看板再交给看板做一次；看板做完就清掉，以后回到看板不会重复（做法同「点通知打开那一条」）。
- **标签选择框**：候选是这个仓库的标签（和原来的下拉同一份数据），已有的打 ✓；回车或点一下 = 发一次「加这个」或「删这个」，框不收起，可以接着改；发送中整个框变灰、不排队。不提供「关框时一次写整份标签」——那会冲掉别人刚加的标签。鼠标点「+ 加标签」打开的也是它。里程碑框单选，回车就改并收起，再选一次当前的就是去掉，只列仓库已有的里程碑。
- **Esc 不丢字**：只管键盘。点「收起 ›」、切到别的条目，回复框里的文字照旧丢掉（和以前一样）；不做跨面板的草稿保存。「关闭 issue / 关闭 PR」附的那句评论在取消后仍在（存在面板里）；点了确认以后，它跟着那次操作存（GitHub#250，见上文「草稿另一条规则」）。
- 点过讨论区之后，键盘停在隔离的讨论框里，除 `R`（跳到回复框，GitHub#322）以外的快捷键传不出来（同 Esc 的限制，PR #171 维护者选的）；先点一下讨论区以外的地方。
- ⌘R、⌘, 由窗口自己处理并拦下默认行为；Tauri 在 macOS 上的默认菜单不占这两个键（未在 Mac 实机核对）。缩放的 ⌘= / ⌘- / ⌘0 仍在菜单里。

## 依赖图（#350）

视图切换处的第三个按钮「依赖图」（看板、表格旁边；选了哪个视图照旧记住，旧版本写下的「看板」「表格」照常读）。拆分与方案见 GigleAI/cavil-loop#346，数据是 #349 跟着同步读进快照的父子与阻塞关系（上文「条目之间的关系」），画图不多发任何请求。

- **进图的条目**（`src/data/graph.ts` 的 `buildGraph`，纯函数）：先按顶栏的来源勾选和搜索筛出条目，其中有父 issue、有子 issue、挡住别人或被别人挡住的 issue 进图；PR 不进图。其余写在左下角「另有 N 个条目没有父子 / 阻塞关系，未显示」，顶栏写「显示 N 个有关系的条目 · 共 M 个条目」。
- **关系另一头**：在来源里但被搜索藏掉 → 照画、整体变淡，箭头不断；不在任何勾选的来源里 → 用读关系时 GitHub 顺带给的编号、标题、状态画成虚线节点 / 虚线框，标「不在当前来源中」，摘要里只有基本信息和「在 GitHub 打开」，不为它去读那个仓库。
- **框**：父 issue 画成框，子 issue 按 GitHub 的顺序在框里；子 issue 自己有子 issue 时框里套框。框头两行：状态、编号、标题、「N / M 子项完成」（GitHub 给的数），下一行是父 issue 的标签（和普通节点、卡片同样的样式）。一个节点的父 issue 先听它自己读到的，再看父 issue 的子项列表；会成环的父子关系不认。
- **箭头**：从阻塞者指向被挡住的条目。阻塞者未关闭 → 琥珀色加粗；已关闭 → 灰色细线。阻塞者在来源里时用它自己的状态（随条目一起读，比对面关系里记的新）。被挡住的节点标「被 N 项挡住」（只数未关闭的阻塞者）；自己没被未关闭的挡住、却挡着别人的未关闭节点标「挡住后面 N 项」（顺着箭头往后数未关闭的）。不读评论里的等前置标记：只贴了 `pending/blocked`、没在 GitHub 侧栏登记 *Blocked by* 的条目没有箭头。
- **排布**（`src/data/graphLayout.ts`，自己写，不引入画图库：安装包体积门槛、窗口的内容安全策略）：框内按箭头从左到右分层（阻塞者在左），同层竖排；顶层有箭头相连的连成一组同样分层；各组按窗口宽高比一行行摆，有未关闭 issue 的组排在前面。读到环时断开一条用于分层，箭头照画。
- **什么时候重排**：排布只看「有哪些节点、哪些框、哪些箭头」（`structure`），不看状态和标签。状态、标签变化只重画那一个节点（`look` 没变的节点不重画），不挪位置；条目增减后重排，并把重排前离视野中心最近的节点留在屏幕原位。
- **平移缩放**：拖空白处（或节点）平移，滚轮以鼠标位置缩放，按钮 / `=` `-` 以窗口中心缩放（20%–200%）；「适应窗口」（`F`）整张图放进窗口、不超过 100%，图极宽 / 极高时可以低于 20%，这时视图的缩放下限就是这次适应的比例：放大再缩小能回到它，不会更小，也不会跳回 20%；「进行中」停在第一组有未关闭 issue 的组。整张图放进窗口后低于 60% 时算「太大」：第一次画出时停在进行中的部分（85%），底部提示条给「看全图」。右下角小地图可点、可拖视野框。视野只在本次运行里记住，重启回到默认。
- **点节点**：单击出摘要（标题全文、标签、被谁挡住 / 挡住谁、父 issue、「打开详情」「在 GitHub 打开」），点空白处收起。摘要按自己的实际高度往上挪、不超出画布，也不压住顶部的图例 / 缩放按钮行；画布太矮时中间部分可滚动，两个按钮始终看得见；双击或「打开详情」打开和看板同一个详情面板。
- **读取失败**（红色提示条，每个来源一条）：之前读到过 → 图照旧画上一次的完整数据，提示条写明哪个来源、失败原因（哪一步由错误文字说明）、图上是几点的数据，带「重试」。从没读到过关系（升级前写下的缓存，升级后又一直没整份读成）→ 这个来源的条目不画，提示条和左下角计数写「关系未知」，不算进「没有关系」；所有来源都这样时图上只有一句说明。
- **测试**：`test/unit/graph.test.ts`（真读取 + 假 GitHub 上录到的关系：框、箭头和颜色、三种来源外节点、筛选、关系未知、排布、视野跟着重排不动）；`test/e2e/graph.spec.ts`（真窗口：上述各项、阻塞者在假 GitHub 上重新打开 / 关闭后箭头变色且节点不动、平移缩放与小地图、读取失败的两种提示各含部分来源和全部来源、图太大时的默认视野）。截图在 `test-results/screens/graph-*.png`。

## 搜索、筛选和表格视图（#137）

**默认搜索条件**（GitHub#298）：新装的客户端搜索框里预先写着 `-Status:done -label:Done`——Project 状态为 Done 的、打着 `Done` 标签的条目默认不显示。清空搜索框即看全部，清空后一直保持空。只有从没存过搜索文字的设置才用它（文字只在 `src/shared/viewImport.ts` 的 `DEFAULT_QUERY` 一处定义）；已经存过的搜索文字，包括空的，升级时原样保留——旧客户端要用它，在搜索框里敲一次即可。

**搜索框**在客户端本地、对缓存数据筛，写法沿用 GitHub 网页（`src/shared/filter.ts`，打字即出结果，停手 0.3 秒后存进视图设置）：

| 写法 | 说明 |
|---|---|
| 文字 | 匹配标题、编号（`135` / `#135`）、标签名；不分大小写；中文词中间也能搜到（GitHub 按空格和标点切词，「看板客户端」里的「客户端」它搜不到） |
| `label:` `status:` `milestone:` `assignee:` `author:` `repo:` `iteration:` | 值完全相等、不分大小写；`repo:` 要写 `组织/仓库名` |
| `iteration:@current` / `@next` / `@previous`，`assignee:@me` / `author:@me` | 迭代按各自 Project 的期次算 |
| `no:` / `has:` 加 `label` `assignee` `milestone` `iteration` `status` | |
| `is:open` `closed`（含已合并的 PR，和 GitHub 一样）`merged` `issue` `pr` | |
| `project:` | 本客户端新增：按来源 Project 的标题、编号或网址筛 |
| `-` 取反、逗号「或」、引号包住带空格的值 | 同一字段写两次是「且」 |

不支持的写法（正文 / 评论、日期比较、`reason:`、自定义字段——包括中文字段名 `优先级:高` 和带引号的 `"Start date":…`、`sort:`、文字前加 `-`、`is:draft` 这类不认识的值……）一律在黄条里点名、忽略，结果可能比网页多，**绝不会因为一个不认识的词变成「0 条」**（GitHub 自己对不认识的写法会静默返回 0 条，`-文字` 也是）。某个来源这次没读全时，顶栏刷新按钮左边出现黄色 ⚠️（见下）。

**搜索时子 issue 跟着父 issue**（GitHub#368）：表格开着「显示层级」时，搜索命中的 issue 下面，它在当前来源里**没命中搜索**的子 issue（以及子 issue 的子 issue）也缩进显示，整行淡显，鼠标停上去提示「此条目不符合搜索条件；因上层有命中的 issue 而显示」——否则父 issue 一行孤零零留着，看不出下面有哪些子项。规则在 `src/data/table.ts`：每个组摆好之后，只从这一组已显示的行往下找；遇到命中搜索的子 issue（它在自己的组里照常显示）、或左侧仓库栏选了某个仓库而子 issue 不属于它，就停在那里，所以淡显行的直接父行一定就在它上面、同一组里。父子关系成环（GitHub 本身不允许，只可能来自损坏的缓存）时，环上的关系一律不算，缩进也用同一个判断（`validParents`）。搜索框为空、「显示层级」关掉、看板、依赖图：都不受影响。计数：左侧仓库栏只数命中搜索的（不随仓库栏变）；组标题、收起的组、仓库段标题数实际显示的行 / 条目（含淡显行）。搜索命中数 N 和「另有 K 个子 issue 随父 issue 显示」（K 是表格里淡显条目去重数，为 0 时不出）GitHub#404 起不再摆在顶栏，而是写在顶栏三个流程数字的鼠标提示里。这些数字来自看板页面构建的同一份表格结果。淡显行不能拖到别的组（它摆在父 issue 的组里，不是它自己的组）。

**离线是什么**（GitHub#270）：每轮同步先向 GitHub 问一句「这个凭据是谁」（身份查询），凭据过期时先续期。离线 = 这一轮完全用不了 GitHub：身份查询连不上（没网、DNS、连接被拒、30 秒超时）或回应正文读不出；凭据过期时续期连不上或 GitHub 回 5xx / 429；身份查询 401 后那一次续期连不上或回 5xx / 429。身份查询回 5xx / 429 / 403 等状态码不算离线（出下面的 ⚠️），续期回了别的错误也不算（出「登录续期没有成功」黄条）。离线黄条写「离线：<原因原文> · 数据整份读取：X（之后有过检查再加「；上次检查：Y」，见下文「两个时间」）· 每分钟自动重试，点刷新可立刻重试」，原因只经 `src/app/controller.ts` 的 `offlineFields` 一处写入，和离线标志同进同出：下一轮落到任何「不离线」的结果，黄条和原因一起消失——这不等于数据已同步成功，那时由 ⚠️ 或续期黄条接着说明。拿不到原因时只写「离线」，不编。原因措辞变了不算新问题（收起的黄条不重新弹出）。

有来源这次读取失败时不再出整宽黄条（GitHub#248），只在刷新按钮左边出一个黄色 ⚠️；点一下弹出详情：每个失败的来源一行（来源名、失败原因、显示的是多久前的数据），正在筛选时再加一行「筛选结果可能不全」，底部「重新同步」。再点一下、点外面或按 Esc 收起；不会自己弹开。两部分各按原来黄条的条件出现：「同步不完整」离线时不出（离线黄条已说明数据是何时读的），「筛选可能不全」离线时照出——所以离线且在筛选时 ⚠️ 仍在、详情只有筛选那一行，离线不筛选时没有 ⚠️。下一轮全部读成功，⚠️ 和详情一起消失。判断在 `src/renderer/warnings.ts` 的 `syncTrouble` 一处。

**两个时间：「整份读取」和「上次检查」**（GitHub#324）：每个来源记两个时间，界面上分开写，不合成一个数。**整份读取** = 眼前这份数据是哪一次整份读下来的。**上次检查** = 最近一次整份读成功，或问过 GitHub「变了没有」而没发现变化（GitHub#261 的变化检查）的时间，所以不早于整份读取。检查有盲区——看不到仓库里被删除、被转走、滑出最近 14 天的条目，也看不到看板标题、保存的视图和写权限的变化——这些只有整份重读才看得到（策略是约每 10 分钟整份读一次；读不成就更久，不是保证），所以「上次检查」从不写成「数据截至」。

- 右上角显示「上次检查 X」：所有已有数据的来源里最旧的那个检查时间。它取代了原来的「上次同步」——那个时间只说明这一轮的身份查询得到了回答，来源全读失败也照样前移。
- 离线黄条写「数据整份读取：X」（最旧的整份读取），检查时间比它新时再加「；上次检查：Y」。
- 鼠标停在右上角那行字上：每个来源一行「来源名：整份读取 X · 上次检查 Y」，一行「最后连上 GitHub：Z」（原来「上次同步」的那个时间），一行检查的盲区，同步中再加一行「同步中，已进行多久，已读完几个来源」。
- 来源这一轮读失败（或整轮离线）：它的两个时间都不动。来源移除再添加、退出登录：清空。重开 App：检查时间不存盘，退回成整份读取时间（只会显得更旧）。从没读成功过的来源两个时间都没有，悬停里写「还没有读到过」，不参与取最旧；所有来源都没有数据时右上角不显示时间。
- 这些时间只在 `src/app/controller.ts` 的 `refreshDerived` 一处算出（`SyncState.times` / `dataFrom` / `checkedFrom`），三处文字只在 `src/renderer/syncTimes.ts` 一处拼。测试：`test/unit/timed-sync.test.ts`。


看板上的黄条（不支持的写法、离线、同步问题、通知被拒）右侧都有「×」，点了只收起那一条。按「问题本身」记，不按文字记：只是时间过去（「1 分钟前」变「5 分钟前」）、在看板和设置页之间来回切，都保持收起；问题内容变了（不支持的词、同步问题的原因不同）、问题恢复后又出现、取消筛选后再筛选，都会重新出现。只记在本次运行里，重开 App 后仍存在的问题照常显示。

`author:` GitHub 的 Project 筛选并不支持（录制时 `author:x` 和 `-author:x` 都返回 0 条），本客户端按条目的作者筛。

**和 GitHub 对拍**：`record.mjs` 录看板数据的同一次运行里，用 GitHub 的服务端筛选（`items(query:)`）跑一遍约 50 条查询，`test/unit/filter-parity.test.ts` 要求客户端对每条筛出完全相同的条目。只有两类预期不同、单独断言：中文词中间（客户端更全）和 `author:`（GitHub 不支持）。

**顶栏右侧的流程数字**（GitHub#404）：看板和表格的第二行右侧是「● 运行中 N　● 等 agent N　● 等人处理 N」，取代原来的「N 个条目」和搜索时的「显示 N / M 条 · 另有 K 个子 issue 随父 issue 显示」（依赖图页那句「显示 N 个有关系的条目 · 共 M 个条目」不变）。每个数 = 顶部勾选的来源里**开着的** issue / PR（草稿 PR 算开着）中带对应标签的条目数，标签名整名、不分大小写；已关闭、已合并的不算；一条同时带两个流程标签就两边都算。三个数不随搜索框、左侧仓库栏变。数的规则就是提醒用的 `isPending()`（`src/data/flowTally.ts` 的 `flowTally`），所以「等人处理」和提醒、角标是同一条规则（只是范围：提醒数全部来源，顶栏只数勾选的来源）。标签名取设置页「流程标签」一节：运行中 = 「运行中的标签」（默认 `doing/agent`，留空就不显示「运行中」）；等 agent / 等人处理 = 「交给 agent 的标签」/「等人处理的标签」（这两格留空会恢复成默认值，所以永远有数）。数为 0 时数字变淡、位置不动。鼠标停上去：这个数数的是哪个标签、当前来源共多少条目；搜索时再加搜索命中数和「另有 K 个子 issue 随父 issue 显示」。**点一个数** = 搜索框换成 `is:open label:"<标签>"`，那个数亮起；**再点亮着的那个数** = 搜索框回到点之前的内容（原来是空就回到空）；亮着时点另一个数，直接换过去，记下的原搜索不变；手动改搜索框、不再等于任何一个数的那句时，记下的原搜索作废。原搜索只记在这个窗口里（去设置页再回来还在），不存盘：重启后搜索框若正好是某个数的那句，它照样亮，点它得到空搜索框。规则（`tallyClick` / `tallyForget`）也在 `flowTally.ts`。标签名写不进搜索语法的（含双引号，或以 `<` `>` 开头——筛选器把它当比较、忽略掉），那个数只显示、不能点：写不写得进由真实解析器读回核对（必须原样读回成「开着」加这一个完整标签），不靠列举字符。

**表格视图**和看板并存，工具栏右侧切换。排序是两种布局共用的：看板每一列里卡片的顺序、表格里行的顺序都按它（导入的「按更新时间从新到旧」在看板上同样生效）。表格的「视图设置」里还能改：分组（迭代 / 状态 / 里程碑 / 仓库 / 不分组）、排序（含「Project 里的顺序」）、显示哪些列、左侧按仓库切片、子 issue 缩进在父 issue 下。GitHub#205：标签、迭代、状态、里程碑四列点一下单元格就能改（和详情用同一套修改：标签是同一个选择器、一次一个加 / 摘；迭代和状态每个 Project 一个下拉框；离线时不可点），结果显示在看板顶部；分组栏滚动时贴在表头下面（GitHub#275 起不再着色、不带左边色条，比仓库标题轻一级；组里的行标题缩进到和分组名对齐，左边一条细竖线一直连到这组最后一行；相邻的两个以上收起的组合成一行「已收起 N 组 · 共 M 条」，列出各组名和条数，点组名只展开那一组，「全部展开」展开这一行里的全部，点这一行别处不展开；展开的组隔开、不跨仓库，被筛空不显示的组不占位，只有一个收起的组时照旧是普通的组标题，规则在 `table.ts` 的 `foldRuns`，只管显示，收起状态照旧按组记）；拖动表头右边缘改列宽（60–2000 px，存进视图设置，重开保持），双击恢复默认。一个条目在两个 Project 里迭代或状态不同时，在两组里各出现一次（和看板一样）。GitHub#294：按迭代 / 状态 / 里程碑分组时，整行可以拖到另一组（在线时；单元格编辑器开着的那一行不拖），松手就和看板上把同一张卡拖到同一列完全一样——改哪几个 Project、拒绝的理由、「还没加入看板，加入并设为…？」确认框都是看板那一份规则（`board.ts` 的 `dragScope` / `dropPlan`，表格只在 `table.ts` 的 `tableDropPlan` 里把组换成看板的列）；拖到「无迭代 / 无状态 / 无里程碑」是清空；收起的组标题和「已收起 N 组」里的组名也接得住；「所有仓库」分块时只能拖到同一个仓库下的组；按仓库分组、不分组时不能拖。表格只显示有条目的组，没有条目的迭代 / 状态要在看板上拖过去。整行可拖以后，行里的文字不能再用鼠标拖选（看板卡片也一样）。「无迭代 / 无状态 / 无里程碑」组排在所有有值的组后面，和网页一致（GitHub#231；看板的「无迭代」列位置不变）。收起了哪些组存在本机设置里（GitHub#231），按分组方式分开记，切到看板再切回来、重开 App 都保持；每种分组方式最多记 200 个组，超出丢最早收起的。迭代下拉（详情和表格单元格同一个，`src/renderer/iterationOptions.tsx`）分三段：「当前」（文字后加「（当前）」；macOS 原生下拉不能给单个选项上色）→「即将开始」由近到远 →「已结束」最近结束的在前；读到的迭代顺序不影响结果。子 issue 只在父 issue 也在同一组里时才缩进。

**看板分泳道：每个仓库各自滚动、各自收起**（GitHub#297）：勾上「按仓库分泳道」后，每个仓库的那一行列单独左右滚（触控板横扫或 Shift+滚轮），不带动别的仓库，所以同一列在不同仓库里不一定上下对齐；每一列最高是看板可见高度的一半，而且不超过「看板可见高度减去本仓库标题、下一个仓库标题和间距」（`BoardView.tsx` 的 `laneColumnMax` 从页面上量，窗口大小和上面的提示条都算进去），卡片多了在列里自己上下滚，下一个仓库的标题一屏内看得到；看板矮到连这样都放不下时，列最矮缩到 48px（`LANE_COL_MIN`），此时下一个仓库的标题可能要滚一下才看到。仓库标题滚动时钉在看板顶上；点标题收起成一行（数字是这个仓库在当前筛选下的卡片数，一个条目落在两列里算两张），再点展开。收起的仓库记在本机（设置键 `laneFolds`，和表格的收起分开、不进视图设置，导入网页视图不碰它，最多记 200 个，规则在 `src/shared/uiPrefs.ts`）。不分泳道的看板和以前一样。

**左边仓库栏选「全部」时先按仓库分**（#213）：开着「左侧按仓库切片」、选的是「全部」时，表格先按仓库分大组（和左边仓库栏同样按字母序，仓库名大小写不同算同一个），每个仓库下面再按视图设置里的分组方式分小组，只列这个仓库有条目的组。仓库标题旁的数字是这个仓库的条目数：一个条目因为两个 Project 意见不同落进两个小组，会出现两行，但只算一次。仓库和仓库下的小组都能各自收起，收起一个仓库的某个组不影响另一个仓库的同名组。点左边某个仓库、关掉「左侧按仓库切片」，或分组方式本身选「仓库」时，表格只有一层，和以前一样；分组选「不分组」时只剩仓库一层。分仓库后，子 issue 和父 issue 不在同一个仓库时不再缩进在父 issue 下，而是在自己仓库里作为顶层行；别的仓库的 PR 跟着它的 issue 进 issue 的仓库（GitHub#275，和看板分泳道时一样）。GitHub#275：仓库标题是最重的一层（图标、16px 粗体、下边两像素的线），滚动时钉在表头下面，小组标题钉在它下面，两层一直看得到；仓库标题下属于这个仓库的行只写「#编号」，不再重复仓库名；跟着 issue 进来的别的仓库的 PR 照旧写全名（`TableView.tsx` 的 `rowRef`）。规则在 `src/data/table.ts` 一处：每个仓库的小组和「只选这个仓库」时完全一样，测试逐仓库对拍。

**导入网页视图**：添加 Project 时，第一次完整读到它之后导入它网页上存的一个视图（贴的网址带 `/views/N` 就导那个，没带就导第一个）：布局、分组、排序、列、筛选。只导入一次——之后网页上改了视图不会跟着变；导入前用户已经动过的设置以用户为准；删掉再加这个 Project 会重新导入。筛选有一个例外（GitHub#298）：网页视图没写筛选、而搜索框此刻恰好是默认条件 `-Status:done -label:Done`（一字不差）时，保留默认条件，不清空；其余情况（自己写的、先前导入的、空的）照旧换成网页视图的筛选。做不到的部分（自定义字段分组 / 排序 / 列、路线图布局、多级排序）在视图顶部列出来。GitHub 的接口不返回「按仓库切片」和「显示层级」两个开关，导入时都设成开。仓库来源（REST）读不到 GitHub 的「关联 PR」，那一格只列正文点名这个 issue 的 PR，一个都没有时显示「—」。

## `pending/human` 提醒（#139，#169 在 Tauri 上重做，#251 收窄）

「待处理」= 所有已加入来源里**开着的** issue / PR（草稿 PR 也算开着）、并且带「等人处理的标签」（默认 `pending/human`，不区分大小写）的条目。已关闭的 issue、已关闭 / 已合并的 PR 不算待办，不论标签（#251：维护者「通知也只通知新的待办 issue/pr」；#139 原先连关闭的也算）。这个标签名和「交回 agent」摘掉的是**同一个设置**（`handBack.human`），改一处两边一起变。通知和 Dock 角标都由 `src/data/pending.ts` 的同一个 `PendingTracker` 算出（「开着且带标签」只有 `isPending()` 一处），角标是其中的未读部分（见下），controller 只在一轮同步收下结果后把「这一轮完整读到、且仍属于这次添加」的那些快照喂给它（和写缓存用的是同一份 `accepted`）。

| 情况 | 结果 |
|---|---|
| 某来源这一轮没读全（断网、凭据失效、分页中途失败） | 它不参与比较，沿用上一轮的那份：不报新增，也不报移除 |
| 某来源在这次运行里第一次读全（启动、新加来源、换账号） | 它已有的条目只当比较起点（历史）：**不通知、不汇总、不算未读**（#251 去掉了原来的启动汇总） |
| 已读全过的来源里，某条目上一轮不是待处理、这一轮是 | 通知一次；摘掉再挂上、或带着标签被重新打开，都算新出现；关闭的条目新挂标签不通知 |
| 通知排出去之后（GitHub#328） | 后台把这一轮新出现的待处理条目的详情先读一遍，放进「本次运行读过的详情」（GitHub#229 那 50 条，只在内存里）：点通知时详情先显示这份、标题下照常写「显示 HH:MM 读到的内容 · 正在更新…」，同时现读一次最新的。一轮最多读前 10 条（`PREFETCH_PER_ROUND`），每一条都等它自己那一轮的通知和角标交给外壳并得到应答之后才读、一次只发一条（隐藏窗口里并排发出的请求会被压住，见下方「窗口对外壳的调用一次只发一条」）；上一轮的预读还没读完时又来一轮，新一轮的条目照样等自己那一轮的通知和角标（PR #331 复审第 1 轮）。轮到某条时按通知发出前的同一条规则再核对一次（仍待处理、来源和标签设置没变、账号没换），不符就不读；读失败不提示、不重试，打开时照常现读。和面板的读取走同一个函数（`readDetail`）：只收本账号的结果，同一条里先发出的读取晚回来，不盖掉后发出的那次。启动时已有的历史条目不预读；没有外壳（不发通知）时也不预读 |
| 点一条条目通知 | 外壳先按这条通知的完整编号把它从通知中心收起（只收这一条，同一条目的其他通知也留着，GitHub#369），再让窗口回到前面，App 里打开那一条的详情；它已不在看板上（比如来源刚删掉）就在浏览器打开 |
| 同一条目在几个来源里 | 按 `仓库#编号` 只算一个、只通知一次 |
| 删除来源 / 改标签名 | 静默重算，不发通知；不会让未读变多（只会因条目不再算待处理而变少） |
| 退出登录 / 换账号 | 清零，下次第一次读全时重新取起点（不通知） |
| 在 App 里改了一条（加 / 摘标签、交回 agent） | 只重读那一条进缓存，不喂给提醒；角标在下一轮同步（≤ 60 秒）时跟上。自己在 App 里打上 `pending/human` 也会在下一轮收到一次通知（窗口在前台，所以不算未读） |

**多人共用一个仓库：只提醒和自己有关的**（GitHub#373）。设置「提醒」里的「提醒哪些条目」有两项，只存在本机（设置 `notifyScope`，读出的不是 `mine` 一律按 `all`）：

- **全部待处理**（默认）：上面的规则原样不变，升级后没有人会少收通知。
- **只提醒和我有关的**：一条待处理还要「和当前登录账号有关」才通知、才计角标。通知和角标仍出自同一个 `PendingTracker`，判断只有 `src/data/pending.ts` 的 `concernsViewer()` 一处，按顺序、先命中先算：
  1. 指派给本人，或请本人 review → 有关；
  2. 否则，指派了别人、或只请了别人 review（团队 review 请求算「别人」：读团队成员要组织权限）→ **无关**，即使本人还订阅着——改派就等于把提醒交出去；
  3. 否则（谁都没指派、没请人 review）：PR 先看它关联的 issue（PR 正文的 `Closes / Fixes / Resolves / Refs #N`，GitHub 为这条 PR 列出的关联 issue——侧栏「Development」手工关联的也在里面，以及 issue 自己列出的「Linked pull requests」），在已读到的数据里找得到的，任一个按这三步算有关就有关；找不到关联 issue 的 PR、以及 issue 自己：本人订阅着（GitHub 的 `viewerSubscription`；开过、评论过、被 @ 过会自动订阅）就有关，没订阅就无关。
  读不到、读不全一律按有关算（订阅状态未知、review 请求或关联 issue 超过一次读到的 20 条、登录名还不知道）：宁可多提醒一条，不漏。

| 情况 | 结果 |
|---|---|
| 已读全过的来源里，条目改派给本人 / 请本人 review / 没人负责的条目本人订阅了 | 通知一次（已挂着标签的也算新来一条） |
| 改派给别人、取消订阅 | 静默移出，还没看的那条不再算未读 |
| PR 所在来源本轮没重读（确认没变，或读失败保留着上一份），关联 issue 所在来源读到改派 | PR 跟着变：改派给本人通知一次，改派给别人静默移出 |
| 新加来源 / 启动 / 换账号后第一次读全 | 它带来的条目是历史，不通知；**只因为它带来的数据**才变得有关的别处条目（老来源里的 PR，关联 issue 随新来源第一次出现）也不通知，之后的变化照常通知 |
| 新加来源的同一轮，老来源里有真实变化 | 不靠新来源的数据也成立的照常通知；非靠新来源的数据不可的，算历史 |
| 删除来源、切换这一项、改标签名 | 静默重算，不通知；切换这一项不会让角标变大（切回「全部」后重新算进来的条目不算未读） |

做法：每轮（有来源读到新数据时）按**所有来源当前持有的数据**重算提醒集合，不只算刚读到的来源；「新出现」= 这一轮在集合里、上一轮不在、而且去掉本轮第一次读全的来源后仍在。提醒用的数据是喂给它的整份读取（和「待处理」一样，App 里改一条后的单条重读不喂给它，下一轮同步跟上）。

**读取**：看板条目和单条重读的查询各加了 `viewerSubscription`，PR 再加 `reviewRequests` 和 `closingIssuesReferences`（GitHub 列出的关联 issue；只给提醒用，PR 显示在哪个 issue 下面仍按原来的规则）；仓库来源的 REST 列表不带这两样，所以对**全部开着的** issue / PR 按 id 补读，和 GitHub#349 的关系批读合成同一批请求（每 100 条一次；关掉的条目不可能是待处理，不读）。任何一条读不到，这个来源本轮读取失败、保留上一份。三个入口都经 `src/data/viewerTies.ts` 的 `readViewerTies()` 转成条目上的 `viewerSubscribed` / `reviewRequested` / `closingIssues` / `viewerAt`（这次读取发出的时间）。**合并**（同一条目在几个来源里，`mergedViewerTies()`）：订阅不改条目的更新时间，所以这三样不跟其他字段走，按 `viewerAt` 取读得最晚的那份；没读过的副本（旧缓存、仓库列表里已关闭的）让位；读取时间相同而说法不同，取「更可能有关」的——有一份未知就未知、有一份订阅就订阅、review 名单和关联 issue 取并集——结果与来源顺序无关。

限制：只在 GitHub 上点 Subscribe / Unsubscribe 不会更新条目，「变了没有」的检查看不出来，要等下一次整份读取成功（约 10 分钟一次，读不成就更久）；指派、请 review 会更新条目，下一轮就算。关联的 issue 要在已添加的来源里才找得到；不在任何来源里时按 PR 自己的订阅状态算。需求机器人开的、没人指派也没人订阅的条目，在这一项下谁都收不到通知。


**Dock 角标只是未读数**（#185；维护者在 PR #194 上改定：「角标变成未读数，切换到 app 后清空，同时清空之前发的 notification」；#251 去掉历史）：

- **未读** = 窗口不在前台时一轮里新出现的待处理条目，只算其中仍然待处理的（还没看就被摘掉标签或关掉的那条不再算）。第一次读到某来源时已有的条目是历史，不进未读。controller 记一份未读集合（`unread`），角标发 `unreadNow()` = 未读集合里当前仍待处理的条数（`PendingTracker.has()`）；计数时不删记录，所以改标签名再改回来不会把没看过的条目当成看过。窗口在前台时新来的条目照样发通知，但不进未读。
- **切到 App 就是看过**：外壳在主窗口获得焦点时发 `active`、失去焦点或关窗隐藏时发 `inactive`（`src-tauri/src/main.rs` 的 `WindowEvent::Focused` / 关窗分支，`desktop.rs` 的 `set_active`）。收到 `active`，controller 清空未读、把角标设成 0。点 Dock 图标、点通知都会让窗口获得焦点，走的是同一条路。退出登录清空未读。
- **通知留在通知中心，点哪条只收哪条**（GitHub#369：「切到客户端时，不消掉所有通知。点通知时，只消掉对应的通知」）：切到 App **不再**收起已发的通知。点一条通知时，外壳（`desktop.rs` 的 `on_click`）先按它的完整编号调 `mac.rs` 的 `clear_delivered_one`（`removeDeliveredNotificationsWithIdentifiers`）只收起这一条，再照旧把窗口带到前面、打开那一条；同一条目摘掉标签又挂回后的另一条通知照样留着。在看板上打开条目详情不收起任何通知。没有条目的打包检查通知也按自己的编号收起。测试模式下每次点击记一行 `{op: "clearNotification", id}`。
- **通知编号带「本次启动」标识**（GitHub#369）：编号是 `{key, url, run, n}`（打包检查的是 `{summary, run}`）。`n` 每次启动从 0 数，`run` 是每次启动随机生成的一串，所以重启前留在通知中心的通知和重启后同一条目的新通知编号不同，点一条不会连带收起另一条。旧版本发出的通知没有 `run`，和新编号也不会相同，点它照样能打开条目。
- **设置里的开关「切到 App 时收起全部系统通知」**（GitHub#369，`AppState.clearAllOnActivate`，本机设置 `clearAllOnActivate`，默认不勾；读出的不是 `true` 一律按不勾）：勾上后，收到 `active` 时 controller 在角标设成 0 之后再排队调 `desktop_clear_notifications`（macOS 上 `removeAllDeliveredNotifications`），即 GitHub#185 的旧行为。它只管切到 App 时要不要全部收起，不改点击本身（外壳照样只按编号收起被点的那一条）、不影响设置页 Esc；但点通知会把窗口带到前台，所以勾上时点一条之后其余通知也会随之全部收起。设置页的说明随开关切换（`notification-keep-rule`），两种状态写的都是实际结果（PR #370 复审第 1 轮）。
- **设置页不列条目、不显示总数**（#251：「设置里也不用把所有的都列出来」）：「提醒」一节只说明规则（哪个标签、关闭的不提醒、启动时已有的不算、通知怎么收起）、「提醒哪些条目」两个单选和所选那一项的规则说明（GitHub#373）、通知被系统拒绝时的提示、「切到 App 时收起全部系统通知」开关、开机自启开关。#185 的待处理列表和「未读 N · 现在待处理 M」已删；`AppState.pendingCount` 仍在（测试用），界面不显示。
- 外壳的通知类型里仍保留 `summary`：打包检查（`--notify-check`）发的那条测试通知用它；App 自己不再发。

**桌面这一侧在外壳里**（`src-tauri/src/desktop.rs`、`mac.rs`），窗口经 `src/app/desktop.ts` 的约定调用它，这些命令都不碰凭据：

- **通知**：macOS 上用系统现行的通知接口（UserNotifications），第一次发之前向系统申请权限，每条的结果（成功 / 系统原话）回报给窗口；拒绝时看板顶部和设置页显示提示，下一条成功后清掉。不用 Tauri 官方通知插件：它在 macOS 上查权限一律回「已允许」、发送失败不回传（按插件仓库提交 `4356356d`、插件 2.7.0 的源码核对），「被拒要让人看见」就做不到。没打包的开发版（`npm start`）不发通知。
- **角标**：Tauri 窗口的设角标接口（Dock 图标的数字），0 时清掉。数字是未读数（见上）。
- **收起已发的通知**：`desktop_clear_notifications`，macOS 上 `UNUserNotificationCenter.removeAllDeliveredNotifications`，只动本 App 的通知；其他系统不做事。
- **窗口在不在前台**：主窗口获得 / 失去焦点、关窗隐藏时，外壳发 `active` / `inactive` 事件，也写进测试记录。
- **开机自启**：Tauri 官方开机自启插件，macOS 用登录项 LaunchAgent（`~/Library/LaunchAgents`），启动参数带 `--hidden`：不显示窗口，照常同步提醒。
- **关窗只隐藏**（macOS）：拦下关窗请求改成隐藏，点 Dock 图标（系统的「重新打开」事件）窗口回来，⌘Q 退出。其他系统 v1 不显示通知和角标、关窗即退出，计数照常。
- **要求 macOS 14 或更新**（`tauri.conf.json` 的 `minimumSystemVersion`，维护者在 PR #173 定的）：窗口隐藏后网页还能继续跑，靠的是网页引擎「不挂起看不见的页面」这个开关，它从 macOS 14 起才生效；11–13 上没有办法保证关窗后继续提醒，所以不再支持。窗口仍按 Safari 14 的网页引擎构建（比需要的更宽），旧引擎的界面测试照留。`scripts/mac-open-check.sh` 第 0c 步核对打出来的 App 确实要求 14。
- **同步节拍在外壳**：外壳每 60 秒告诉窗口「该同步了」（并带上节拍间隔），窗口收到才同步（窗口里不再有周期定时器；慢轮之后的那一次补跑见「定时同步不首尾相接」）——隐藏窗口的定时器会被网页引擎放慢。macOS 上另外声明一个「用户发起的活动」，不让系统的 App 小憩把没有窗口的 App 停掉。
- **窗口对外壳的调用一次只发一条**：隐藏窗口里同时发出的第二条请求可能被压到下一次唤醒（实测：角标比通知晚了整整一拍，超过 2 分钟的承诺），所以 controller 把它们排成队。

**测试模式**（只在 `CAVIL_CLIENT_TEST_MODE=1` 且 GitHub 指向本机回环时生效）：`CAVIL_CLIENT_TEST_ALERTS_FILE` 把每次通知 / 角标 / 节拍（带当时窗口是否可见）/ 隐藏 / 显示写成一行 JSON，不弹真通知；`CAVIL_CLIENT_TEST_NOTIFY_REFUSE=<消息>` 模拟系统拒绝；`CAVIL_CLIENT_TEST_TICK_MS` 改节拍；`CAVIL_CLIENT_TEST_HIDE_ON_CLOSE=1` 让 Linux 上也关窗只隐藏；`CAVIL_CLIENT_TEST_CONTROL_FILE` 里追加 `close`（和关窗按钮同一个请求）、`click <通知 id>`（和点那条通知同一段处理）或 `activate`（和窗口获得焦点同一段处理：没有窗口管理器的测试显示上焦点事件不一定有）。

## 登录用的 GitHub 应用

浏览器授权走 GitHub 的设备授权流程（App 显示短码，浏览器里输入、同意）。登录页和设置页都有「登录方式」二选一：**默认 OAuth 应用**（已内置），用户想用时可选 **GitHub App**（预览，维护者 2026-11-05 在 #140 定：第一版先把 OAuth 做完整，GitHub App 以后再完整支持）。选项旁的小字链接「两种有什么区别？」打开一页说明（纯本地文字）。说明页、选项下的权限说明和登录前的 Client ID 核对都来自 `src/shared/appKind.ts` 一处：只说能确定的事——OAuth 应用申请的 scope 是本客户端定的，可以写明；GitHub App 的权限由那个 App 登记时决定、登录请求收窄不了，所以不承诺「碰不到代码」；令牌过不过期是各自应用的设置，不按登录方式一刀切。Client ID 和所选方式对不上（GitHub App 的 ID 以 `Iv` 开头，OAuth 应用的不是）时，输入框当场提示、不让保存，登录也直接拒绝、不联系 GitHub。登录代码本身不区分两种：

| | OAuth 应用（默认，已内置） | GitHub App（可选，预览） |
|---|---|---|
| 权限 | 本客户端整块申请：`repo`（含代码与设置）、`read:org`、`project` | 由 App 登记时逐项勾选（下面「建 GitHub App」推荐只勾 Issues、Pull requests、Projects 读写 + 仓库基本信息只读）；登录时收窄不了，以授权页为准 |
| 令牌 | 看应用设置：开了令牌过期就带续期令牌，没开就不过期 | 看 App 设置：默认 8 小时过期、带续期令牌（约 6 个月），建 App 时可关；GitHub 每次续期都换一个新的续期令牌 |
| 能看到的 | 账号能看到的、申请范围内的 | 账号能看到的、App 权限允许的、App 装到的仓库，三者交集 |
| 这一版 | 内置 Client ID，直接登录 | 没有内置的 App：要填自己建的 GitHub App 的 Client ID；还没做的：内置 App、引导组织安装、提示「哪些仓库没装到」 |

客户端会在令牌到期前 5 分钟自动续期，GitHub 说 401 时也先续期重试一次。续期只在一处进行，同一时刻最多一次（续期令牌用过即作废）。续期的结果只有这几种（`src-tauri/crates/core/src/engine.rs` 的 `ensure_fresh` 注释里逐条列着）：

| 续期遇到的 | 结果 |
|---|---|
| 连不上、超时、HTTP 5xx / 429（不管正文写什么） | 暂时不可用：登录、凭据、缓存都保留，下一轮再试 |
| GitHub 回 `bad_refresh_token`（续期令牌错误或过期） | 回登录页并说明原因 |
| 其他错误、回应无法解析、没有新令牌 | 不能证明凭据失效：保留一切，顶部提示，下一轮再试 |
| 拿到新令牌但写钥匙串失败 | GitHub 已作废旧续期令牌，所以新令牌留在内存里继续用、顶部提示，之后每轮重试保存；保存成功前退出 App，下次要重新登录 |
| 续期途中退出登录 / 换账号 | 退出、新登录优先，这次续期什么都不留 |

任何情况下续期都不会抛出没人处理的错误（有真实子进程测试守着）。

**启动时只用「可信」的凭据**：本地数据库里记着一份可信名单（只存凭据的哈希，写入是同步落盘的）。启动时钥匙串里的凭据不在名单上，就不用它登录，回登录页并把它删掉。名单只在这几处改：

| 时机 | 名单怎么变 | 为什么 |
|---|---|---|
| 退出登录（手动、续期被拒、续期令牌到期） | **第一步**清空，然后才切页面、才排队删钥匙串 | 删除排队中、进行中、失败、或进程直接被关掉，重启都不会用旧凭据 |
| 登录 | 写钥匙串前清空；写成功且这次登录没被取消，才加入新凭据 | 写到一半被关掉、或被取消，重启都不信它 |
| 续期 | 写钥匙串时同时信任新旧两份；写成功后只留新的 | 写到一半被关掉，重启用新的继续，不用重新登录 |
| 名单从没写过（这条规则之前的预览版留下的数据） | 当作空名单：不用钥匙串里那份，回登录页并删掉它 | 旧数据分不清「还登录着」和「退出了但没删掉」（只有最后一版预览会记「不得复用」，更早的什么都不记），所以一律不信。代价是装过预览版的人升级后要重新登录一次 |

退出时钥匙串删不掉，登录页会写明旧凭据可能还在钥匙串里；它已不在名单上，下次启动会再试着删。两进程测试（`test/unit/crash-restart.test.ts`）在每个时刻结束第一个进程，再用同一份磁盘数据启动第二个进程核对。

内置的 Client ID 在 `src/shared/config.ts`：OAuth 应用是 `DEFAULT_OAUTH_CLIENT_ID`，GitHub App 是 `DEFAULT_GITHUB_APP_CLIENT_ID`（目前为空）。Client ID 不是秘密。两种方式各存各的覆盖值（`oauthClientId` / `githubAppClientId`），在登录页或设置页「改 Client ID」里改；选了 GitHub App 而没有 Client ID 时，登录直接说明要填什么，不会联系 GitHub。预览版只有一格 Client ID：里面存的是 GitHub App 的 ID（`Iv` 开头）时，升级后自动归到 GitHub App 那一格并保持选 GitHub App。续期时用的是登录那一刻的 Client ID，之后改登录方式或 Client ID 都不影响已登录的令牌（有测试）。

### 建 GitHub App 的逐项设置

1. 在 GigleAI 组织页「Settings → Developer settings → GitHub Apps → New GitHub App」新建（建在组织下，组织的 Project 才能授权给它）。
2. **GitHub App name**：`Cavil Loop`；**Homepage URL**：`https://github.com/GigleAI/cavil-loop`。
3. **Identifying and authorizing users**：勾 **Expire user authorization tokens**（默认已勾）；**Callback URL** 留空也行（设备授权用不到）；不勾「Request user authorization (OAuth) during installation」。
4. 勾 **Enable Device Flow**。
5. **Webhook**：取消勾选 **Active**（客户端不需要回调）。
6. **Permissions**：
   - Repository permissions：**Issues** = Read and write；**Pull requests** = Read and write；**Metadata** = Read-only（必选）。其余保持 No access。
   - Organization permissions：**Projects** = Read and write。其余保持 No access。
   - Account permissions：全部 No access。
7. **Where can this GitHub App be installed?**：Only on this account。点 **Create GitHub App**。
8. 不需要生成 Client secret，也不需要 Private key。
9. 在 App 页面左侧 **Install App** → 安装到 GigleAI → 选 All repositories 或要看的那几个仓库。
10. 把 App 页面上的 **Client ID**（形如 `Iv23li…`）写进 `DEFAULT_GITHUB_APP_CLIENT_ID`，或先在登录页选「GitHub App」、把它填进 Client ID 框试用。

要在客户端里**合并 PR**，按 GitHub 文档 App 还要 **Contents** = Read and write（上面没勾；OAuth 应用的 `repo` 已含这项）。不加的话，其他操作照常，合并会被 GitHub 拒绝、界面照实显示原因。

要在讨论里看到**私有仓库的 Release 附件图**（GitHub#395），App 要有 **Contents** = Read-only（上面没勾；OAuth 应用的 `repo` 已含这项）。不加的话，其他内容照常显示，这类图的位置显示「没取到：当前登录读不到这个仓库的发布附件；用 GitHub App 登录时，需要那个 App 有读取仓库内容（Contents）的权限」，可以点「在网页上看」。客户端不会自己去要这项权限。

## 自动更新（#184）

**谁做什么**：判断全在后台本体 `src-tauri/crates/core/src/update.rs`（App 和测试后台跑同一份）；碰到已安装 App 的部分（读更新说明、下载、验签、换掉 App 包）是外壳的 `src-tauri/src/updater.rs`，用 Tauri 官方更新插件；窗口只显示外壳报来的状态（`state.update`，设置页「更新」一节 + 看板顶部的「已下载」提示条，`src/renderer/UpdateViews.tsx`）。

- **挑哪个版本**（`update::pick`）：读本仓库发版列表（不带令牌，最多 10 页），只认标签 `client/vX.Y.Z`（三段纯数字、不带前导零）、不是草稿也不是预发布、版本号比当前大的；取版本号最大的，不看发布时间。它的附件里必须有 `latest.json`，而且地址在本仓库的下载地址下，否则判失败（不退而求其次装更旧的）。
- **两个渠道**（#215，设置页「更新渠道」，存在本机设置 `update.channel`，默认正式版，看不懂的值按正式版）：**正式版**只按上一条挑；**开发版**另外认标签 `client/vX.Y.Z-dev.N`、而且标成预发布的发版（main 上每次客户端改动由 CI 发，见下面「开发版」）。两种一起比版本号：按 semver 的先后——同一个 X.Y.Z，正式版比它的开发版高；开发版之间按 N 的数值比（`dev.10` > `dev.9`）。形状不对的（`-rc.1`、`-dev.01`、标成预发布的 `X.Y.Z`、没标预发布的 `-dev.N`）两个渠道都不认。从开发版切回正式版不降级：等下一个比当前高的正式版。开发版只有 Apple 芯片的包（`update::DEV_TARGETS`，和发版说明生成器 `CHANNEL_PLATFORMS.dev` 是同一张表，测试对拍），Intel Mac 上开发版选项置灰并写明原因。
- **切渠道遇上正在进行的一轮**：切换和「这一轮属于哪个渠道」在同一把锁下记一个代号；一轮在读列表、读更新说明、下载时看到代号变了就作废（读到的丢掉，下载停掉），随即按新渠道重来一轮；下载完、开始换 App 之前在同一把锁下再核对一次。正在换 App（「正在安装 X」）时换不了、也停不下来，这时切换被拒绝，单选置灰。已装好等重启时可以切，已换上的版本不撤回，重启前不再查。
- **什么时候查**：启动时一次，之后每 6 小时一次；关掉「自动检查更新」后都不查，手动「立即检查」照查。一次只跑一轮：跑着时再点不会再开一轮；新版装好以后不再查（重启就是新版）。
- **失败不等于已是最新**：发版列表或更新说明 30 秒没回应、任一页读失败、内容看不懂、下载 60 秒收不到数据（按「多久没收到数据」算，不按总时长）、中途断开、签名不符、换 App 失败，都记成失败并写明原因，下一轮再试；只有真的没有更高版本才说「已是最新」。
- **免放行命令的依据**：macOS 只拦带「从网络下载」标记的 App，这个标记是浏览器下载时加的。更新插件用自己的网络代码下载、在进程里解包换掉 App，不加这个标记；万一换上的新版带着标记，`updater.rs` 会把新版自己身上的去掉。CI 的 Mac 上真跑更新核对（`scripts/mac-update-check.sh`）。
- **更新了什么**（#348，`update::notes`）：新版下载、安装、等重启时，状态里带一份清单——从正在运行的版本（不含）到新版本之间、所选渠道上每个可安装的版本各一项，从新到旧；看板提示、设置页「更新」一节的按钮和重启后的提示打开的是同一份（`UpdateViews.tsx` 的 `UpdateNotesDialog`）。它只从这一轮已经读到的发版列表里取（和 `pick` 共用同一条「这个发版算不算」的规则 `installable`），不多发请求、不带令牌。每个版本的内容取自它发版页的正文，按顺序找：① `### 更新内容` 小节里的 `- ` 行（发开发版的脚本写的，见下面「开发版」）；② 正式版取 `### 这一版…` 小节里的 `- ` 行；③ 开发版取正文第一行「开发版 X，构建自 main 的 <提交>：<提交标题>」里的提交标题；都取不到就只列版本号、写「这一版没有写更新说明」。`- **标题**（GitHub#N）：说明` 拆成标题和可展开的说明，其余的行整行当标题；一律当纯文本显示（去掉 `**` 和反引号，不渲染、不出链接）。同一行在范围内更旧的版本里、或正在运行的版本自己的发版页里出现过，就不重复列（正式版的发版页是整份发版说明）。正在运行的版本自己的发版页还在列表里才算「列全了」；不在（开发版只留最近 10 个）就标成可能不全，清单底部写明。上限：最多 30 个版本、每版 20 条、每段 2000 字，超出的只报个数。清单读不出不影响更新。新版装好时把清单存进本机设置 `update.installed`；重启后只有它的目标版本等于正在运行的版本才显示「已从 A 更新到 B」，关掉记在 `update.installedSeen`，之后仍能从设置页打开。切渠道作废一轮时清单一起作废。这个功能合进来之后的第一次更新由旧版执行，看不到清单。
- **哪些构建查更新**（`updater::mode`）：只有发布的 macOS App。开发版、`--smoke-test` / `--notify-check`、测试模式（除非 `CAVIL_CLIENT_TEST_UPDATE=1`）、Linux 都不查，设置页也不出现「更新」一节。公钥（`tauri.conf.json` 的 `plugins.updater.pubkey`）空着时设置页写明「这一版没有带更新用的公钥」，从不去查。
- **只在测试构建里有的开关**（cargo feature `update-test`，`scripts/mac-update-check.sh` 用）：公钥可以从 `CAVIL_CLIENT_TEST_UPDATE_PUBKEY` 来，调试构建也会查更新。发布的 App 不带这个 feature。

## 发版

**开发版**（#215）：客户端改动每次合进 main，`.github/workflows/client.yml` 在 Apple 芯片的 Mac 上打包前把版本号改成 `X.Y.(Z+1)-dev.N`（`scripts/dev-version.mjs`：X.Y.Z 是三处一致的当前版本号，N 是 main 上的提交数；只改 CI 机器上的工作区，不提交），用发版签名私钥签名（和正式版同一把，维护者在 #215 定的），快速测试、打包、体积门槛、真实更新检查都过了以后，由 `publish development build` 这一步（`scripts/dev-release.mjs`）发成预发布：先建草稿带齐文件再发布，发版页正文末尾加一个 `### 更新内容` 小节，内容是 `RELEASE_NOTES.md` 相对上一个已发布的开发版新增的 `- ` 行（#348，装着的 App 靠它列出每版改了什么；上一版的提交读不到或没有新增就不加），已有更高的开发版就不发，只留版本号最高的 10 个（连标签一起删更旧的；正式版、daemon 的发版、别的形状一概不碰）。删除时逐个处理，每个分三步：先把它改成草稿（装着的 App 就看不到了；草稿上记着标签名和它来自的提交），再删它的标签，最后删草稿。每一步之前都重新读一次发版列表，按发版编号（不按标签名）找到它，用同一条规则重判它还该不该删，不该删（被改成不是预发布、同名换了一个发版、进了最新 10 个）就跳过。进度都记在 GitHub 上，不靠本机：哪一步暂时失败（读不到、删不掉、进程被杀），这个版本就停在「已发布」或「草稿」，下一次合并按同一规则接着做完；比当前最高开发版低的开发版草稿都在清理范围里。标签只在没有别的发版用它、而且仍指向草稿记下的那个提交时才删；读不到标签算暂时失败（留着草稿下次再来），确定不是它的标签（指向别的提交、别的发版在用）才放过标签、照删草稿。GitHub 没有「内容没变才删」的接口，最后一次重读和写之间的变化仍拦不住。每周定时和手动触发的打包也改成开发版号，但用一次性密钥、不发布。

**正式版**：改 `package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml` 的 `version`（三处一致）→ 合入 main → 打标签 `client/vX.Y.Z` 并推送。`.github/workflows/client.yml` 会在两台 Mac 上各打一个 dmg 和一个更新包（`tauri build --bundles app`，带 `createUpdaterArtifacts` + `scripts/make-dmg.mjs`）、过体积门槛（`scripts/size-gate.mjs`：dmg 和更新包每个 ≤ 20 MB）、跑 `scripts/mac-open-check.sh` 和 `scripts/mac-update-check.sh`，通过后生成 `latest.json`（`scripts/update-manifest.mjs`）并建 Release，附件是两个 dmg、两个更新包（`Cavil-Loop-<版本>-<芯片>.app.tar.gz`）和它们的签名（`.sig`）、`latest.json`（说明取自 `RELEASE_NOTES.md`，不标成 Latest，daemon 的每周发版不受影响）。

**更新签名密钥**（#184，维护者做一次）：公钥只放一处——`src-tauri/tauri.conf.json` 的 `plugins.updater.pubkey`：App 运行时用它验更新包，打包时打包工具用它，发版前生成 `latest.json` 那一步也用它逐个验签。发版标签的更新包用仓库 Actions secret `TAURI_SIGNING_PRIVATE_KEY`（有密码时再加 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`）签名。发版标签上缺这个 secret、或公钥是空的，打包直接失败；更新包的签名用公钥验不过（包被改过、签名坏了、不是这把钥匙签的、绑定的版本不对），生成 `latest.json` 那一步拒绝发版。合入 main 的打包（开发版，#215）也用这把私钥签名，同样缺 secret 或公钥空着就失败。每周定时和手动触发的打包用每次现生成的一对一次性密钥（同样的文件、同样过体积门槛和真实更新检查，但这些包不会被发出去）。

在自己的 Mac 上，进仓库的 `client/` 目录，**一条一条**跑下面的命令；任何一条报错就停下，先看下面「出错了怎么办」，不要继续上传。

**第一段：生成钥匙（只做一次）**

**第二段：写入公钥并检查这对钥匙（可以反复跑）**

第一条先进到仓库的 `client/` 目录（在仓库里任何位置跑都行）；第二条把公钥写进 `client/src-tauri/tauri.conf.json`，打印「已把公钥（密钥编号 …）写进 …」。后两条用私钥签一个小文件（会问一次密码，填第一段设的那个），再用刚写进去的公钥验它：看到「✅ … 签名有效」才算这对钥匙能用。

**出错了怎么办**

- **签名那一步密码输错了**：钥匙没坏，**不要**重跑第一段（它不会覆盖已有的钥匙，会报 `already exists`）。把第二段整段再跑一次，输对密码即可——它会重新写入同一把公钥、重新签名、重新验签，钥匙文件不会变。
- **密码忘了、或者想换一把钥匙**：只有在还没用这把钥匙发过版时才这样做（发过版的话，已装好的 App 只认旧钥匙，换了以后大家要再手动装一次）。先删掉旧的两个文件，再从第一段开始：

<!-- update-key-steps:replace:begin -->
```bash
rm ~/.tauri/cavil-loop-updater.key ~/.tauri/cavil-loop-updater.key.pub
```
<!-- update-key-steps:replace:end -->

- **不想继续了**：`git checkout "$(git rev-parse --show-toplevel)/client/src-tauri/tauri.conf.json"` 退回公钥那一处改动；钥匙文件留在 `~/.tauri/` 里不影响任何东西。

钥匙检查通过之后：

1. 仓库 **Settings → Secrets and variables → Actions → New repository secret**：`TAURI_SIGNING_PRIVATE_KEY` = 私钥文件全部内容；设了密码再建 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。列表里出现这两个名字就算成功。私钥和密码不要贴到任何评论里。
2. 把改过的 `src-tauri/tauri.conf.json`（只多了公钥）提交，随一个版本号升级一起合入 main。
3. 私钥另外备份。丢了只能换一把新的：已经装好的 App 认不出新钥匙签的包，大家要再手动装一次（含一次放行）。

`test/unit/update-key-steps.test.ts` 把上面三段命令原样取出，在伪终端里照上面写的走：正常一遍；签名输错密码 → 只重跑第二段 → 验签成功、钥匙文件一个字节没变；重跑第一段会被拒 → 跑「换钥匙」那段 → 重新生成并检查成功，钥匙换成了新的。
