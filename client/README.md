# Cavil Loop 客户端

`client/` 是一个本地桌面客户端（Tauri：界面 TypeScript + React，后台 Rust），把多个 GitHub Project 看板和仓库合进一个视图。它只和 `api.github.com` / `github.com` 通信（例外三处：头像图片从 GitHub 的头像地址 `avatars.githubusercontent.com` 加载，#155；讨论里的图片从 GitHub 自己的附件地址和图片代理加载，GitHub#205；自动更新下载更新包时跟着 GitHub 的跳转到 `release-assets.githubusercontent.com` / `objects.githubusercontent.com`，只有外壳的更新插件访问它们，窗口的 Content-Security-Policy 不放开，#184），和 daemon 没有任何交互，也不读 daemon 的配置。设计与拆分见 GigleAI/cavil-loop#135，本目录的第一块是 #136（骨架），#138 加上了查看与修改，#137 加上了搜索筛选与表格视图，#151 把外壳从 Electron 换成 Tauri（安装包从 134 / 139.5 MB 降下来），并把 GitHub 凭据整段收进 Rust 后台，#155 加上了头像、详情折叠与浮动、PR 跟在关联 issue 下面、⌘+ / ⌘- 缩放。#214 在表格每个分组底部加了「＋ 新建 issue」：对话框先列出会带上的迭代 / 状态 / 里程碑，创建时只按这份清单写，写前现读核对里程碑，对不上一条都不写。

## 开发

要装 Rust（`rustup`）。单元测试和界面测试会先 `cargo build -p cavil-harness`，把真实后台当子进程驱动。

```bash
cd client
npm ci
npm run test:rust              # Rust 单元测试（后台 + 外壳；先构建一次界面，外壳编译要用）
npm test                       # 单元测试（真实后台子进程），末尾打印「负对照：跳过 N 项」
npm run test:mutation -- --changed  # 负对照（MUTATION=1），只跑和本次改动相关的项（只在手动时跑；CI 只在每周发版门禁里跑全部）：基线约 30 秒，之后每项几秒到十几秒（只跑它点名的测试所在文件）
npm run test:mutation          # 全部负对照（很慢，每周发版门禁里自动跑，或手动跑）：先跑未改动的基线，再逐项改坏一处（含 Rust 后台），指定的断言必须失败
npm run typecheck
npm run test:e2e               # 界面测试（WebKit；WebKit 起不来的机器加 CAVIL_E2E_ENGINE=chromium）
npm run test:tauri             # 真实 App（Linux：要 tauri-driver、WebKitWebDriver，CI 用 xvfb-run；约 6 分钟，同步节拍是正式的 60 秒）
npm start                      # tauri dev：本机跑起来（Linux 要装 libwebkit2gtk-4.1-dev；凭据只在内存里，退出即忘）
npm run dist:mac               # Mac 上：打 .app 和 dmg（要 dmgbuild：pip install dmgbuild）
```

## 规则（改代码前读）

- **GitHub 是唯一数据源**：缓存只从 GitHub 往下写。一个来源要么整个读成功、整条覆盖本地，要么沿用上一轮——任何一页失败都不能把半份结果写进去，否则「读失败」会看起来像「条目消失」。GitHub#229 的「先显示的修改」不进这份缓存：它们另存一行（见下文「修改先显示」），只叠在界面上；看板数据仍只装 GitHub 读回来的值。
- **缓存只属于一个账号**：退出登录清空缓存（GitHub#229：没确认的修改和它同一步删掉；本次运行记住的详情、标签 / 里程碑列表、新建 issue 的结果条也一起清空）；启动时凭据和上次读缓存用的不是同一把（只比对哈希），在 GitHub 确认账号前一律不显示旧缓存；一轮同步发出后有人退出 / 换账号，这一轮整个作废；来源在同步途中被删除（或删了又加）时，这一轮对它的结果不写入。
- **登录要么完整成功，要么什么都不留**：凭据只在登录最后一步写入，所有写入 / 删除在一条队列里依次执行；写完立刻核对这次登录是否已被取消、退出或被更新的登录取代，是就在同一步里删掉，不会误删排在后面的新凭据。
- **去重按条目本身**（`仓库#编号`），不按来源。迭代、状态属于各个 Project：两个 Project 值不同，同一条目在两列各出现一次；里程碑属于仓库。
- **凭据只在 Rust 后台**（#151）：登录、续期、凭据写入队列、可信名单、退出全在 `src-tauri/crates/core`，只有这一份实现。窗口里的应用逻辑只拿到「未登录 / 等待授权（短码、网址）/ 已登录（账号、会话编号）」，要发 GitHub 请求就交给后台代发——后台加上凭据，只放行 `api.github.com`（地址按解析结果比，不按前缀），窗口自己带的 `Authorization` 头被丢掉，会话结束后一律拒绝。描述凭据的几项设置（可信名单、缓存绑定的凭据、缓存所属账号、登录时的 Client ID）窗口既读不到也写不了。`test/unit/backend-boundary.test.ts` 把一次完整的登录、同步、修改、续期、退出里所有跨过边界的命令和回答扫一遍，里面不许出现任何令牌。钥匙串写入走 `security -i` 的标准输入，不进命令行参数（和 Electron 版同一个钥匙串条目，升级不用重新登录）。
- **测试模式**（`CAVIL_CLIENT_TEST_MODE=1`）只给自动测试用：可以把 GitHub 地址换成本机回环地址的假服务，换成别的主机会直接报错（判断在 `src-tauri/crates/core/src/platform.rs` 的 `select`）。
- 只和 `github.com` 通信（头像图片例外：`avatars.githubusercontent.com`，只用来加载图片，不带凭据）；外链一律用系统浏览器打开，且只放行 GitHub 的地址。

### 查看与修改（#138）

- **修改直接发给 GitHub，成功后立即重读那一条**：只替换缓存里那一条（所在的每个来源各一份，同样受「退出 / 换账号 / 来源被删」的保护）；同步正在进行时再补一轮。重读失败不影响修改本身，界面会说明，下一轮同步补上。离线时所有修改入口变灰，不排队、不重试。
- **修改先显示**（GitHub#229，规则全在 `src/data/edits.ts`，controller 只负责存、发、喂读取结果）：标签单个增删、里程碑、看板状态、看板迭代这四种，点下去就显示新值，详情、看板卡片、表格一致（`getBoardData` 一处叠加），界面不再等 GitHub、不再整页变灰；同一条的修改按点的顺序一个接一个发，不同条之间互不等待。合并、关闭、交给 agent / 托管（见下文「关闭 / 合并 / 托管 / 交给 agent 不卡对话框」）、评论、改正文、新建 issue 不在此列。
  - **一个字段一条记录**：目标值、点之前的值、所有结局没定的请求；整条记录存在快照表的 `__edits__` 一行里（`EDITS_KEY`），和缓存同受会话检查、同一事务清空。先存成功再发；存不上就不发，并说「没能存到本机，这次修改没发出」。请求状态先存成「已发出」再真的发，所以发出前后被杀，重开后都读作「没确认」，不会当成「没发过」。重开 App 不会自动发出任何修改。
  - **确认时刻 C**：收到「已接受」= C；或者一次在目标请求发出之后才发出、读到的正是目标值的读取——仅当目标值和点之前的值、其他请求的值都不同（GitHub 上原本不可能有它）——也算 C。之后只有 C 之后才发出的、真的写进看板数据、带着这个字段的读取才算数：读到目标值 → 核对完（还有值不同的没答复旧请求时，观察到最晚那个发出后 2 分钟，期间重读两次）；读到旧请求的值 → 「没保存上，可能被它改回去了」；读到别的值 → 有人在之后改过，以 GitHub 为准。C 之前发出的读取一律不算。详情读取不算（它不带里程碑和看板字段，也不写看板数据）。
  - **晚回来的旧读取不落地**（PR #240 复审第 5 轮）：每次读取（整轮同步、单条重读）都记下发出时刻；看板数据按「来源 + 条目」记住已落地的最新一次读取。比它更早发出的单条重读晚回来时，不写进那个来源（内存、磁盘都不写）；整轮同步落地时，开始之后才重读过的条目保留那次重读的副本。所有落地在同一条写入队列里依次算、依次写：每次都在前一次写完、内存更新之后，按那时的内存算要写的行，所以后写的不会把先写的盖掉。重读仍然不占这一条的修改队列。
  - **凭 GitHub 的值做决定只认已落地的读取**（PR #240 方案修订 1）：读取时间只在本机写成功、账号没换、来源还在之后，和内存里的行一起提交；写盘失败、账号切换、来源被删的那次读取不留任何痕迹，不算证据。修改的核对、观察期收尾、重新发送前的检查、「读不到 GitHub」的显示，都通过同一个取值入口（`evidence`）从看板数据里取这一条的值，只认发出时间不早于这次检查的读取；单条读取的原始答复不交给任何调用者。有足够新的证据就按它判断（检查本身晚回来或失败也一样），没有就按「读不到」拦下重新发送。例外：这一条不在任何来源里时，用这次读取自己的标签、里程碑（看板字段不走例外）。
  - **GitHub 拒绝（4xx / GraphQL 报错）**→「没保存上」；**没收到明确答复（断线、超时、5xx、408 / 429）**→「没确认」。两种都保留新值、并排显示「GitHub 现在」的值和读到的时间，可「重新发送」或「放弃」。重新发送先读 GitHub：仍是点之前的值（或已经是目标值）才发；有人改过、或读不到，就拦下，要再点「仍然覆盖 / 仍然发送」（维护者在 #229 选的 A）。读和写之间的空档、观察期 2 分钟之后才执行的旧请求，都拦不住，写在 #229 的限制里。
- **新建 issue 不卡对话框**（GitHub#229）：发不出去的（离线、标题空）当场拒绝、对话框留着；其余点「创建」就关，结果显示在看板上方。① 全部成功：自动打开新 issue；② GitHub 回了编号但没加进看板 / 字段没设上：只给「打开 #N」「再试加入看板」（只对这个编号补，不再新建）；③ 没收到明确答复：一直算「不确定」，列出最近 10 分钟这个账号在这个仓库建的同标题 issue（只是链接），可复制草稿，不给带「创建」按钮的草稿，也不对任何候选补写；④ GitHub 明确拒绝：给「重新打开草稿」，原样填回。
- **关闭 / 合并 / 托管 / 交给 agent 不卡对话框**（GitHub#250，判断全在 `src/shared/ops.ts` 一处，发送入口、按钮、面板和看板上方的结果条都用它；controller 只负责存、发、重读、查证据）：点「确认」（交给 agent 没有确认框，点按钮即发）后对话框立刻关，结果条先写「正在关闭 issue #N…」，GitHub 一应答就更新；应答之后的重读在后台做，不再挡对话框。每次操作是一条记录，跟缓存存在一起（同一个账号、退出登录一起删，重启还在），面板关了再开、换条目再回来看到的是同一条。
  - **每一步分开记**：关闭 = 关 + 附带评论；合并 = 合；托管 = 加托管标签 + 加 `pending/agent` + 摘 `pending/human`；交给 agent = 后两步。每一步只有「等应答 / 成功 / 被拒（GitHub 明确拒绝）/ 不确定（断线、超时、5xx 等，没收到明确答复）/ 没发」五种，前一步不是成功后面一律不发；结果条逐步写清，不把部分成功说成全没做，也不把「不确定」说成「没发出去」。
  - **一条规则管防重复**：同一条上这五种操作互相冲突。只要这一条还有一次操作没结清，从哪里都发不出去（后台在发送入口拒绝，面板按钮变灰并写原因；回复、改标签 / 里程碑 / 看板字段不受影响）。结清只有三种：每一步都有确定结果、且有成功的步骤时等到一次应答之后发出并已落进缓存的重读（关闭 / 合并还要读到「已关闭 / 已合并」，超过 2 分钟没读到就给「去 GitHub 页面核对」「已核对，解除锁定」）；不确定的步骤被正面证据证实；人点「已核对，解除锁定」（只解本机的锁，不发任何请求）。任何一步不确定，整条就一直锁着；不确定的步骤没有一键重发。
  - **证据只认正面的，而且必须是这次的**：第一个请求发出前先读一次这一条最新的 100 条评论和 100 条标签记录，记下已有的；之后查证只认这份名单里没有的记录（PR #255 代码复审第 1 轮：一分钟前同内容的旧评论、旧的「加派工标签」记录都不能证明这一次）。关闭 / 合并看应答之后（重启前没收到应答的，看发出之后）的重读是否已关闭 / 已合并；附带评论看有没有本账号发的、内容完全相同的新评论；加标签看有没有本账号加这个标签的新记录（`pending/agent` 被 daemon 接手后会被摘掉，所以不看它现在在不在）；摘标签看新记录或重读时已不在。发出前那次读取失败的，这一步永远不能自动证实，只能人核对后解锁。读不到、查不到都只算「仍不确定」，绝不算「没发生」。没应答时自动查一次，结果条上可「重新查证据」。
  - **按钮**：首步被拒 →「重新关闭 / 合并 / 托管…」，对话框里原样还原；托管 / 交给 agent 主步成功、后面的标签步骤被拒 →「补做剩下的步骤」，先重读，只补被拒或因此没发的那几步（已就位的跳过；成功过或不确定的派工标签永远不补）。
  - **草稿另一条规则**：关闭原因、附带评论、合并方式各看自己那一步——那一步确认成功才自动删；被拒、没发、不确定都留着，直到用它重做成功或人点「丢掉草稿」。结清、解除锁定、关掉结果条都不删草稿（关掉后面板顶部留一行「点这里找回」）。评论被拒或没发可「放进回复框」，不确定只给「复制原文」，还在等应答时都不给。用「放进回复框」发出的回复带着是哪次操作的草稿，结果记在那次操作上、与面板还开不开无关：发出 = 草稿用掉；明确被拒 = 还能再放；没收到应答 = 不确定，只给「复制原文」，不会再放进回复框（PR #255 代码复审第 1 轮）。这条回复也算这次操作的一步（代码复审第 2 轮）：还在路上时整条算「进行中」、没收到应答时算「不确定」，都锁住这一条，也不给「重新关闭」；「正在发送」先存进本机，存不上就不发；查证同样只认发送前没有的评论；证实发出后只算评论用掉，关闭原因等其余草稿照留，之后「重新关闭」不会再带回这条评论。每次操作和这条回复都只属于开始时的那次登录（代码复审第 3 轮）：从头到尾用同一个绑定该次登录的连接（后台对已结束的登录一律拒绝），每次等待之后都重新核对登录和记录、存盘没成功就停；中途退出登录或换了账号，什么都不发，也不会用新账号代发。
- **改完之后列表跟着动**（#177）：合并或关闭 PR 成功后，除了 PR 本身，缓存里和它关联的 issue 也立即重读——关联取两处的并集：GitHub 报的「这个 PR 会关掉的 issue」（翻页读完，没有条数上限），加上缓存里侧栏「关联 PR」列着它的 issue；只重读缓存里有的。这份清单没读全（某一页失败）时，已读到的照样重读，结果里写明「没读全」，不当成完整清单。另外，任何一次修改成功后（包括成功但带警告的）约 5 秒再自动同步一轮，连续改几下只补一轮（从最后一次算起）；被拒 / 失败的修改不补，退出登录时取消。这一轮是给 GitHub 自己在后台晚做的事（看板「关闭 / 合并 → Done」之类的自动化）准备的：5 秒只是同步的时间点，不保证 GitHub 那时已做完，没做完的照旧等 60 秒的定时同步。
- **标签只发「加这个 / 删这个」**（`POST …/labels {labels:[一个]}`、`DELETE …/labels/<名字>`），从不整份覆盖——整份覆盖会把别人刚加的标签冲掉（负对照守着）。
- **合并一定带上看到的提交**（`sha`）：期间被推了新提交，GitHub 回 409，界面说「请刷新」，什么都不合；合并方式只列仓库允许的，默认是这个仓库上次选的方式（没选过就用最近一次在任何仓库选的；只记在本机，GitHub#175）；确认框只写一句「把哪个分支合进哪里、用什么方式」；不提供绕过分支保护的管理员合并。关闭 PR 先关、关成功才发附带的评论（结果怎么报、怎么防重复见上文 GitHub#250 一条）。
- **关闭 issue**（GitHub#180）：详情底部「发送」那一行左侧的「关闭 issue…」，只在详情现读到这个 issue 仍开着时出现（PR 的关闭仍在 PR 状态框里）。确认框里选关闭原因「已完成」（默认）或「不计划」，可附一句评论；发 `PATCH …/issues/<n> {state: closed, state_reason}`，关成功才发评论，评论没发出去只给警告、不再重发关闭（GitHub#250 起对话框不等结果，见上文）。原因只认这两个、条目必须是 issue，否则发送前拒绝。「重复」要指定重复的是哪一条、重新打开 issue / PR，都不在客户端里做，去网页。
- **里程碑**改的是这一条所在仓库里同名的那个；没有就拒绝并说明，什么都不发，不新建。
- **迭代 / 状态**只改那张卡所在 Project 的值，用那个 Project 自己的字段和选项 id；拖卡时卡上有两个 Project 就两个都改，其中一个没有目标迭代就整次拒绝。「未加入看板」的卡拖进迭代列先问「加入看板 X 并设为这个迭代？」。GitHub 说这个账号不能改某个 Project（`viewerCanUpdate`）时，那个 Project 的入口变灰并说明，标签 / 里程碑照常可改。
- **详情**每次打开都从 GitHub 现读；GitHub#229 起本次运行读到的最近 50 条记在内存里（不写盘，退出登录清空），再次打开先显示上次的内容、标题下写「显示 HH:MM 读到的内容 · 正在更新…」，读回来再换；评论、评审、每个评审下的逐行评论全部分页读完（任何一页失败就整次报错，不显示半份讨论）；最新在上，正文最老所以在最下，逐行评论挂在所属评审下面。默认只展开最新一条（没有评论时就是正文），其余折成一行（作者、时间、开头约 80 字），点一下展开，面板上有「全部展开 / 全部收起」（#155；折叠用浏览器自带的 `<details>`）。GitHub 渲染好的 HTML 放在 `sandbox` 隔离框里（不同源、不能导航，有自己的 CSP），链接用系统浏览器打开。框里唯一能跑的是客户端自己的一段固定脚本（GitHub#193，`src/renderer/frameScript.ts`），见下一条。
- **开着的详情跟着同步更新**（GitHub#226，规则在 `src/renderer/autoRefresh.ts`）：不另设定时器，挂在看板的同步轮上（60 秒一轮、改完后 5 秒补的一轮）。一轮里装着这一条的来源（Project 或仓库）有一个完整读成功，而且读到的这一条「最后更新时间」和详情上次读取时看板上的不一样，就重读一次详情；只有别的来源成功、或这一条所在来源读失败（沿用旧数据），不算有新数据。打开中的 PR 若上次读到检查「进行中 / 等待中」或「能否合并」还没算出，每轮都重读，出结果就停——检查结果变化 GitHub 不算「这一条有更新」，所以检查结束后又被重新触发、而这一条本身没有别的变化时，不会自动发现，点「刷新这一条」。读回来的内容和屏上一样就不换（讨论区不重绘，选中的文字不丢）；回复草稿、编辑框、合并方式的手选、已展开的条目和滚动位置都不动。自动重读失败不弹错误条，屏上内容留着，下面一行小字「自动更新失败，显示的是 HH:MM 的内容」，下一轮再试。提交修改（合并、发评论、加标签、勾选择题……）一开始，所有还在路上的详情读取都作废（它们带的是改之前的 GitHub）；提交进行中到了同步轮不自动读；提交成功或失败后都立刻重读一次。
- **在详情里勾选择题**（GitHub#193）：正文和普通评论里的任务列表勾选框（`- [ ] A. …`）可以直接点，效果和在网页上勾一样——原文里那一个 `[ ]` 变成 `[x]`（或反过来），其他字节不动，然后重读详情（已展开的条目和滚动位置不变）。规则：
  - **只有能确定的才可点**：GitHub 说这个账号能改这一条（`viewerCanUpdate`），而且客户端按 GitHub 的 markdown 规则（`src/data/taskList.ts`，CommonMark + GFM 任务列表）从原文读出的框，和 GitHub 渲染出的框逐个一致（个数、勾没勾）；任何一项没读到或对不上，这条的框只读，下面写原因。评审意见和代码逐行评论里的框一律只读（去网页勾）。离线、有修改在途时全部变灰。
  - **写前现读**：GitHub 改评论没有「内容没变才写」，所以写之前按评论 / 正文的 id 现读一次：必须仍属于这一条、这个账号仍能改、原文和点的时候看到的一字不差，目标那个框正处在点之前的状态；任一不符就不写、重读、提示「刚被改过」。现读失败就报错，不拿旧原文写。现读和写入之间仍有空档（长度未测、给不出上限），这期间别人改了同一条会被覆盖——网页上勾选也一样。同一条评论一次只允许一个写入在途。写用 GraphQL `updateIssueComment` / `updateIssue` / `updatePullRequest`。
  - **框里的脚本**：时间线隔离框的 `sandbox` 有 `allow-scripts`、没有 `allow-same-origin`（碰不到窗口的对象、存储和后台通道），自己的 CSP 是 `connect-src 'none'`（发不出请求）。能跑的只有 `FRAME_SCRIPT` 这一段：它只把「哪条评论第几个框、勾没勾」和「哪些条目展开、滚到哪」用 `postMessage` 告诉窗口，变化的数据放在 `<body data-…>` 里，脚本本身是常量。`srcdoc` 框同时受窗口和自己两层 CSP 约束，所以两层都按内容哈希只放行它：窗口那层写在 `src-tauri/tauri.conf.json` 的 `script-src`，框那层由 `TIMELINE_CSP` 生成。改了脚本就要同时改 `FRAME_SCRIPT_HASH` 和配置里的哈希，`test/unit/taskList.test.ts` 核对三处一致。窗口只认来自当前这个框（`event.source`）、当前这次渲染编号的消息，而且自己再核一遍条目可点、序号在范围内。回复预览框不跑任何脚本。
  - **测试**：`test/fixtures/tasklists.github.json` 是 GitHub 自己对 18 种写法和两条真实评论的渲染（`node test/fixtures/record-tasklists.mjs` 重录，不手改），读框规则逐条和它对拍；`test/e2e/frame-policy.spec.ts` 两层策略各测各的（另一层在测试页里放宽），每组都要「框内脚本跑了」且「注入的脚本、事件属性一个没跑」；`test/tauri/real-window.spec.ts` 在真实 App、正式策略下真点一次，假 GitHub 恰好收到一次只差一个字符的修改，框里拿不到 IPC、发不出请求。
- **详情顶部的类型徽章**（#172，`src/renderer/KindBadge.tsx`）：issue 和 PR 靠图标形状（圆圈带点 / 分支）和全称（「Issue」/「Pull Request」）区分，底色是 GitHub 的状态色。类型、状态、关闭原因和草稿标记都取自看板里的这一条，打开就有；草稿标记优先用详情现读的（更新），详情还没读到或读取失败时用看板读到的，两处都不知道就不当草稿；只有仍开着的草稿 PR 变灰写「草稿」，已关闭、已合并优先。图标是内联 SVG，不加载任何外部资源。
- **状态配色跟 GitHub 一致**（PR #174 复审时维护者要求）：开着 = 绿；PR 关闭未合并 = 红；PR 已合并、issue 按「已完成」关闭（或没记关闭原因）= 紫；草稿 PR、issue 按「不计划 / 重复」关闭 = 灰（徽章文字补「（不计划）」「（重复）」）。哪种情况用哪种颜色只在 `src/shared/stateTone.ts` 一处判断，详情徽章、看板卡片、表格行都用它；色值是 GitHub 设计系统 Primer 的状态色（浅色 / 深色各一套，在 `styles.css` 的 `--state-*`）。关闭原因和草稿标记三条读取路径都读：Project（GraphQL `stateReason` / `isDraft`）、仓库列表（REST `state_reason` / `draft`）、改完后的单条重读，所以草稿 PR 在徽章、卡片、表格里都是灰色；徽章优先用详情现读的草稿标记（更新），详情没读到时用看板读到的。
- **同步中点刷新 = 重新开始**（GitHub#217，`restartSync` in `src/app/controller.ts`）：刷新按钮和 ⌘R 在同步中也能点，图标在转。正在读 GitHub 的这一轮被放弃——它读到的东西不进界面、不进缓存，也不再发下一页（已经发出的那一个请求由后台跑完、结果丢掉；后台没有取消单个请求的接口）——新一轮马上开始。正在续期登录或正在写缓存的那一段不打断（半路断开可能丢登录 / 让新旧两轮抢着写），做完马上重来。60 秒定时器等自动触发仍是排队，不互相打断。详情的「刷新这一条」读取中也能点，新的读取作废旧的（同上一条的规则）。
- **详情面板按「这一次打开」认回应**（`src/renderer/openSession.ts`，四种异步调用——读详情、读仓库候选、预览、修改——都走它）：每次打开一条（换到别的再回来、关掉再开都算新的一次）是一个新面板，上一次打开发出的回应一律不进新面板；同一次打开里，同类的新调用作废旧的（改完后的重读胜过慢的刷新，改了字后旧文字的预览不显示）。修改晚到时，结果显示在看板顶部（带编号），不动新面板的草稿、忙碌状态和对话框。负对照里有真实界面的项（`runner: 'e2e'`），`MUTATION=1` 时自动构建并驱动真实窗口（WebKit + 真实后台）。
- **图片只从 GitHub 的地址加载**：`github.com` / `api.github.com`、头像地址 `avatars.githubusercontent.com`（#155），以及 GitHub#205 维护者放开的 GitHub 自己的图片地址——附件 `private-user-images.githubusercontent.com`（GitHub 返回的正文里粘贴截图的地址，带有效期约 5 分钟的签名，不带凭据就能取）、2023 年以前的老附件 `user-images.githubusercontent.com`、图片代理 `camo.githubusercontent.com`（外链图片由 GitHub 代取）。只按完整主机名放行，不放开 `*.githubusercontent.com`；名单在 `src/shared/avatar.ts` 一处，页面的 CSP（`src-tauri/tauri.conf.json`）由 `test/unit/detailHtml.test.ts` 逐项核对与它一致，「在浏览器里打开」的放行规则（`src-tauri/crates/core/src/engine.rs` 的 `GITHUB_IMAGE_HOSTS`，点图片打开原图）由 `test/unit/github.test.ts` 逐个地址核对。Electron 版还有第二层「主进程拦掉窗口发往其他主机的一切请求」，Tauri 用系统网页引擎，没有这一层（#151 方案里写明的取舍）；补偿是凭据从不进窗口，加载图片也从不带凭据。不在这些地址上的图片不加载，那一条下面会写「有 N 张图片不在 GitHub 的地址上…点『在网页上看』」。详情开着超过约 5 分钟后才第一次加载的附件图片可能因签名过期而裂开，重新打开这一条即可。
- **交给 agent / 托管**（GitHub#205）：详情底部发送按钮左边，条目开着就有，不用先回复。「交给 agent」= 加 `pending/agent`、摘 `pending/human`（先加后摘：第二步失败也不会两个都没有）；「托管（自动合并）…」先弹确认框，再加托管标签（默认 `autopilot`），然后同「交给 agent」——GitHub#250 起两者都不等结果，每个标签步骤分开报，托管标签加上了而派工标签没加上时结果条逐步写明，可「补做剩下的步骤」。三个标签名都在设置里改，要和 daemon 配置一致；托管标签留空就不显示「托管」按钮。确认框分三段（加 / 摘哪些标签、之后发生什么、怎么叫停），底部「不再提示」默认不勾（GitHub#231）：勾上并点「确认托管」后，按钮变成「托管（自动合并）」（没有省略号），点一下直接托管、不再弹框；点「取消」不记。设置页「交给 agent / 托管用的标签」一节的「托管前先弹确认框」勾回来就又弹框。这一项存在本机设置里，单独一项，导入网页视图不会改到它。
- **有冲突时**（GitHub#205）：PR 和目标分支有冲突（GitHub 说 `CONFLICTING` 或 `DIRTY`）时，PR 状态框顶部一条红色提示，合并按钮变成「有冲突，不能合并」且不可点。
- **编辑正文 / 评论**（GitHub#205）：GitHub 说这个账号能改的正文和评论下面有「编辑」（评审意见、逐行评论不能在客户端改）。点开是整段 markdown 原文，保存时和勾选框一样先现读：仍属于这一条、仍能改、原文和开始编辑时一字不差才写，否则不写、提示「被别人改过」，编辑框里的文字保留。评论不能改成空的。同一条一次只有一个修改在途。
- **新建 issue**（GitHub#205）：标签用和详情一样的选择器（可筛选、带 GitHub 颜色），选中的显示成彩色标签；建好后加入哪些看板逐个勾选，列出全部已添加的看板（不只是顶栏当前勾着的）；从表格分组的「＋ 新建 issue」打开时，这一组的迭代 / 状态只写进勾了的看板，「会带上」的说明紧跟在看板勾选框下面（里程碑那一行留在仓库下面）。预先勾哪个（GitHub#231，两个入口同一条规则，`src/data/newIssueBoards.ts`）：在全部已添加、已同步过的看板里，数一下各自装着所选仓库的条目有几条，只勾条数最多、而且这个账号能改的那一个；并列时取先添加的；所有看板都没有这个仓库的条目就一个都不勾。和顶栏当前勾着什么无关（数的是每个看板自己的同步结果，只勾了仓库来源时照样能勾上它的看板）。还没完整同步过的看板不当成「没有」，勾选框下面写一行「看板「X」还没同步完，默认勾选没把它算进去」。换仓库、看板同步完都会按新数据重算；手动勾过或取消过任何一个后不再自动改。只加入勾了的看板；勾了客户端不认识的看板（比如刚被删掉）整次拒绝、什么都不建。
- **新建时交给 agent / 托管**（GitHub#245）：新建 issue 对话框「建好后」三选一：「只建 issue」「交给 agent」「托管（自动合并）」（设置里托管标签留空时没有第三项）。选了交接的，标签和 issue 在同一次创建请求里一起带上（托管 = 托管标签 + 派工标签，标签名取设置里那两项），不是建完再补；所以没有确认框，选项下方常驻一行说明之后会发生什么、怎么叫停。规则只有一份（`src/shared/handoff.ts`），对话框、创建请求、「到 GitHub 网页上继续新建」共用。仓库标签分三种情况：还在读取 → 记住的选项照常选中，「创建」等读完再能点；读不到（断网、权限、超时）→ 写「读不到标签，暂时不能确认」，本次只能建普通 issue，不说成「没有标签」；读到了但确实没有 → 该项不能选并写明缺哪个（发出去 GitHub 会自己新建这个标签）。创建前数据层再现读一次仓库标签核对，对不上整次拒绝、什么都不建。GitHub 对没有写权限的账号会悄悄丢掉新 issue 的标签，建好后核对返回的标签，缺了在结果条写明缺哪个、「还没有交给 agent」（手选的标签被丢掉也会提示）。记住：只有在本次对话框里亲手点过、并且确实用它建成了的选项才存进本机设置；因读不到 / 缺标签自动退回「只建 issue」、或点了「取消」都不改记住的值。首次默认「只建 issue」。单独一项本机设置，导入网页视图不会改到它。
- **粘贴图片**（GitHub#205，维护者选 A）：GitHub 的图片上传只给网页登录状态用，没有第三方程序能调的上传接口，客户端没法把图片放到 GitHub 上。在新建 issue 正文、回复框、编辑框里粘贴只有图片的内容时，不再悄悄没反应：提示「客户端不能把图片上传到 GitHub」，按钮「到 GitHub 网页上继续写」——新建 issue 把标题、正文、标签带进网页的新建页；回复和编辑把已写的文字复制到剪贴板、打开这一条的网页。带文字的粘贴照常贴进来。
- 被拒时界面照实显示原因（含 GitHub 的原话），GitHub 上什么都不改；测试对每种被拒情况核对假 GitHub 的 `digest()` 前后相同。
- 缓存格式升到第 2 版（多存了写入要用的各种 id），#137 再升到第 3 版（多存了作者、父 issue、子 issue 进度、关联 PR、网页视图）：升级后第一次启动会丢掉旧缓存、重新同步一次。

### 头像、浮动详情、PR 跟在 issue 下面、缩放（#155）

- **头像**：卡片（作者、负责人）、表格（作者、负责人两列）、详情（作者、负责人、讨论里每条的作者）都在名字前放头像，按登录名从 `avatars.githubusercontent.com` 取（不改查询、不改缓存）。已删除的账号、图片加载不出时显示首字母：首字母垫在图片下面，图片加载不出就露出来，不靠脚本（讨论框里唯一能跑的是 GitHub#193 那段只管勾选框的固定脚本，见上文「在详情里勾选择题」；评论内容里的脚本一律不跑）。
- **详情浮在看板上**：贴右、从搜索栏下方到底，看板宽度不变；左边缘可拖动改宽度（最窄 360px，窗口左边总留 120px 看板），宽度存进视图设置，关掉再开、重开 App 都保持；窗口变窄时自动收窄，变宽恢复。右上角「收起 ›」、Esc，或在面板以外的地方点一下收起（GitHub#191：点卡片、表格行标题是换一条，不收起；按下鼠标时有确认框开着、回复框里有字、拖动滚动条或从面板里拖选到外面都不收起；用键盘按工具栏按钮也不收起；在讨论框里点，包括勾选择题，算面板里面）。Esc 的规则：光标在回复框里、回复框里有没发出的文字、或有对话框时，Esc 不收；按钮原来叫「关闭」，和「关闭 issue」撞词，GitHub#180 改名）；点过讨论之后键盘在讨论框里，Esc 传不到外面，要先点一下讨论以外的地方（面板空白处、标题）再按 Esc，或直接点「收起 ›」——讨论框保持隔离、不把按键转给窗口，这是维护者在 PR #171 选的（当时框里不跑任何脚本）。GitHub#193 之后框里多了一段固定脚本，它只报告勾选框和展开 / 滚动位置，不转发按键，框也仍然不同源，所以这条行为不变。
- **PR 跟在关联 issue 下面**（视图设置里的开关，默认开，看板和表格都生效；规则只有一份：`src/data/prNest.ts`）：关联关系是 issue 侧栏的「关联 PR」（会关掉这个 issue 的 PR）。只在同一列 / 同一组里归在一起，PR 缩进一格带「↳」；排序是「更新时间」时，这一对按两者里更晚的那个排，其他排序按 issue 的位置；一个 PR 关联同列几个 issue 只跟在排得最前的那个下面；一个 issue 有几个 PR 时按更新时间从新到旧；分泳道时 PR 跟进 issue 的泳道；表格同时缩进子 issue 时，PR 排在子 issue 前面。只从仓库来源读到的 issue 不知道关联 PR（表格里那格显示「—」），它们不归组。
- **缩放**：macOS 菜单「缩放」里的放大 ⌘= / 缩小 ⌘- / 实际大小 ⌘0，档位 50%–200%，整个窗口（包括详情里的讨论）一起缩放；档位存在后台本地存储（`src-tauri/crates/core/src/zoom.rs`），重开 App 恢复。菜单快捷键只在 macOS 上有（其他平台的构建只用于测试）。

## 界面的样子（#181）

- **颜色只在一处定**：`src/renderer/styles.css` 顶部的设计变量（浅色一份、深色一份，跟随系统）。issue / PR 的状态色仍只由 `src/shared/stateTone.ts` 决定。图标是 `src/renderer/Icons.tsx` 里自己画的线条图，不引入图标库、不从网络加载。
- **标签颜色一个函数**：看板卡片、详情、表格的标签都走 `src/renderer/colors.ts` 的 `labelStyle`——浅色下实心底、黑白字里挑对比度高的；深色下 18% 透明底 + 同色边框 + 提亮到 4.5:1 的字。
- **可读性和窄窗口有测试**：界面测试「GitHub#181 look」在真实窗口里把登录、看板、详情、表格、设置每段可见文字和它实际背后的底色（逐层叠加、算上透明度）比对，浅色和深色都要 ≥ 4.5:1（大字 3:1，变灰的按钮按规范豁免）；深色下三处标签必须是半透明底；1024×700 的窗口里两层顶栏不重叠、不横向滚动。讨论框（隔离的 iframe）不在这项检查里。
- **来源多了顶栏横向滚动**：顶栏的数据来源是一条可横向滚动的条（鼠标滚轮、触控板、Tab 都能滚到），每个来源保持能看清的名字（最长 220px，完整名字悬停可见），不会被挤没或裁掉。界面测试「GitHub#181 many sources」加 20 个仓库，在 1024 和 1280 宽下用滚轮滚到末尾和中间的来源，真点它的勾选框，看板条目数随之变化。

## 快捷键（#192）

键位尽量照搬 GitHub 网页。**一张表**（`src/renderer/shortcuts.ts` 的 `SHORTCUTS`）同时决定按键行为和「快捷键一览」（`?`）里列的内容，两者不会对不上；**一处判断**（同文件的 `resolve`）决定一次按键归谁。窗口只有一个按键监听，挂在 `App.tsx`（看板在设置页时被卸载，监听不能放在看板里）。

| 在哪 | 按键 | 效果 |
|---|---|---|
| 已登录的任何页面（看板、设置、「选哪种 App」说明页） | `/` | 跳到搜索框（在别的页面先回到看板） |
| | `C` | 新建 issue（在别的页面先回到看板；离线或没有来源时不弹，和按钮一样） |
| | ⌘R | 立即同步，停在当前页；正在同步时放弃这一轮、马上重新开始（同刷新按钮） |
| | ⌘, | 打开设置 |
| | `?` | 快捷键一览 |
| 详情面板（光标不在输入框里） | `L` / `M` | 标签 / 里程碑选择框 |
| | `R` | 跳到回复框 |
| | Esc | 收起；回复框里有没发出的文字时不收起，出一行提示 |
| 回复框 | ⌘↩ | 发送 |
| | ⌘⇧P | 预览 / 继续编辑 |
| | Esc | 离开回复框，文字保留 |
| 标签 / 里程碑选择框 | ↑↓ ↩ Esc | 选择、加上或去掉、收起 |
| 所有确认对话框 | ⌘↩ / Esc | 确认 / 取消；新建 issue 有字时 Esc 不取消 |

规则：

- **谁接键**，按顺序：没登录一律不响应；**输入法正在拼字时一律不响应**（⌘↩ 不会把没拼完的字发出去，Esc 只取消拼字）；对话框、选择框、快捷键一览开着时只有它自己的键（Esc 只关最上面那一层）；光标在输入框 / 下拉框里时单个字母就是打字，只有 ⌘ 组合键生效（回复框另有自己的 ⌘↩ / ⌘⇧P / Esc）；其余情况全局键和详情面板的键生效。⌘ 和 Ctrl 都认（发布的只有 macOS 版；Ctrl 给 Linux 上的自动测试），按键提示按平台写 ⌘ 或 Ctrl。
- **快捷键只替你点按钮**：每个键调用的就是那个按钮自己的处理，按钮变灰时（离线、正在发送、内容为空）键也不做事。合并、关闭不配单键，只能在确认对话框里确认；对话框里单按回车什么都不做（焦点在按钮上也一样），只有点按钮或 ⌘↩ 才确认。
- **要用到看板的键**（`/`、`C`）在别的页面按时，先切回看板再交给看板做一次；看板做完就清掉，以后回到看板不会重复（做法同「点通知打开那一条」）。
- **标签选择框**：候选是这个仓库的标签（和原来的下拉同一份数据），已有的打 ✓；回车或点一下 = 发一次「加这个」或「删这个」，框不收起，可以接着改；发送中整个框变灰、不排队。不提供「关框时一次写整份标签」——那会冲掉别人刚加的标签。鼠标点「+ 加标签」打开的也是它。里程碑框单选，回车就改并收起，再选一次当前的就是去掉，只列仓库已有的里程碑。
- **Esc 不丢字**：只管键盘。点「收起 ›」、切到别的条目，回复框里的文字照旧丢掉（和以前一样）；不做跨面板的草稿保存。「关闭 issue / 关闭 PR」附的那句评论在取消后仍在（存在面板里）；点了确认以后，它跟着那次操作存（GitHub#250，见上文「草稿另一条规则」）。
- 点过讨论区之后，键盘停在隔离的讨论框里，快捷键传不出来（同 Esc 的限制，PR #171 维护者选的）；先点一下讨论区以外的地方。
- ⌘R、⌘, 由窗口自己处理并拦下默认行为；Tauri 在 macOS 上的默认菜单不占这两个键（未在 Mac 实机核对）。缩放的 ⌘= / ⌘- / ⌘0 仍在菜单里。

## 搜索、筛选和表格视图（#137）

**搜索框**在客户端本地、对缓存数据筛，写法沿用 GitHub 网页（`src/shared/filter.ts`，打字即出结果，停手 0.3 秒后存进视图设置）：

| 写法 | 说明 |
|---|---|
| 文字 | 匹配标题、编号（`135` / `#135`）、标签名；不分大小写；中文词中间也能搜到（GitHub 按空格和标点切词，「看板客户端」里的「客户端」它搜不到） |
| `label:` `status:` `milestone:` `assignee:` `author:` `repo:` `iteration:` | 值完全相等、不分大小写；`repo:` 要写 `组织/仓库名` |
| `iteration:@current` / `@next` / `@previous`，`assignee:@me` / `author:@me` | 迭代按各自 Project 的期次算 |
| `no:` / `has:` 加 `label` `assignee` `milestone` `iteration` `status` | |
| `is:open` `closed`（含已合并的 PR，和 GitHub 一样）`merged` `issue` `pr` | |
| `project:` | 本客户端新增：按来源 Project 的标题、编号或网址筛 |
| `-` 取反、逗号「或」、引号包住带空格的值 | 同一字段写两次是「且」 |

不支持的写法（正文 / 评论、日期比较、`reason:`、自定义字段——包括中文字段名 `优先级:高` 和带引号的 `"Start date":…`、`sort:`、文字前加 `-`、`is:draft` 这类不认识的值……）一律在黄条里点名、忽略，结果可能比网页多，**绝不会因为一个不认识的词变成「0 条」**（GitHub 自己对不认识的写法会静默返回 0 条，`-文字` 也是）。某个来源这次没读全时，顶栏刷新按钮左边出现黄色 ⚠️（见下）。

有来源这次读取失败时不再出整宽黄条（GitHub#248），只在刷新按钮左边出一个黄色 ⚠️；点一下弹出详情：每个失败的来源一行（来源名、失败原因、显示的是多久前的数据），正在筛选时再加一行「筛选结果可能不全」，底部「重新同步」。再点一下、点外面或按 Esc 收起；不会自己弹开。两部分各按原来黄条的条件出现：「同步不完整」离线时不出（离线黄条已说明数据截至何时），「筛选可能不全」离线时照出——所以离线且在筛选时 ⚠️ 仍在、详情只有筛选那一行，离线不筛选时没有 ⚠️。下一轮全部读成功，⚠️ 和详情一起消失。判断在 `src/renderer/warnings.ts` 的 `syncTrouble` 一处。

看板上的黄条（不支持的写法、离线、同步问题、通知被拒）右侧都有「×」，点了只收起那一条。按「问题本身」记，不按文字记：只是时间过去（「1 分钟前」变「5 分钟前」）、在看板和设置页之间来回切，都保持收起；问题内容变了（不支持的词、同步问题的原因不同）、问题恢复后又出现、取消筛选后再筛选，都会重新出现。只记在本次运行里，重开 App 后仍存在的问题照常显示。

`author:` GitHub 的 Project 筛选并不支持（录制时 `author:x` 和 `-author:x` 都返回 0 条），本客户端按条目的作者筛。

**和 GitHub 对拍**：`record.mjs` 录看板数据的同一次运行里，用 GitHub 的服务端筛选（`items(query:)`）跑一遍约 50 条查询，`test/unit/filter-parity.test.ts` 要求客户端对每条筛出完全相同的条目。只有两类预期不同、单独断言：中文词中间（客户端更全）和 `author:`（GitHub 不支持）。

**表格视图**和看板并存，工具栏右侧切换。排序是两种布局共用的：看板每一列里卡片的顺序、表格里行的顺序都按它（导入的「按更新时间从新到旧」在看板上同样生效）。表格的「视图设置」里还能改：分组（迭代 / 状态 / 里程碑 / 仓库 / 不分组）、排序（含「Project 里的顺序」）、显示哪些列、左侧按仓库切片、子 issue 缩进在父 issue 下。GitHub#205：标签、迭代、状态、里程碑四列点一下单元格就能改（和详情用同一套修改：标签是同一个选择器、一次一个加 / 摘；迭代和状态每个 Project 一个下拉框；离线时不可点），结果显示在看板顶部；分组栏整行着色、左边一条色条、滚动时贴在表头下面；拖动表头右边缘改列宽（60–2000 px，存进视图设置，重开保持），双击恢复默认。一个条目在两个 Project 里迭代或状态不同时，在两组里各出现一次（和看板一样）。「无迭代 / 无状态 / 无里程碑」组排在所有有值的组后面，和网页一致（GitHub#231；看板的「无迭代」列位置不变）。收起了哪些组存在本机设置里（GitHub#231），按分组方式分开记，切到看板再切回来、重开 App 都保持；每种分组方式最多记 200 个组，超出丢最早收起的。迭代下拉（详情和表格单元格同一个，`src/renderer/iterationOptions.tsx`）分三段：「当前」（文字后加「（当前）」；macOS 原生下拉不能给单个选项上色）→「即将开始」由近到远 →「已结束」最近结束的在前；读到的迭代顺序不影响结果。子 issue 只在父 issue 也在同一组里时才缩进。

**左边仓库栏选「全部」时先按仓库分**（#213）：开着「左侧按仓库切片」、选的是「全部」时，表格先按仓库分大组（和左边仓库栏同样按字母序，仓库名大小写不同算同一个），每个仓库下面再按视图设置里的分组方式分小组，只列这个仓库有条目的组。仓库标题旁的数字是这个仓库的条目数：一个条目因为两个 Project 意见不同落进两个小组，会出现两行，但只算一次。仓库和仓库下的小组都能各自收起，收起一个仓库的某个组不影响另一个仓库的同名组。点左边某个仓库、关掉「左侧按仓库切片」，或分组方式本身选「仓库」时，表格只有一层，和以前一样；分组选「不分组」时只剩仓库一层。分仓库后，子 issue 或 PR 和父 issue 不在同一个仓库时不再缩进在父 issue 下，而是在自己仓库里作为顶层行。规则在 `src/data/table.ts` 一处：每个仓库的小组和「只选这个仓库」时完全一样，测试逐仓库对拍。

**导入网页视图**：添加 Project 时，第一次完整读到它之后导入它网页上存的一个视图（贴的网址带 `/views/N` 就导那个，没带就导第一个）：布局、分组、排序、列、筛选。只导入一次——之后网页上改了视图不会跟着变；导入前用户已经动过的设置以用户为准；删掉再加这个 Project 会重新导入。做不到的部分（自定义字段分组 / 排序 / 列、路线图布局、多级排序）在视图顶部列出来。GitHub 的接口不返回「按仓库切片」和「显示层级」两个开关，导入时都设成开。仓库来源（REST）读不到「关联 PR」，那一格显示「—」。

## `pending/human` 提醒（#139，#169 在 Tauri 上重做，#251 收窄）

「待处理」= 所有已加入来源里**开着的** issue / PR（草稿 PR 也算开着）、并且带「等人处理的标签」（默认 `pending/human`，不区分大小写）的条目。已关闭的 issue、已关闭 / 已合并的 PR 不算待办，不论标签（#251：维护者「通知也只通知新的待办 issue/pr」；#139 原先连关闭的也算）。这个标签名和「交回 agent」摘掉的是**同一个设置**（`handBack.human`），改一处两边一起变。通知和 Dock 角标都由 `src/data/pending.ts` 的同一个 `PendingTracker` 算出（「开着且带标签」只有 `isPending()` 一处），角标是其中的未读部分（见下），controller 只在一轮同步收下结果后把「这一轮完整读到、且仍属于这次添加」的那些快照喂给它（和写缓存用的是同一份 `accepted`）。

| 情况 | 结果 |
|---|---|
| 某来源这一轮没读全（断网、凭据失效、分页中途失败） | 它不参与比较，沿用上一轮的那份：不报新增，也不报移除 |
| 某来源在这次运行里第一次读全（启动、新加来源、换账号） | 它已有的条目只当比较起点（历史）：**不通知、不汇总、不算未读**（#251 去掉了原来的启动汇总） |
| 已读全过的来源里，某条目上一轮不是待处理、这一轮是 | 通知一次；摘掉再挂上、或带着标签被重新打开，都算新出现；关闭的条目新挂标签不通知 |
| 点一条条目通知 | 窗口回到前面，App 里打开那一条的详情；它已不在看板上（比如来源刚删掉）就在浏览器打开 |
| 同一条目在几个来源里 | 按 `仓库#编号` 只算一个、只通知一次 |
| 删除来源 / 改标签名 | 静默重算，不发通知；不会让未读变多（只会因条目不再算待处理而变少） |
| 退出登录 / 换账号 | 清零，下次第一次读全时重新取起点（不通知） |
| 在 App 里改了一条（加 / 摘标签、交回 agent） | 只重读那一条进缓存，不喂给提醒；角标在下一轮同步（≤ 60 秒）时跟上。自己在 App 里打上 `pending/human` 也会在下一轮收到一次通知（窗口在前台，所以不算未读） |

**Dock 角标只是未读数**（#185；维护者在 PR #194 上改定：「角标变成未读数，切换到 app 后清空，同时清空之前发的 notification」；#251 去掉历史）：

- **未读** = 窗口不在前台时一轮里新出现的待处理条目，只算其中仍然待处理的（还没看就被摘掉标签或关掉的那条不再算）。第一次读到某来源时已有的条目是历史，不进未读。controller 记一份未读集合（`unread`），角标发 `unreadNow()` = 未读集合里当前仍待处理的条数（`PendingTracker.has()`）；计数时不删记录，所以改标签名再改回来不会把没看过的条目当成看过。窗口在前台时新来的条目照样发通知，但不进未读。
- **切到 App 就是看过**：外壳在主窗口获得焦点时发 `active`、失去焦点或关窗隐藏时发 `inactive`（`src-tauri/src/main.rs` 的 `WindowEvent::Focused` / 关窗分支，`desktop.rs` 的 `set_active`）。收到 `active`，controller 清空未读、把角标设成 0，再排队调 `desktop_clear_notifications`：macOS 上 `removeAllDeliveredNotifications` 收起本 App 留在通知中心的全部通知。点 Dock 图标、点通知都会让窗口获得焦点，走的是同一条路。退出登录清空未读。
- **设置页不列条目、不显示总数**（#251：「设置里也不用把所有的都列出来」）：「提醒」一节只说明规则（哪个标签、关闭的不提醒、启动时已有的不算）、通知被系统拒绝时的提示、开机自启开关。#185 的待处理列表和「未读 N · 现在待处理 M」已删；`AppState.pendingCount` 仍在（测试用），界面不显示。
- 外壳的通知类型里仍保留 `summary`：打包检查（`--notify-check`）发的那条测试通知用它；App 自己不再发。

**桌面这一侧在外壳里**（`src-tauri/src/desktop.rs`、`mac.rs`），窗口经 `src/app/desktop.ts` 的约定调用它，这些命令都不碰凭据：

- **通知**：macOS 上用系统现行的通知接口（UserNotifications），第一次发之前向系统申请权限，每条的结果（成功 / 系统原话）回报给窗口；拒绝时看板顶部和设置页显示提示，下一条成功后清掉。不用 Tauri 官方通知插件：它在 macOS 上查权限一律回「已允许」、发送失败不回传（按插件仓库提交 `4356356d`、插件 2.7.0 的源码核对），「被拒要让人看见」就做不到。没打包的开发版（`npm start`）不发通知。
- **角标**：Tauri 窗口的设角标接口（Dock 图标的数字），0 时清掉。数字是未读数（见上）。
- **收起已发的通知**：`desktop_clear_notifications`，macOS 上 `UNUserNotificationCenter.removeAllDeliveredNotifications`，只动本 App 的通知；其他系统不做事。
- **窗口在不在前台**：主窗口获得 / 失去焦点、关窗隐藏时，外壳发 `active` / `inactive` 事件，也写进测试记录。
- **开机自启**：Tauri 官方开机自启插件，macOS 用登录项 LaunchAgent（`~/Library/LaunchAgents`），启动参数带 `--hidden`：不显示窗口，照常同步提醒。
- **关窗只隐藏**（macOS）：拦下关窗请求改成隐藏，点 Dock 图标（系统的「重新打开」事件）窗口回来，⌘Q 退出。其他系统 v1 不显示通知和角标、关窗即退出，计数照常。
- **要求 macOS 14 或更新**（`tauri.conf.json` 的 `minimumSystemVersion`，维护者在 PR #173 定的）：窗口隐藏后网页还能继续跑，靠的是网页引擎「不挂起看不见的页面」这个开关，它从 macOS 14 起才生效；11–13 上没有办法保证关窗后继续提醒，所以不再支持。窗口仍按 Safari 14 的网页引擎构建（比需要的更宽），旧引擎的界面测试照留。`scripts/mac-open-check.sh` 第 0c 步核对打出来的 App 确实要求 14。
- **同步节拍在外壳**：外壳每 60 秒告诉窗口「该同步了」，窗口收到才同步（窗口里不再有定时器）——隐藏窗口的定时器会被网页引擎放慢。macOS 上另外声明一个「用户发起的活动」，不让系统的 App 小憩把没有窗口的 App 停掉。
- **窗口对外壳的调用一次只发一条**：隐藏窗口里同时发出的第二条请求可能被压到下一次唤醒（实测：角标比通知晚了整整一拍，超过 2 分钟的承诺），所以 controller 把它们排成队。

**测试模式**（只在 `CAVIL_CLIENT_TEST_MODE=1` 且 GitHub 指向本机回环时生效）：`CAVIL_CLIENT_TEST_ALERTS_FILE` 把每次通知 / 角标 / 节拍（带当时窗口是否可见）/ 隐藏 / 显示写成一行 JSON，不弹真通知；`CAVIL_CLIENT_TEST_NOTIFY_REFUSE=<消息>` 模拟系统拒绝；`CAVIL_CLIENT_TEST_TICK_MS` 改节拍；`CAVIL_CLIENT_TEST_HIDE_ON_CLOSE=1` 让 Linux 上也关窗只隐藏；`CAVIL_CLIENT_TEST_CONTROL_FILE` 里追加 `close`（和关窗按钮同一个请求）、`click <通知 id>`（和点那条通知同一段处理）或 `activate`（和窗口获得焦点同一段处理：没有窗口管理器的测试显示上焦点事件不一定有）。

**怎么验的**：

| 层 | 测什么 | 判失败 |
|---|---|---|
| `test/unit/pending.test.ts` | 只算开着的（关闭的 issue、已合并的 PR 挂标签不通知；带标签重新打开通知一次、再关掉就不算未读）、启动和新加来源时已有的一律不通知不汇总不算未读（录制数据里带标签的都是已关闭的历史条目）、去重、读失败、离线启动、删来源、改标签名、退出、被拒、节拍、点通知、开机自启（真实后台子进程 + 假 GitHub）；每轮都核对「角标 = 未读 ≤ 待处理、除条目通知外没有任何别的通知」；未读：切到窗口清零并收起通知、在前台时新来的不算、离开后重新计数、摘标签不再算、改设置不增加、退出清空（#185、#251） | 是 |

## 登录用的 GitHub 应用

浏览器授权走 GitHub 的设备授权流程（App 显示短码，浏览器里输入、同意）。登录页和设置页都有「登录方式」二选一：**默认 OAuth 应用**（已内置），用户想用时可选 **GitHub App**（预览，维护者 2026-11-05 在 #140 定：第一版先把 OAuth 做完整，GitHub App 以后再完整支持）。选项旁的小字链接「两种有什么区别？」打开一页说明（纯本地文字）。说明页、选项下的权限说明和登录前的 Client ID 核对都来自 `src/shared/appKind.ts` 一处：只说能确定的事——OAuth 应用申请的 scope 是本客户端定的，可以写明；GitHub App 的权限由那个 App 登记时决定、登录请求收窄不了，所以不承诺「碰不到代码」；令牌过不过期是各自应用的设置，不按登录方式一刀切。Client ID 和所选方式对不上（GitHub App 的 ID 以 `Iv` 开头，OAuth 应用的不是）时，输入框当场提示、不让保存，登录也直接拒绝、不联系 GitHub。登录代码本身不区分两种：

| | OAuth 应用（默认，已内置） | GitHub App（可选，预览） |
|---|---|---|
| 权限 | 本客户端整块申请：`repo`（含代码与设置）、`read:org`、`project` | 由 App 登记时逐项勾选（下面「建 GitHub App」推荐只勾 Issues、Pull requests、Projects 读写 + 仓库基本信息只读）；登录时收窄不了，以授权页为准 |
| 令牌 | 看应用设置：开了令牌过期就带续期令牌，没开就不过期 | 看 App 设置：默认 8 小时过期、带续期令牌（约 6 个月），建 App 时可关；GitHub 每次续期都换一个新的续期令牌 |
| 能看到的 | 账号能看到的、申请范围内的 | 账号能看到的、App 权限允许的、App 装到的仓库，三者交集 |
| 这一版 | 内置 Client ID，直接登录 | 没有内置的 App：要填自己建的 GitHub App 的 Client ID；还没做的：内置 App、引导组织安装、提示「哪些仓库没装到」 |

客户端会在令牌到期前 5 分钟自动续期，GitHub 说 401 时也先续期重试一次。续期只在一处进行，同一时刻最多一次（续期令牌用过即作废）。续期的结果只有这几种（`src-tauri/crates/core/src/engine.rs` 的 `ensure_fresh` 注释里逐条列着）：

| 续期遇到的 | 结果 |
|---|---|
| 连不上、超时、HTTP 5xx / 429（不管正文写什么） | 暂时不可用：登录、凭据、缓存都保留，下一轮再试 |
| GitHub 回 `bad_refresh_token`（续期令牌错误或过期） | 回登录页并说明原因 |
| 其他错误、回应无法解析、没有新令牌 | 不能证明凭据失效：保留一切，顶部提示，下一轮再试 |
| 拿到新令牌但写钥匙串失败 | GitHub 已作废旧续期令牌，所以新令牌留在内存里继续用、顶部提示，之后每轮重试保存；保存成功前退出 App，下次要重新登录 |
| 续期途中退出登录 / 换账号 | 退出、新登录优先，这次续期什么都不留 |

任何情况下续期都不会抛出没人处理的错误（有真实子进程测试守着）。

**启动时只用「可信」的凭据**：本地数据库里记着一份可信名单（只存凭据的哈希，写入是同步落盘的）。启动时钥匙串里的凭据不在名单上，就不用它登录，回登录页并把它删掉。名单只在这几处改：

| 时机 | 名单怎么变 | 为什么 |
|---|---|---|
| 退出登录（手动、续期被拒、续期令牌到期） | **第一步**清空，然后才切页面、才排队删钥匙串 | 删除排队中、进行中、失败、或进程直接被关掉，重启都不会用旧凭据 |
| 登录 | 写钥匙串前清空；写成功且这次登录没被取消，才加入新凭据 | 写到一半被关掉、或被取消，重启都不信它 |
| 续期 | 写钥匙串时同时信任新旧两份；写成功后只留新的 | 写到一半被关掉，重启用新的继续，不用重新登录 |
| 名单从没写过（这条规则之前的预览版留下的数据） | 当作空名单：不用钥匙串里那份，回登录页并删掉它 | 旧数据分不清「还登录着」和「退出了但没删掉」（只有最后一版预览会记「不得复用」，更早的什么都不记），所以一律不信。代价是装过预览版的人升级后要重新登录一次 |

退出时钥匙串删不掉，登录页会写明旧凭据可能还在钥匙串里；它已不在名单上，下次启动会再试着删。两进程测试（`test/unit/crash-restart.test.ts`）在每个时刻结束第一个进程，再用同一份磁盘数据启动第二个进程核对。

内置的 Client ID 在 `src/shared/config.ts`：OAuth 应用是 `DEFAULT_OAUTH_CLIENT_ID`，GitHub App 是 `DEFAULT_GITHUB_APP_CLIENT_ID`（目前为空）。Client ID 不是秘密。两种方式各存各的覆盖值（`oauthClientId` / `githubAppClientId`），在登录页或设置页「改 Client ID」里改；选了 GitHub App 而没有 Client ID 时，登录直接说明要填什么，不会联系 GitHub。预览版只有一格 Client ID：里面存的是 GitHub App 的 ID（`Iv` 开头）时，升级后自动归到 GitHub App 那一格并保持选 GitHub App。续期时用的是登录那一刻的 Client ID，之后改登录方式或 Client ID 都不影响已登录的令牌（有测试）。

### 建 GitHub App 的逐项设置

1. 在 GigleAI 组织页「Settings → Developer settings → GitHub Apps → New GitHub App」新建（建在组织下，组织的 Project 才能授权给它）。
2. **GitHub App name**：`Cavil Loop`；**Homepage URL**：`https://github.com/GigleAI/cavil-loop`。
3. **Identifying and authorizing users**：勾 **Expire user authorization tokens**（默认已勾）；**Callback URL** 留空也行（设备授权用不到）；不勾「Request user authorization (OAuth) during installation」。
4. 勾 **Enable Device Flow**。
5. **Webhook**：取消勾选 **Active**（客户端不需要回调）。
6. **Permissions**：
   - Repository permissions：**Issues** = Read and write；**Pull requests** = Read and write；**Metadata** = Read-only（必选）。其余保持 No access。
   - Organization permissions：**Projects** = Read and write。其余保持 No access。
   - Account permissions：全部 No access。
7. **Where can this GitHub App be installed?**：Only on this account。点 **Create GitHub App**。
8. 不需要生成 Client secret，也不需要 Private key。
9. 在 App 页面左侧 **Install App** → 安装到 GigleAI → 选 All repositories 或要看的那几个仓库。
10. 把 App 页面上的 **Client ID**（形如 `Iv23li…`）写进 `DEFAULT_GITHUB_APP_CLIENT_ID`，或先在登录页选「GitHub App」、把它填进 Client ID 框试用。

要在客户端里**合并 PR**，按 GitHub 文档 App 还要 **Contents** = Read and write（上面没勾；OAuth 应用的 `repo` 已含这项）。不加的话，其他操作照常，合并会被 GitHub 拒绝、界面照实显示原因。

## 自动更新（#184）

**谁做什么**：判断全在后台本体 `src-tauri/crates/core/src/update.rs`（App 和测试后台跑同一份）；碰到已安装 App 的部分（读更新说明、下载、验签、换掉 App 包）是外壳的 `src-tauri/src/updater.rs`，用 Tauri 官方更新插件；窗口只显示外壳报来的状态（`state.update`，设置页「更新」一节 + 看板顶部的「已下载」提示条，`src/renderer/UpdateViews.tsx`）。

- **挑哪个版本**（`update::pick`）：读本仓库发版列表（不带令牌，最多 10 页），只认标签 `client/vX.Y.Z`（三段纯数字、不带前导零）、不是草稿也不是预发布、版本号比当前大的；取版本号最大的，不看发布时间。它的附件里必须有 `latest.json`，而且地址在本仓库的下载地址下，否则判失败（不退而求其次装更旧的）。
- **两个渠道**（#215，设置页「更新渠道」，存在本机设置 `update.channel`，默认正式版，看不懂的值按正式版）：**正式版**只按上一条挑；**开发版**另外认标签 `client/vX.Y.Z-dev.N`、而且标成预发布的发版（main 上每次客户端改动由 CI 发，见下面「开发版」）。两种一起比版本号：按 semver 的先后——同一个 X.Y.Z，正式版比它的开发版高；开发版之间按 N 的数值比（`dev.10` > `dev.9`）。形状不对的（`-rc.1`、`-dev.01`、标成预发布的 `X.Y.Z`、没标预发布的 `-dev.N`）两个渠道都不认。从开发版切回正式版不降级：等下一个比当前高的正式版。开发版只有 Apple 芯片的包（`update::DEV_TARGETS`，和发版说明生成器 `CHANNEL_PLATFORMS.dev` 是同一张表，测试对拍），Intel Mac 上开发版选项置灰并写明原因。
- **切渠道遇上正在进行的一轮**：切换和「这一轮属于哪个渠道」在同一把锁下记一个代号；一轮在读列表、读更新说明、下载时看到代号变了就作废（读到的丢掉，下载停掉），随即按新渠道重来一轮；下载完、开始换 App 之前在同一把锁下再核对一次。正在换 App（「正在安装 X」）时换不了、也停不下来，这时切换被拒绝，单选置灰。已装好等重启时可以切，已换上的版本不撤回，重启前不再查。
- **什么时候查**：启动时一次，之后每 6 小时一次；关掉「自动检查更新」后都不查，手动「立即检查」照查。一次只跑一轮：跑着时再点不会再开一轮；新版装好以后不再查（重启就是新版）。
- **失败不等于已是最新**：发版列表或更新说明 30 秒没回应、任一页读失败、内容看不懂、下载 60 秒收不到数据（按「多久没收到数据」算，不按总时长）、中途断开、签名不符、换 App 失败，都记成失败并写明原因，下一轮再试；只有真的没有更高版本才说「已是最新」。
- **免放行命令的依据**：macOS 只拦带「从网络下载」标记的 App，这个标记是浏览器下载时加的。更新插件用自己的网络代码下载、在进程里解包换掉 App，不加这个标记；万一换上的新版带着标记，`updater.rs` 会把新版自己身上的去掉。CI 的 Mac 上真跑更新核对（`scripts/mac-update-check.sh`）。
- **哪些构建查更新**（`updater::mode`）：只有发布的 macOS App。开发版、`--smoke-test` / `--notify-check`、测试模式（除非 `CAVIL_CLIENT_TEST_UPDATE=1`）、Linux 都不查，设置页也不出现「更新」一节。公钥（`tauri.conf.json` 的 `plugins.updater.pubkey`）空着时设置页写明「这一版没有带更新用的公钥」，从不去查。
- **只在测试构建里有的开关**（cargo feature `update-test`，`scripts/mac-update-check.sh` 用）：公钥可以从 `CAVIL_CLIENT_TEST_UPDATE_PUBKEY` 来，调试构建也会查更新。发布的 App 不带这个 feature。

**怎么验的**：

## 发版

**开发版**（#215）：客户端改动每次合进 main，`.github/workflows/client.yml` 在 Apple 芯片的 Mac 上打包前把版本号改成 `X.Y.(Z+1)-dev.N`（`scripts/dev-version.mjs`：X.Y.Z 是三处一致的当前版本号，N 是 main 上的提交数；只改 CI 机器上的工作区，不提交），用发版签名私钥签名（和正式版同一把，维护者在 #215 定的），快速测试、打包、体积门槛、真实更新检查都过了以后，由 `publish development build` 这一步（`scripts/dev-release.mjs`）发成预发布：先建草稿带齐文件再发布，已有更高的开发版就不发，只留版本号最高的 10 个（连标签一起删更旧的；正式版、daemon 的发版、别的形状一概不碰）。删除时逐个处理，每个分三步：先把它改成草稿（装着的 App 就看不到了；草稿上记着标签名和它来自的提交），再删它的标签，最后删草稿。每一步之前都重新读一次发版列表，按发版编号（不按标签名）找到它，用同一条规则重判它还该不该删，不该删（被改成不是预发布、同名换了一个发版、进了最新 10 个）就跳过。进度都记在 GitHub 上，不靠本机：哪一步暂时失败（读不到、删不掉、进程被杀），这个版本就停在「已发布」或「草稿」，下一次合并按同一规则接着做完；比当前最高开发版低的开发版草稿都在清理范围里。标签只在没有别的发版用它、而且仍指向草稿记下的那个提交时才删；读不到标签算暂时失败（留着草稿下次再来），确定不是它的标签（指向别的提交、别的发版在用）才放过标签、照删草稿。GitHub 没有「内容没变才删」的接口，最后一次重读和写之间的变化仍拦不住。每周定时和手动触发的打包也改成开发版号，但用一次性密钥、不发布。

**正式版**：改 `package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml` 的 `version`（三处一致）→ 合入 main → 打标签 `client/vX.Y.Z` 并推送。`.github/workflows/client.yml` 会在两台 Mac 上各打一个 dmg 和一个更新包（`tauri build --bundles app`，带 `createUpdaterArtifacts` + `scripts/make-dmg.mjs`）、过体积门槛（`scripts/size-gate.mjs`：dmg 和更新包每个 ≤ 20 MB）、跑 `scripts/mac-open-check.sh` 和 `scripts/mac-update-check.sh`，通过后生成 `latest.json`（`scripts/update-manifest.mjs`）并建 Release，附件是两个 dmg、两个更新包（`Cavil-Loop-<版本>-<芯片>.app.tar.gz`）和它们的签名（`.sig`）、`latest.json`（说明取自 `RELEASE_NOTES.md`，不标成 Latest，daemon 的每周发版不受影响）。

**更新签名密钥**（#184，维护者做一次）：公钥只放一处——`src-tauri/tauri.conf.json` 的 `plugins.updater.pubkey`：App 运行时用它验更新包，打包时打包工具用它，发版前生成 `latest.json` 那一步也用它逐个验签。发版标签的更新包用仓库 Actions secret `TAURI_SIGNING_PRIVATE_KEY`（有密码时再加 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`）签名。发版标签上缺这个 secret、或公钥是空的，打包直接失败；更新包的签名用公钥验不过（包被改过、签名坏了、不是这把钥匙签的、绑定的版本不对），生成 `latest.json` 那一步拒绝发版。合入 main 的打包（开发版，#215）也用这把私钥签名，同样缺 secret 或公钥空着就失败。每周定时和手动触发的打包用每次现生成的一对一次性密钥（同样的文件、同样过体积门槛和真实更新检查，但这些包不会被发出去）。

在自己的 Mac 上，进仓库的 `client/` 目录，**一条一条**跑下面的命令；任何一条报错就停下，先看下面「出错了怎么办」，不要继续上传。

第一条先进到仓库的 `client/` 目录（在仓库里任何位置跑都行）；第二条把公钥写进 `client/src-tauri/tauri.conf.json`，打印「已把公钥（密钥编号 …）写进 …」。后两条用私钥签一个小文件（会问一次密码，填第一段设的那个），再用刚写进去的公钥验它：看到「✅ … 签名有效」才算这对钥匙能用。

**出错了怎么办**

- **签名那一步密码输错了**：钥匙没坏，**不要**重跑第一段（它不会覆盖已有的钥匙，会报 `already exists`）。把第二段整段再跑一次，输对密码即可——它会重新写入同一把公钥、重新签名、重新验签，钥匙文件不会变。
- **密码忘了、或者想换一把钥匙**：只有在还没用这把钥匙发过版时才这样做（发过版的话，已装好的 App 只认旧钥匙，换了以后大家要再手动装一次）。先删掉旧的两个文件，再从第一段开始：

<!-- update-key-steps:replace:begin -->
```bash
rm ~/.tauri/cavil-loop-updater.key ~/.tauri/cavil-loop-updater.key.pub
```
<!-- update-key-steps:replace:end -->

- **不想继续了**：`git checkout "$(git rev-parse --show-toplevel)/client/src-tauri/tauri.conf.json"` 退回公钥那一处改动；钥匙文件留在 `~/.tauri/` 里不影响任何东西。

钥匙检查通过之后：

1. 仓库 **Settings → Secrets and variables → Actions → New repository secret**：`TAURI_SIGNING_PRIVATE_KEY` = 私钥文件全部内容；设了密码再建 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。列表里出现这两个名字就算成功。私钥和密码不要贴到任何评论里。
2. 把改过的 `src-tauri/tauri.conf.json`（只多了公钥）提交，随一个版本号升级一起合入 main。
3. 私钥另外备份。丢了只能换一把新的：已经装好的 App 认不出新钥匙签的包，大家要再手动装一次（含一次放行）。

`test/unit/update-key-steps.test.ts` 把上面三段命令原样取出，在伪终端里照上面写的走：正常一遍；签名输错密码 → 只重跑第二段 → 验签成功、钥匙文件一个字节没变；重跑第一段会被拒 → 跑「换钥匙」那段 → 重新生成并检查成功，钥匙换成了新的。
